# ADR-P3 (เลขถัดไปตอนรับเข้า) — กะ เงินเข้า-ออกลิ้นชัก นับเงิน ใบปิดกะ (Z) เก็บในฐานกลาง

- สถานะ: **เสนอ** · 25 ก.ย. 2569 (ร่างจากทีม POS — สเปก POS §4.10 ก้อน 3, §6.2, §6.8 · เจ้าของตัดสิน Q43 (D68), Q52 (D76) · แก้ตามรีวิวรอบ 1 ข้อ 6, 7, 8, 11 · รอบ 2 ข้อ N1, N3 · รอบ 3 ข้อ R1–R4) · ขยาย ADR-0035 (ขอบเขตของ POS: เป็นเครื่องมือเรื่องเงิน) · ไม่แก้ ADR-0024 ข้อ 2 (บอทยังไม่มีคำสั่งกะ — กะมีเฉพาะที่แท็บเล็ต)
- บริบท: POS มีกะ ลิ้นชัก นับเงิน 9 ชนิดธนบัตร/เหรียญ และ Z ที่แก้ไม่ได้อยู่แล้วในเครื่อง (แผน 3b) · สถาปัตยกรรม C1 ให้ตัวเลขทั้งหมดอยู่ในฐานเดียว (Q15 · D62) · ขายได้ทั้ง POS และบอท (P2) เงินสดจากบิลบอทก็อยู่ในลิ้นชักเดียวกัน ตอนปิดกะแท็บเล็ตต้องดึงบิลเงินสดจากบอทมานับรวมในเงินสดที่ควรมี (ต้องออนไลน์) · วันหนึ่งมีได้หลายกะ และกะถัดไปเปิดได้ขณะกะก่อนรอ Z (Q43) จึงต้องไม่นับบิลบอทใบเดียวซ้ำสองกะ · โค้ด POS (`packages/domain/src/shift.ts`, D36) นับยอดขายเงินสดรวมบิลที่ยกเลิกภายหลังแล้วหักเงินคืนแยก · เจ้าของอยากเห็นสรุปกะบรรทัดเดียวบนแดชบอร์ด (Q20)
- ตัดสินใจ:
  1. ตาราง (ทุกตาราง: `id` จากแท็บเล็ต · `shop_id` · `api_client_id` · `created_at` (เวลาเครื่อง) · RLS เปิดไม่มี policy · append-only ด้วย trigger raise ยกเว้นคอลัมน์ปิดที่ตั้งได้ครั้งเดียวจาก null · เงิน `numeric(10,2)` · อยู่ในไฟล์สำรอง):
     - `shifts`: `business_date`, `opened_by`, `opened_at`, `opening_float`, `status` (`open` → `counted` เมื่อรับ `cash_count` → `closed` เมื่อรับ Z), `closed_by`, `closed_at` · สถานะ `open` มีได้ครั้งละ 1 ต่อ `api_client_id` (unique partial)
     - `cash_movements`: `shift_id`, `kind` (`PAID_IN`/`PAID_OUT`/`DROP`/`VOID_REFUND`), `amount > 0`, `pos_order_id` (เฉพาะ `VOID_REFUND` — check), `reason`, `created_by` · **`VOID_REFUND` เป็นแหล่งความจริงเดียวของเงินคืนจากบิลที่ยกเลิก** (แถว `order_void` ของ P2 ไม่มีข้อมูลคืนเงิน)
     - `cash_counts`: `shift_id`, `lines jsonb [{denomination, count}]` (1000/500/100/50/20/10/5/2/1 บาท), `counted`, `expected`, `variance`, `reason`, `counted_by`, `counted_at` (เวลาเครื่องตอนนับ)
     - `z_reports`: `shift_id` unique, `snapshot jsonb`, `hash` (โซ่แฮชของแท็บเล็ต), `recompute_status` (`waiting_bills`/`matched`/`mismatch`), `z_mismatch bool` (= `recompute_status='mismatch'`), `missing_pos_order_ids uuid[]`, `recomputed_at` · `snapshot` = `bot_window: {after, until}` + `bot_bills: [{order_no, version, total}]` + **`pos_bills: [{pos_order_id, receipt_no, payment, total, sold_at, voided_at, excluded}]` = บิล POS ทุกใบของกะ** (ทุกวิธีชำระ รวมที่ยกเลิก · `excluded` = owner ปิดเป็นรายการนอกระบบกลาง)
     - `pos_excluded_orders`: `pos_order_id` (unique ต่อ `api_client_id`), `shift_id`, `total numeric(10,2)`, `sold_at`, `reason`, `staff_id` (owner ที่กันออก), `created_at_device` — จากชนิด push `order_excluded`
     - **`orders.pos_shift_id` ไม่มี FK — ผูกทีหลังได้**: บิลที่อ้างกะที่ยังไม่มา (หรือกะถูกปฏิเสธ) บันทึกได้ทันที ไม่ถูกบล็อก · แดชบอร์ดแสดงบิลที่ `pos_shift_id` ยังไม่มีกะ · บิล POS ต้องส่ง `shift_id` ตั้งแต่ก้อนนี้
  2. ชนิดใหม่ของ `POST /v1/pos/push` (scope ใหม่ `shift:write`): `shift_open` · `cash_movement` · `cash_count` · `shift_close` (มี Z ในตัว) · `order_excluded` · **สัญญา `order_excluded` (ล็อก — ตรงกับสเปก POS §4.10 ก้อน 3)**: key = **`order_excluded:<pos_order_id>`** (ตามรูป `<kind>:<uuid>` — `pos_order_id` เป็น UUID · บิลละครั้งเดียว) · `data` = `{pos_order_id, shift_id, total, sold_at, reason, staff_id, created_at_device}` — `total` = ยอดบิลจาก `total_satang` แปลงด้วย `edgeSatangToBaht` · `staff_id` = owner ที่กดกันออกด้วย PIN · `reason` 1–200 · **สร้างบนแท็บเล็ตได้เฉพาะ role owner** · อยู่ในช่องของกะนั้น (§6.2) · ฝั่ง dayo: `shift_close` ของกะนั้นยังไม่มา → `deferred PARENT_PENDING` · มีบิล `pos_order_id` นี้ใน `orders` แล้ว → **`rejected ALREADY_PRESENT`** (ตระกูลเดียวกับ `CONFLICT` — ห้ามกันบิลจริงออก) · ส่งซ้ำเนื้อหาเดิม = `duplicate` · บิลที่ถูกกันออกทุกใบ (ไม่ว่ากันออกก่อนหรือหลัง Z) ส่ง `order_excluded` หลัง `shift_close` · **เงินของบิลที่ถูกกันออก**: เงินสดถูกนับใน Z เดิมแล้ว (จาก snapshot) → **ห้ามบันทึก `PAID_IN`/`PAID_OUT` ในกะปัจจุบันสำหรับกรณีนี้** · รายได้เข้ารายงานกลางจาก `pos_excluded_orders` (ยอด + `sold_at` + เหตุผล) นับครั้งเดียว — ยอดขายรวมและ `dashboard_net_profit` บวกยอดนี้ตามวันที่ไทยของ `sold_at` พร้อมป้าย "บิลนอกระบบกลาง" (ต้นทุนไม่ทราบ = 0 พร้อมป้าย) · ข้อจำกัดที่ยอมรับ: บิลที่ถูกกันออกของกะ `local_only` หรือช่วงก้อน 2 (ไม่มีกะในฐาน) ไม่มีทางส่ง `order_excluded` — รายได้นั้นอยู่เฉพาะในรายงานของแท็บเล็ต · คำตัดสิน/กันซ้ำ/แผนที่ error แบบ P2 · แถวของกะเอง (`cash_movement` `cash_count` `shift_close`) ที่อ้างกะที่ยังไม่มี = `deferred PARENT_PENDING`
  3. **`GET /v1/pos/shift-cash?after=<ISO>&until=<ISO>`** (scope `orders:read`): บิล `status='ok'`, วิธีชำระ `cash`, `source in ('line','web')` ที่ `created_at` อยู่ในช่วง **`(after, until]`** → `{bills:[{order_no, version, source, sold_at, total, created_by_name}], cash_total}` · ไม่มีต้นทุน · **บิลบอทแต่ละใบถูกนับครั้งเดียว**: `until` = `counted_at` ของการนับครั้งนี้ · `after` = `counted_at` ของการนับครั้งก่อนของ API key นี้ (ไม่มี = 00:00 เวลาไทยของ `business_date`) · ช่วงเก็บใน `snapshot.bot_window`
  4. **เงินสดที่ควรมี** = เงินทอนตั้งต้น + ยอดเงินสดของ **บิล POS ทุกใบใน `snapshot.pos_bills` ที่ `sold_at` ≤ `counted_at` รวมใบที่ยกเลิกภายหลัง** − Σ `VOID_REFUND` + Σ `PAID_IN` − Σ `PAID_OUT` − Σ `DROP` − ค่าใช้จ่ายจ่ายจากลิ้นชักของกะ (P4) + Σ `snapshot.bot_bills` · แถวเงินสด/ค่าใช้จ่ายนับเฉพาะที่ `created_at` (เวลาเครื่องของตารางใหม่) ≤ `counted_at` · แท็บเล็ตคิดเป็นสตางค์และส่ง `expected` มา
     **การคิดซ้ำของฝั่งนี้**: ใช้รายการ id ใน snapshot กับแถวในฐาน และเวลาจากเครื่อง (`sold_at`, `voided_at`, `created_at`/`counted_at` ของตารางใหม่) — **ห้ามใช้ `orders.created_at`** (เวลาเซิร์ฟเวอร์รับบิล) · บิลในรายการยังไม่มาถึง (ไม่นับ `excluded` และที่อยู่ใน `pos_excluded_orders`) → `recompute_status = 'waiting_bills'` + `missing_pos_order_ids` (**ไม่ใช่ mismatch**) · **คิดซ้ำทุกครั้งที่บิล การยกเลิก หรือ `order_excluded` ของกะนั้นเข้ามา** · บิลครบแล้วตัวเลขยังต่าง → `mismatch` (`z_mismatch = true`) บันทึกตามที่แท็บเล็ตส่ง (แบบเดียวกับ `amount_mismatch` — ADR-0035 ข้อ 3) · ครบและตรง → `matched` · บิลที่ excluded ใช้ยอดจาก snapshot
  5. **ลำดับและเวลา**: แถวของกะเดียวกันเป็นช่องเดียวกันในคิวของแท็บเล็ต — แถวที่ได้ `deferred` หยุดแถวหลังในช่องนั้น (สเปก POS §6.2) · กติกาฝั่งนี้ตัดสินด้วยเวลาในแถว (`created_at`/`counted_at`/`closed_at`) ไม่ใช่สถานะ ณ ตอนแถวมาถึง
  6. บิลบอท/เว็บที่ไม่อยู่ใน Z ใดเลย หรือถูกแก้/ยกเลิกหลังถูกนับ (เทียบ `version` ใน snapshot): Z ไม่เปลี่ยน (แช่แข็ง) · แดชบอร์ดแสดงรายการ "บิลบอทนอกใบปิดกะ" / "เปลี่ยนหลังนับ"
  7. แดชบอร์ด (owner): 1 บรรทัดต่อกะ "กะ <วันที่> · เปิด <เวลา> <ชื่อ> · ปิด <เวลา> · เงินขาด/เกิน ฿<n>" + ป้าย `z_mismatch` · manager/staff เห็นใน `today_mini` เฉพาะสถานะกะ (เปิด/ปิด) ไม่เห็นยอดขาด/เกิน
  8. **กะก่อนก้อนนี้**: แถวกะ/เงินสดทุกชนิด (รวม `VOID_REFUND`) ของกะที่เปิดก่อนก้อนนี้ใช้งานจริงเป็นข้อมูลในเครื่องแท็บเล็ตเท่านั้น (`local_only`) **ไม่ถูกส่งมาเลย** · กะแรกในฐานนี้คือกะที่เปิดหลังเปิดใช้ก้อนนี้ · **บิลของกะ `local_only` ส่ง `shift_id: null` เสมอ แม้ก้อนนี้ใช้งานแล้ว** · วันที่เปิดใช้ก้อนนี้เก็บใน `shop_settings.block3_live_from` (ADR-0046) · รายการ "บิลบอทนอกใบปิดกะ" (ข้อ 6) นับเฉพาะบิลที่ `sale_date` ≥ ค่านี้
  9. ออฟไลน์ตอนปิดกะ (Q43 · D68): นับเงินบันทึกได้ตอนออฟไลน์ · Z ออกเมื่อออนไลน์และดึงบิลบอทได้ (ช่วงยังใช้ `counted_at` ของการนับ) · กะถัดไปเปิดได้ — ฝั่งนี้รองรับด้วยการรับ `cash_count` ก่อน `shift_close` และรับกะใหม่ของ client เดียวกันขณะกะก่อนอยู่สถานะ `counted` · unique นับเฉพาะสถานะ `open`
  10. บิล POS ของวันที่ปิดแล้วแก้ไม่ได้ (P2) · ส่วนต่างที่พบภายหลังแก้ด้วย `cash_movement` `PAID_IN`/`PAID_OUT` ในกะปัจจุบัน พร้อมเหตุผลอ้างเลขใบเสร็จ หรือบันทึกเป็นค่าใช้จ่าย (P4) (Q52)
- ทางเลือกที่ไม่เลือก: เก็บกะไว้แค่ในแท็บเล็ต (รายงานเงินอยู่สองที่ ขัด C1) · ให้บอทมีคำสั่งเปิด/ปิดกะ (ADR-0024) · ให้ dayo เป็นคนคิด expected แล้วส่งกลับ (แท็บเล็ตต้องออนไลน์ทุกครั้งที่ดูยอดลิ้นชัก) · เลือกบิลบอทด้วย `sale_date` ทั้งวัน (นับซ้ำเมื่อวันเดียวมีหลายกะ) · ใช้ `closed_at` เป็นเวลาตัด (เวลาออก Z อาจช้ากว่าเวลานับ) · FK `orders.pos_shift_id` (กะที่ถูกปฏิเสธจะบล็อกบิลทั้งกะ) · เก็บเงินคืนทั้งใน `order_void` และ `VOID_REFUND` (หักซ้ำ)
- ผลที่ตามมา: migration ใหม่ (4 ตาราง + trigger append-only + ชนิดใหม่ใน `api_pos_push` + `api_shift_cash` + `dashboard_shifts` + รายการ "บิลบอทนอกใบปิดกะ" และ "บิลยังไม่มีกะ") · route `app/api/v1/pos/shift-cash/route.ts` · scope `shift:write` · แดชบอร์ด · `backup_dump_table` · DATA-CONTRACT · API.md · GLOSSARY ("กะ", "ใบปิดกะ", "เงินสดที่ควรมี") · เทสต์: ปิดกะที่มีบิลเงินสดจากบอท 3 ใบ → expected รวม · สองกะในวันเดียว บิลบอทแต่ละใบอยู่ใน Z เดียว · บิลบอทหลัง `counted_at` ไม่อยู่ใน Z นี้ · ขายเงินสด ฿100 แล้วยกเลิกคืนเงิน → expected เท่าเงินทอนตั้งต้น (ไม่หักซ้ำ) และ `matched` · ขายออฟไลน์ทั้งกะ Z มาถึงก่อนบิล → `waiting_bills` แล้วเปลี่ยนเป็น `matched` เองเมื่อบิลครบ (ไม่ใช่ mismatch) · บิลครบแต่ตัวเลขต่าง → `mismatch` · บิล `excluded`/`order_excluded` ไม่ทำให้ค้าง `waiting_bills` · `order_excluded` ก่อน `shift_close` มา = `PARENT_PENDING` · `order_excluded` ของบิลที่มีในฐานแล้ว = `ALREADY_PRESENT` · ยอดบิลที่ถูกกันออกนับในยอดขาย/กำไรกลางครั้งเดียว และกะปัจจุบันไม่มี `PAID_IN` จากกรณีนี้ · บิลของกะ `local_only` หลังก้อนนี้ใช้งานส่ง `shift_id: null` ไม่ขึ้น "บิลยังไม่มีกะ" · บิลบอทก่อน `block3_live_from` ไม่ขึ้น "บิลบอทนอกใบปิดกะ" · กะถูกปฏิเสธ → บิลของกะยังบันทึกได้ · `z_mismatch` เมื่อแท็บเล็ตส่ง expected ผิด · update/delete ตารางกะ = raise · ส่งซ้ำ = duplicate · **ต้องล็อกรูปฟิลด์ของชนิด push ทั้ง 4 ในสเปก POS ก่อนเริ่มก้อน 3**
