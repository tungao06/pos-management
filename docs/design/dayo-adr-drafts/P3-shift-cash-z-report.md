# ADR-P3 (รับเข้าเป็น ADR-0056) — กะ เงินเข้า-ออกลิ้นชัก นับเงิน ใบปิดกะ (Z) และบิลนอกแคตตาล็อก ในฐานกลาง

- สถานะ: **เสนอ** · ร่างแรก 25 ก.ย. 2569 · **เขียนใหม่ 26 ก.ย. 2569 ตามคำตัดสินของเจ้าของ D90–D102 (POS รอบ 15) และคำถาม 3 ข้อของ ADR-0056 · แก้ตามรีวิวความปลอดภัยของสเปก (สเปก POS §13.8 R2-…)** · ใช้แทนเนื้อหาร่างของ ADR-0056 ที่ "เลื่อน" ไว้ · ที่มาฝั่ง POS: สเปก POS `04-สเปกการเชื่อม-POS-กับ-dayo.md` §4.10 ก้อน 3, §6.1, §6.2, §6.4, §6.8, §13.8 (สเปกกับร่างนี้ต้องตรงกันทุกข้อ — ขัดกันให้ถือสเปก POS แล้วแจ้ง architect ของ POS) · **ขยาย ADR-0035** (POS เป็นเครื่องมือเรื่องเงิน) · **แก้ ADR-0024 ข้อ 2** (กะมีเฉพาะที่แท็บเล็ต) · **แก้ ADR-0049 ข้อ 3** (ขั้น (ก0) `pos_excluded_orders` ยกเลิก — แทนด้วยบิลนอกแคตตาล็อก) · ใช้คู่กับ ADR-0050 (ยอดทุกแหล่งอยู่ใน `orders` เดียว · owner แก้บิล POS บนเว็บ) และ ADR-0055 (หน้าดูกำไร)
- บริบท: POS มีกะ ลิ้นชัก นับเงิน 9 ชนิด และ Z ที่แก้ไม่ได้อยู่แล้วในเครื่อง (แผน 3b) · สถาปัตยกรรม C1 ให้ตัวเลขเงินอยู่ฐานเดียว (D62) · ขายได้ทั้ง POS บอท เว็บ (ADR-0050) เงินสดจากบิลบอทอยู่ในลิ้นชักเดียวกัน ตอนออก Z แท็บเล็ตต้องดึงบิลเงินสดบอทมานับ (ต้องออนไลน์ — Q15) · นับเงินได้ตอนออฟไลน์ Z รอออนไลน์ กะถัดไปเปิดได้ (D68) · owner แก้บิล POS บนเว็บได้ (ADR-0050 · D85) แต่เงินในลิ้นชักคือเงินที่เก็บจริงตอนขาย · ร่างเดิมใช้ตาราง `pos_excluded_orders` เก็บรายได้ของบิลที่เข้าฐานไม่ได้ ซึ่งทำให้รายได้อยู่นอก `orders` และถือต้นทุนเป็น 0 (ADR-0056 คำถามข้อ 2) — เจ้าของเลือกให้เป็นบิลใน `orders` แทน (D91)

## ตัดสินใจ

1. **กะมีเฉพาะที่แท็บเล็ต** (D92): เปิด/ปิดกะ นับเงิน ใบปิดกะ ทำบนแท็บเล็ต POS เท่านั้น · **บอทไม่มีคำสั่งกะ** · เว็บอ่านอย่างเดียว (ข้อ 11) · แก้ ADR-0024 ข้อ 2 ตามข้อความในส่วน "สิ่งที่ dayo ต้องตัดสิน/เปลี่ยน" ข้อ 2
2. **เงินในลิ้นชักยึดเงินที่เก็บจริงตอนขาย** (D93): เงินที่ควรมีและการคิด Z ซ้ำใช้ยอดและวิธีชำระที่แท็บเล็ตเก็บจริง (`orders.pos_reported_amounts` แช่แข็ง) **ไม่ใช่** `total_amount`/วิธีชำระ/สถานะหลัง owner แก้บนเว็บ · การแก้บนเว็บแสดงเป็นบรรทัดแยก "เจ้าของแก้บิลหลังขาย" (ข้อ 9) ไม่เข้า Z ไม่ทำให้ `mismatch`
3. **ตาราง** (ทุกตาราง: `id` จากแท็บเล็ต · `shop_id` · `api_client_id` · `received_at timestamptz default now()` · RLS เปิดไม่มี policy · append-only ด้วย trigger raise ยกเว้นที่ระบุ · เงิน `numeric(10,2)` บาท · อยู่ในไฟล์สำรอง `backup_dump_table`):
   - `shifts`: `id` (= `shift_id`), `business_date`, `opened_by`, `opened_at`, `opening_float`, `quick_open`, `status` (`open` → `counted` เมื่อรับ `cash_count` → `closed` เมื่อรับ `shift_close` · แสดงผลเท่านั้น · เปลี่ยนไปข้างหน้าได้อย่างเดียว), `closed_by`, `closed_at` (ตั้งครั้งเดียวจาก null) · **ไม่มี unique "กะ `open` ละหนึ่งต่อ key"** (ข้อ 8)
   - `cash_movements`: `id`, `shift_id`, `kind` (`PAID_IN`/`PAID_OUT`/`DROP`/`VOID_REFUND`), `amount > 0`, `pos_order_id` (มีเฉพาะ `VOID_REFUND` — check), `reason`, `created_by`, `created_at` (เวลาเครื่อง) · **`VOID_REFUND` เป็นแหล่งความจริงเดียวของเงินคืนจากบิลที่ยกเลิก** (`order_void` ไม่มีข้อมูลคืนเงิน)
   - `cash_counts`: `id`, `shift_id` (**unique** — นับปิดกะกะละครั้ง), `lines jsonb [{denomination, count}]` (1000/500/100/50/20/10/5/2/1 บาท), `counted`, `counted_by`, `counted_at` (เวลาเครื่อง) · ไม่มี expected/variance (นับได้ตอนออฟไลน์แต่เงินที่ควรมีต้องรอบิลบอท)
   - `z_reports`: `shift_id` (unique), `z_no`, `hash`, `prev_hash`, `chain_warning`, `snapshot jsonb` (= `z_report` ที่ส่งมาตรงตัว), `expected`, `counted`, `variance` (**ระบบคิดจาก `snapshot.cash`** · ติดลบ = ขาด), `variance_reason`, `recompute_status` (`waiting_bills` = รอแถวมาครบทั้งบิลและเงินเข้า-ออก / `matched` / `mismatch`), `z_mismatch bool`, `recompute_detail jsonb`, `missing_pos_order_ids uuid[]`, `missing_movement_ids uuid[]`, `waiting_since`, `recomputed_at`, `variance_alert` (เกณฑ์จาก Z — D102), `chain_break bool`, `recompute_notes jsonb` (ข้อสังเกตเช่น "Z ขาดช่วง"), `missing_void_order_ids uuid[]`, `alerted_variance_at`, `alerted_mismatch_at` · **unique `(api_client_id, z_no)`** · trigger ยอมให้แก้เฉพาะกลุ่ม `recompute_*`/`z_mismatch`/`missing_*`/`waiting_since`/`recomputed_at`/`chain_break`/`alerted_*` โดยฟังก์ชันคิดซ้ำ/แจ้งเตือน · `shifts` มี `data_conflict bool` (ตั้งได้เฉพาะฟังก์ชันตรวจชน)
   - `pos_push_rejections` (ใหม่): `shop_id`, `api_client_id`, `pos_order_id`, `reason`, `first_at` · **หนึ่งแถวต่อ `(api_client_id, pos_order_id, reason)`** (เก็บทุกเหตุผลที่เคยเห็น) · ดัชนี `(shop_id, pos_order_id)` · แทรกเมื่อแถว `order` ได้ `rejected` (นอก savepoint ของแถว ไม่ถูกย้อน · ชนแล้วข้าม) · ใช้ตัดสิน `order_off_catalog` (ข้อ 5)
   - `shop_settings.off_catalog_max_total numeric(10,2)` (ใหม่): เพดานยอดต่อบิลนอกแคตตาล็อก **ค่าเริ่มต้น ฿3,000 (รอเจ้าของยืนยัน Q72)** · owner แก้บนเว็บพร้อม `audit_log`
   - `orders`: **unique index `(api_client_id, pos_order_id)` เปลี่ยนเป็น `(shop_id, pos_order_id)`** (migration ใหม่ทับของที่ ship แล้ว — ส่วน "สิ่งที่ dayo ต้องเปลี่ยน" ข้อ 7) · เพิ่ม: `off_catalog boolean not null default false` · `off_catalog_lines jsonb` · `cost_total` เป็น null ได้ **เฉพาะ** บิลนอกแคตตาล็อก (check `off_catalog = (cost_total is null)`) · **บิล POS ใหม่ทุกใบใส่คีย์ `payment`** (รหัสวิธีชำระตอนขาย) ใน `pos_reported_amounts` ตอนแทรก (แช่แข็งด้วย `orders_pos_frozen` เดิม) · **`orders_pos_frozen` เพิ่ม `pos_shift_id` และ `external_ref`** ของบิล POS (ตอนนี้ไม่อยู่ใน `0051_multi_source_sales.sql:104-108` — Z จับคู่บิลด้วยค่าทั้งสอง)
   - `shop_settings.block3_live_from date`: **ตั้งอัตโนมัติ** = `business_date` ของ `shift_open` แรกที่ `accepted` ของร้าน **เฉพาะเมื่อ `business_date` ≥ วันนี้ − 1** ตั้งครั้งเดียวจาก null ในธุรกรรมของแถวนั้น · เจ้าของไม่ต้องกรอก (D100) · owner แก้บนเว็บได้ **เฉพาะเป็นวันที่เก่ากว่าเดิม** พร้อม `audit_log` (ห้ามเลื่อนไปข้างหน้าหรือล้าง — เป็นพื้นล่างของบิลนอกแคตตาล็อก)
   - `api_clients` scope เพิ่ม `shift:write` (check `api_clients_scopes_check` + `dayo_check_api_scopes` + `apps/web/src/lib/apiScopes.ts`)
   - `orders.pos_shift_id` ไม่มี FK ต่อไป — ผูกทีหลังได้
4. **ชนิดใหม่ของ `POST /v1/pos/push`** (ซอง คำตัดสิน กันซ้ำ ตารางแผนที่ error ตาม ADR-0049 · รูปฟิลด์ทุกตัวตามสเปก POS §4.10 ก้อน 3 — ล็อก):

   | ชนิด | key | ช่อง id | scope | ต้องมีแล้ว (ไม่งั้น `deferred PARENT_PENDING`) |
   |---|---|---|---|---|
   | `shift_open` | `shift_open:<shift_id>` | `shift_id` | `shift:write` | — |
   | `cash_movement` | `cash_movement:<movement_id>` | `movement_id` | `shift:write` | กะ |
   | `cash_count` | `cash_count:<count_id>` | `count_id` | `shift:write` | กะ |
   | `shift_close` | `shift_close:<shift_id>` | `shift_id` | `shift:write` | การนับของกะ |
   | `order_off_catalog` | `order_off_catalog:<pos_order_id>` | `pos_order_id` | `orders:write` | — |

   - **`api_pos_push` ต้องขยาย**: ช่อง id ตามชนิด (ตอนนี้ `dayo_pos_push_row` บังคับ `pos_order_id` ทุกชนิด — `0052_pos_push.sql:596-600`) · หลังขั้น `orders:write` เพิ่ม "ชนิดกะแต่ key ไม่มี `shift:write` → `rejected FORBIDDEN`" (403 ทั้งคำขอยังใช้กับ `orders:write` เท่านั้น) · `DY404` ของ `cash_movement`/`cash_count`/`shift_close` → `deferred PARENT_PENDING` · **ทุกการหา `shifts` `cash_counts` `cash_movements` `z_reports` ใช้ `(shop_id, api_client_id, id)`** · แถวแม่ของ key อื่น = `FORBIDDEN` `rule:` · id เดิมมีแล้ว (key เดียวกัน) หลังคีย์หมดอายุ = `duplicate` · **ตัวแปลง `23505`**: `order`/`order_off_catalog` หาใหม่ด้วย `(shop_id, pos_order_id)` — บิลเดียวกัน key เดียวกันชนิดเดียวกัน = `duplicate` · `order` ชนบิลนอกแคตตาล็อก → `CONFLICT` `off_catalog_exists:` · `order_off_catalog` ชนบิลปกติ → `CONFLICT` `exists:` · ชนบิลของ key อื่น → `CONFLICT` ตามชนิดบิล · ชนิดกะหาใหม่ด้วย `(api_client_id, id)`: เจอ = `duplicate` ไม่เจอ = `CONFLICT` (`counted:` เมื่อชนการนับของกะ) · **เพดานรายการ** `pos_bills` ≤ 2000 · `bot_bills` ≤ 500 · `movement_ids` ≤ 500 (เกิน = `INVALID`) · `dayo_pos_supported()` เพิ่ม 5 ชนิดและรายชื่อฟิลด์ **รวม `lines.denomination` `lines.count` ของ `cash_count`** (ตัวตรวจฟิลด์ตรวจ `lines.*` ของทุกชนิด — `0052:587-591`) · คีย์ย่อยที่ไม่รู้จักใน `z_report`/`totals` = `rejected INVALID`
   - **เวลา**: ช่องเวลาหลักของแถว (`opened_at`/`created_at`/`counted_at`/`closed_at`) เกินเวลาเซิร์ฟเวอร์ + 5 นาที = `deferred CLOCK_AHEAD` · เก่ากว่า − 60 วัน = `rejected INVALID` · `shift_open.business_date` = วันไทยของ `opened_at` · `cash_movement.created_at` ≥ `opened_at` และ ≤ `counted_at` เมื่อมีการนับแล้ว · `counted_at` ≥ `opened_at` · `closed_at` ≥ `counted_at`
   - **พนักงาน**: `*_by` เป็น active หรือ removed (`UNKNOWN_STAFF`) · `shift_close.closed_by` และ `order_off_catalog.closed_by` ต้องเป็น owner **active ณ `closed_at`** · `shift_open.quick_open = true` ⇒ `opened_by` เป็น owner active ณ `opened_at` (ไม่ใช่ = `FORBIDDEN` `role:`) · เป็นการระบุตัว ไม่ใช่สิทธิ์ (ADR-0040) — ด่านจริงคือ PIN owner บนแท็บเล็ต
   - **เงิน**: บาท ≥ 0 ทุกช่อง (แท็บเล็ตแปลงจากสตางค์ที่ขอบ) · **ไม่มีเงินติดลบในคำขอ** — `expected`/`variance` ระบบคิดเอง: `expected = opening_float + pos_cash_sales − void_refunds + paid_in − paid_out − drops − drawer_expenses + bot_cash` · `variance = counted − expected` (`expected` ติดลบได้เมื่อจ่ายออกเกินเงินในลิ้นชัก)
   - `cash_count`: 9 แถว ชนิดละหนึ่ง · `counted` = Σ `denomination × count` (ไม่ตรง = `INVALID`) · กะมีการนับอื่นแล้ว = `CONFLICT` `counted:` · `counted_at` = เวลากด "นับเสร็จ" · หลังเวลานี้กะไม่รับบิล/เงินเข้า-ออก
   - `shift_close.z_report` = `{z_no, hash, prev_hash, chain_warning, variance_alert, cash:{opening_float, pos_cash_sales, void_refunds, paid_in, paid_out, drops, drawer_expenses, bot_cash}, counted, bot_window:{after, until}, movement_ids:[uuid], bot_bills:[{order_no, version, total}], pos_bills:[{pos_order_id, receipt_no, payment, total, sold_at, voided_at}]}` · `variance_alert` = เกณฑ์ขอเหตุผลของแท็บเล็ต (`cash.variance_alert_satang` ค่าเริ่มต้น ฿20 · บาท ≥ 0 — D102) · **ลำดับ `z_no` และโซ่** ("Z ใบก่อน" = Z ของ key เดียวกันที่ `z_no` มากสุดที่น้อยกว่าใบนี้): (0) `z_no` > สูงสุดของ key + 50 = `INVALID` + แจ้งแบบข้อมูลกะชนกัน (key ที่ยังไม่มี Z ไม่มีเพดาน) (1) `z_no` ซ้ำ = `CONFLICT` `z_no_taken:` + ถือเป็นข้อมูลกะชนกัน · **ตรวจก่อนข้อ 5 เสมอ** (2) key ไม่มี Z ในฐานเลย `mismatch`) (4) ใบก่อนขาดช่วงหรือไม่มี (ถูกปิดไว้ในเครื่อง/ถูกปฏิเสธแล้วยังไม่ส่งใหม่) = ข้อสังเกต "Z ขาดช่วง / Z ก่อนหน้ายังไม่มี" ใน `recompute_notes` ไม่ใช่ `chain_break` · `after` เทียบกับ การนับของกะ · `until` = `counted_at` · Σ `bot_bills.total` = `cash.bot_cash` (ไม่ตรง = `INVALID`) · `drawer_expenses` = 0 จนกว่าจะมี ADR-0057 · `movement_ids` = id เงินเข้า-ออกทุกแถวของกะที่ 10. **แจ้งเตือน Discord `#dayo-ระบบ`** (D98 · D102 · ADR-0044) — **ข้อความไม่มียอดเงิน** (ค่าเริ่มต้น รอเจ้าของยืนยัน Q73) ไม่มีชื่อพนักงาน/เหตุผลอิสระ/id นอกจากลิงก์หน้ากะ: รับ `shift_close` แล้ว **|variance| ≥ `z_report.variance_alert`** (กติกาเดียวกับที่แท็บเล็ตขอเหตุผล — D102) → "กะ 25 ก.ย. เงินไม่ตรงเกินเกณฑ์ — ดูที่ /shifts/<id>" ครั้งเดียวต่อ Z · `recompute_status` เปลี่ยนเข้า `mismatch` → แจ้งครั้งเดียวต่อการเปลี่ยน · ข้อมูลกะชนกัน → 🔴 · บิลนอกแคตตาล็อกที่รับ → 🟡 นับใบ · `scope:` → 🟡 วันละครั้งต่อ key · "กะซ้อนกัน" และ key มี > 3 กะต่อวัน → 🟡 · **`waiting_bills` ไม่แจ้ง** (D98 · ข้อเสนอแจ้งเมื่อรอ > 48 ชม. ขัด D98 รอเจ้าของ Q74) · `duplicate` ไม่แจ้งซ้ำ
11. **เว็บ** (Q20 · D99) — **สิทธิ์**: RPC `dashboard_shifts` และ RPC หน้ารายละเอียดกะรับ `p_staff_id` และ raise `DY403` ถ้าไม่ใช่ owner · `today_mini` คืนแค่เปิด/ปิด · ไม่มี API ใดคืน `z_reports` หรือส่วนต่าง · Export ที่มีข้อมูลกะเฉพาะ owner · แดชบอร์ด owner 1 บรรทัดต่อกะ "กะ <วันที่> · เปิด <เวลา> <ชื่อ> · ปิด <เวลา> · เงินขาด/เกิน ฿<n>" + ป้าย "ไม่ตรง"/"รอบิล N ชม."/"โซ่ Z ขาด"/"Z ขาดช่วง"/"ข้อมูลชนกัน" + "เจ้าของแก้ N บิล" + ป้ายนับบิลนอกแคตตาล็อก · หน้ากะแสดงเกณฑ์ขอเหตุผลที่ใช้ (`variance_alert`) และติดป้ายเมื่อต่างจาก Z ใบก่อนของ key · **หน้ารายละเอียดกะ owner เท่านั้น อ่านอย่างเดียว**: ธนบัตรแต่ละชนิด · เงินเข้า-ออก · องค์ประกอบเงินที่ควรมี · บิลบอทที่นับ · บิล POS ของกะ · ส่วนต่าง + เหตุผล · สถานะคิดซ้ำ + บิลที่ยังไม่มา · บรรทัดข้อ 9 · manager/staff เห็นใน `today_mini` แค่สถานะกะ (เปิด/ปิด) · รายการเสริม: "บิลบอทนอกใบปิดกะ"/"เปลี่ยนหลังนับ"/"เปลี่ยนจากเงินสดก่อนนับ" (เฉพาะ `sale_date ≥ block3_live_from` · Z แช่แข็งไม่เปลี่ยน) · "บิลที่ `pos_shift_id` ยังไม่มีกะ" · "กะซ้อนกัน"
12. **กะก่อนก้อนนี้**: แถวกะ/เงินสดทุกชนิดของกะที่เปิดก่อนก้อนนี้ใช้งานจริงอยู่ในแท็บเล็ตเท่านั้น (`local_only`) ไม่ถูกส่งมาเลย · บิลของกะเหล่านั้นส่ง `shift_id: null` เสมอ · บิลของกะเหล่านั้นที่ถูกปฏิเสธหลังก้อนนี้ใช้งาน ปิดเป็นบิลนอกแคตตาล็อกได้ตามปกติ (`shift_id: null`) · บิลที่แท็บเล็ตปิดเป็น "นอกระบบกลาง" ก่อนก้อนนี้ (ช่วงทดสอบ — แท็บเล็ตยังไม่ขายจริงก่อนก้อนนี้ตาม D94) ไม่ถูกส่งมา
13. บิล POS ของวันที่ปิดแล้ว: owner แก้/ยกเลิกบนเว็บได้ (ADR-0050) · บนแท็บเล็ตแก้ไม่ได้ ส่วนต่างที่พบภายหลังแก้ด้วย `cash_movement` `PAID_IN`/`PAID_OUT` ในกะปัจจุบันพร้อมเหตุผลอ้างเลขใบเสร็จ หรือค่าใช้จ่าย (ADR-0057) · **ห้ามใช้ `PAID_IN`/`PAID_OUT` "ชดเชย" บิลนอกแคตตาล็อก** (เงินสดของบิลอยู่ในกะของมันแล้ว)

- ทางเลือกที่ไม่เลือก: ตาราง `pos_excluded_orders` แยก (รายได้อยู่นอก `orders` · ต้นทุน 0 ทำ GP สูงเกินจริง — ADR-0056 คำถามข้อ 2 · D91) · ต้นทุนบิลนอกแคตตาล็อก = 0 · เก็บกะไว้แค่ในแท็บเล็ต (ขัด C1) · ให้บอทมีคำสั่งกะ (D92) · Z ยึดยอดหลังแก้บนเว็บ (เงินในลิ้นชักไม่ได้เปลี่ยน — D93) · ให้ระบบคิด expected แล้วส่งกลับ (แท็บเล็ตต้องออนไลน์ทุกครั้งที่ดูลิ้นชัก) · เลือกบิลบอทด้วย `sale_date` ทั้งวัน (นับซ้ำเมื่อวันเดียวมีหลายกะ) · ใช้ `closed_at` เป็นเวลาตัด · FK `orders.pos_shift_id` · เงินคืนทั้งใน `order_void` และ `VOID_REFUND` (หักซ้ำ) · unique "กะ open ละหนึ่ง" ในฐาน (ขัดกติกาตัดสินด้วยเวลา) · ช่องคิวต่อกะ (กะใหม่แซงการนับของกะก่อน) · ส่ง `expected`/`variance` ที่ติดลบข้ามขอบสัญญา · แจ้งเตือนตอน `waiting_bills` (D98)
- ผลที่ตามมา: migration ใหม่ (5 ตาราง — `shifts` `cash_movements` `cash_counts` `z_reports` `pos_push_rejections` + trigger · คอลัมน์ `orders` + check + `pos_reported_amounts.payment` · `shop_settings.block3_live_from` · scope `shift:write` · ขยาย `api_pos_push`/`dayo_pos_push_row`/`dayo_pos_map_error`/`dayo_pos_supported` · ชนิดใหม่ 5 ชนิด · `api_shift_cash` · ฟังก์ชันคิด Z ซ้ำ · `create_order` (คีย์ `payment`) · `cancel_order` (บิลไม่มีรายการ) · `dayo_summary_range`/`dashboard_*`/สรุปประจำวัน/Export/`profit_view_dashboard` (บิลไม่รู้ต้นทุน) · `dashboard_shifts` + หน้ารายละเอียดกะ · `backup_dump_table`) · route `app/api/v1/pos/shift-cash/route.ts` · แจ้งเตือน Discord · DATA-CONTRACT · API.md · GLOSSARY ("กะ", "ใบปิดกะ", "เงินสดที่ควรมี", "บิลนอกแคตตาล็อก", "เจ้าของแก้บิลหลังขาย") · **dayo deploy ก่อน POS เสมอ** (ADR-0049 ข้อ 7) · เทสต์: ตามเกณฑ์ก้อน 3 ในสเปก POS §9 (ทุกข้อ) · `supported_kinds`/`supported_fields` ตรงกับที่ RPC รับจริง · security-reviewer ตรวจ · **ขอบเขตของ key ที่หลุดต่อบิลนอกแคตตาล็อก**: การต้องมีแถวใน `pos_push_rejections` แค่ผูกบิลกับแถว `order` ที่ถูกส่งมาจริง **ไม่กัน key ที่หลุด** (คนถือ key ส่ง `order` ที่ตั้งใจให้ถูกปฏิเสธก่อนได้) · ด่านจริงคือ `sold_at` ≥ `block3_live_from` · ยอด ≤ `off_catalog_max_total` ต่อบิล · ทุกใบแจ้ง Discord + ป้ายแดชบอร์ด — ความเสียหายจำกัดที่เพดานต่อบิลและเห็นทันที

## สิ่งที่ dayo ต้องตัดสิน/เปลี่ยน (ขอจากทีม POS)

1. **รับ ADR-0056 ตามร่างนี้** (D91–D93 · D97–D100) — เปลี่ยนสถานะจาก "เลื่อน" เป็น "ยอมรับ" หลังเจ้าของอนุมัติใน session ของ dayo
2. **แก้ ADR-0024 ข้อ 2** เป็น (เสนอ): "พนักงานทุกคนใช้ LINE ของตัวเอง → ผู้บันทึกในบอท = แถว `staff` ของคนพิมพ์ · บอทไม่มีคำสั่งกะ/ใครกำลังใช้ · **เครื่องใช้ร่วมมีเครื่องเดียวคือแท็บเล็ต POS ซึ่งล็อกอินด้วย PIN รายคน (ADR-0050 ข้อ 2) · กะ นับเงิน และใบปิดกะมีเฉพาะที่แท็บเล็ต (ADR-0056)**"
3. **ธง "บิลนอกแคตตาล็อก" บน `orders`** (`off_catalog` + `off_catalog_lines` + `cost_total` null ได้เฉพาะบิลนี้) และรายงานทุกตัวที่คิดต้นทุน/กำไรต้องรองรับ (ข้อ 5) · แก้ ADR-0049 ข้อ 3 ขั้น (ก0) เป็นกติกาข้อ 5 · ADR-0050 ข้อ 1 ("ยอดทุกแหล่งอยู่ใน `orders` เดียว") ยังจริงทุกคำ
4. **ยกเลิกการเลื่อน ADR-0051 (สำรองอัตโนมัติทุกคืนไป OneDrive) แล้วทำฝั่ง dayo** (D95) · POS จะไม่เปิดใช้แท็บเล็ตขายจริงจนกว่าสำรองอัตโนมัติทำงานจริง (D86) และเปิดใช้หลังก้อน 3 (D94) · POS มีแผนเปิดใช้งานที่ตรวจการสำรองนี้
5. ขยาย `api_pos_push` ให้ช่อง id ตามชนิด + scope ต่อแถว + คำนำหน้า `detail` (ข้อ 4) โดยไม่เปลี่ยนคำตัดสินของ `order`/`order_void` (เปลี่ยนแค่ขึ้นต้น `detail` ด้วยคำนำหน้า)
6. **แช่แข็ง `pos_shift_id` และ `external_ref` ของบิล POS** ใน `orders_pos_frozen` (ตอนนี้แช่แข็งแค่ยอด/`pos_order_id`/`sold_at`/`catalog_version` — `0051_multi_source_sales.sql:104-108`)

7. **เปลี่ยน unique index ของ `orders`** จาก `orders_api_client_pos_order_key (api_client_id, pos_order_id)` เป็น `(shop_id, pos_order_id)` where `pos_order_id is not null` — ต้องเป็น **migration ใหม่ทับ index ที่ ship แล้ว** (สร้างใน `0051_multi_source_sales.sql:38` ใช้ใน `0052`) · ตรวจข้อมูลเดิมว่าไม่มีคู่ซ้ำก่อนสร้าง · ตัวแปลง `23505` หาใหม่ด้วย `(shop_id, pos_order_id)` · กัน `order`/`order_off_catalog` ที่ส่งซ้ำด้วย key ใหม่หลังเปลี่ยนกุญแจเครื่องไม่ให้นับรายได้ซ้ำ
8. **E1 `client` เพิ่ม `last_z_no` (int หรือ null) และ `last_z_hash` (hex 64 หรือ null)** = `z_no`/`hash` ของ Z ที่เลขสูงสุดของ key นี้ · แท็บเล็ตที่ติดตั้งใหม่ด้วย key เดิมโดยไม่กู้ไฟล์สำรองต่อเลข Z และโซ่จากค่านี้ (แบบ `last_receipt_no`) — ไม่งั้นเริ่ม `z_no` 1 ใหม่แล้วได้ `z_no_taken:` + 🔴 ปลอมตลอดไป · `supported_fields` ไม่เกี่ยว (เป็นฟิลด์คำตอบ)
9. **ตาราง `pos_push_rejections`** + ตรวจสิทธิ์ปิดบิลนอกแคตตาล็อกฝั่งเซิร์ฟเวอร์ + ค่าตั้ง `off_catalog_max_total` (ข้อ 3, 5)
10. **สิทธิ์หน้ากะ**: `dashboard_shifts` และ RPC หน้ารายละเอียดกะตรวจ owner เอง (`p_staff_id` → `DY403`) · Export ข้อมูลกะเฉพาะ owner (ข้อ 11)

หมายเหตุ: ขั้นตอนนับเงินฝั่งแท็บเล็ตตอนออฟไลน์ล็อกแล้วตาม D101 (สเปก POS §6.8) · ไม่กระทบรูปแถวในร่างนี้ · รอเจ้าของยืนยัน: **Q72** เพดานต่อบิลนอกแคตตาล็อก ฿3,000 · **Q73** ข้อความ Discord ไม่มียอดเงิน · **Q74** แจ้งเมื่อ `waiting_bills` เกิน 48 ชม. (ขัด D98 — ยังไม่ทำ)

## คำถามเปิดสำหรับ dayo (พร้อมคำแนะนำ)

- **ค1 ที่เก็บข้อมูลของบิลนอกแคตตาล็อก**: ชื่อคอลัมน์ และจะเก็บ `closed_by`/`closed_at`/`reason`/`original_reason` เป็นคอลัมน์หรือใน `audit_log` — **แนะนำ**: ใช้ชื่อตามร่าง · เก็บใน `audit_log` action `order_off_catalog` (แช่แข็งอยู่แล้ว) และแสดงผ่าน `get_order_history` · ถ้าเปลี่ยนชื่อ แจ้ง POS (ไม่กระทบสัญญา API เพราะไม่ส่งออก)
- **ค2 owner แก้บิลนอกแคตตาล็อกบนเว็บได้ไหม**: `update_order` คิดราคาใหม่จากแคตตาล็อก ซึ่งบิลนี้ไม่มีรายการแคตตาล็อก — **แนะนำ**: **ยกเลิกได้** (พร้อมเหตุผล ตาม ADR-0050) **แต่แก้รายการไม่ได้** (`DY422` ข้อความ "บิลนอกแคตตาล็อกแก้ไม่ได้ ยกเลิกแล้วบันทึกใหม่") · การยกเลิกบนเว็บขึ้นในบรรทัด "เจ้าของแก้บิลหลังขาย" ตามข้อ 9
- **ค3 ระดับข้อความ Discord**: **แนะนำ** ขาด/เกิน ≥ เกณฑ์ = 🟡 WARNING · `mismatch` = 🔴 ERROR (ตัวเลขแท็บเล็ตกับฐานไม่ตรง = สัญญาณบั๊ก) · ข้อมูลกะชนกัน = 🔴 ERROR + `@here` (อาจมีคนใช้กุญแจเครื่อง) · อื่น ๆ 🟡 ไม่ `@here`
- **ค4 กลไกส่งแจ้งเตือนจาก RPC**: `mismatch` อาจเกิดตอนรับแถว `order` ของวันหลัง ไม่ใช่แค่ตอน `shift_close` — **แนะนำ**: แบบเดียวกับ `SERVER_ERROR` (RPC ใส่เครื่องหมายในข้อความคำตอบ Route Handler หาข้อความแล้ว `console.warn`/`console.error` → Discord) และเก็บเวลาที่แจ้งแล้วใน `z_reports` กันแจ้งซ้ำ
- **ค5 path หน้ารายละเอียดกะ**: **แนะนำ** `/shifts/[shift_id]` ใต้ layout owner (`requireRole('owner')`) · ลิงก์จากบรรทัดกะบนแดชบอร์ด
