# ADR-P1 (เลขถัดไปตอนรับเข้า) — เปิด `/api/v1` ให้ POS · พนักงานและบทบาทใน API · ฉบับแคตตาล็อก

- สถานะ: **เสนอ** · 25 ก.ย. 2569 (ร่างจากทีม POS — สเปก POS `docs/design/04-สเปกการเชื่อม-POS-กับ-dayo.md` §4.1–4.4, §4.9, §5.2, §7 · แก้ตามรีวิวรอบ 1 ข้อ 3, 4, 12, 16) · **ขยาย ADR-0035** (ข้อ 2 รายการ endpoint) และ **ADR-0042** (เงื่อนไขเปิดใช้)
- บริบท: เจ้าของเลือกสถาปัตยกรรม C1 — ฐานข้อมูลเซิร์ฟเวอร์เดียวคือ Supabase นี้ แท็บเล็ต POS เก็บสำเนาในเครื่องเพื่อขายตอนออฟไลน์ แล้วส่งบิลเข้ามาทาง `/api/v1` · แท็บเล็ตต้องคิดราคาให้ได้ **เท่ากับ `quote_order` ทุกสตางค์** โดยใช้ตัวคิดราคาของ `packages/shared` (สำเนาที่ปักรุ่น) · แต่ `GET /v1/catalog` เดิมไม่มีสูตร (ตัดสินนมโอ๊ต/เกรดผง) ไม่มีกติกาช่องทาง (บวก % / บวกบาท / ปัด / ค่าธรรมเนียม) ไม่มีค่าเริ่มต้นร้าน (ADR-0046) และ `etag` ครอบแค่เมนู · POS ต้องมีรายชื่อพนักงาน+บทบาทเพื่อล็อกอินด้วย PIN ในเครื่อง (PIN ไม่ออกจากเครื่อง) · แท็บเล็ตเป็น PWA ในเบราว์เซอร์คนละ origin จึงต้องมี CORS ซึ่งยังไม่มี · ADR-0042 ปิด API ไว้จนกว่าจะเชื่อม POS จริง
- ตัดสินใจ:
  1. **ฉบับแคตตาล็อก**: ตาราง `catalog_versions (shop_id pk, version bigint default 1, changed_at)` · trigger ระดับแถวเพิ่มฉบับเมื่อแถวเปลี่ยนใน `menu_items` `menu_variants` `recipe_lines` `bases` `base_lines` `menu_options` `sales_channels` `payment_methods` `promotions` `shop_settings` · `staff` เฉพาะ `display_name`/`role`/`status` · `ingredients` เฉพาะ `code`/`name`/`use_unit`/`is_active` (รับเข้าที่แก้ `buy_price` ไม่เพิ่มฉบับ) · เลขเพิ่มขึ้นเสมอ ผู้ใช้เทียบแค่เท่ากัน/ไม่เท่ากัน
  2. **`GET /v1/pos/catalog?known_version=`** (scope `catalog:read` + `staff:read`) · RPC `api_pos_catalog(p_shop_id, p_api_client_id, p_known_version)` · ฉบับตรงกัน → `{changed:false, catalog_version, server_time}` · ไม่ตรง → `{changed:true, catalog_version, server_time, client:{name, last_receipt_no}, staff:[…], catalog:{…}}` · `catalog` = ผลของ `dayo_impl_get_full_catalog` (รูป `OrderCatalog` ของ shared) **ตัด `costPerUseUnit` ออก** + เพิ่ม `categoryLabel`, `menuSortOrder` ต่อตัวแปร · `staff` = `{id, display_name, role, active}` ของสถานะ active และ removed ไม่มี pending ไม่มี `line_user_id` · `last_receipt_no` = `external_ref` ล่าสุดของ client นี้ · ทั้งสองแบบของคำตอบมี `pricing: {commit, files_sha256}` (commit ของ build ที่ deploy อยู่ = เวอร์ชันระบบ ADR-0045 · sha256 ของไฟล์ตัวคิดราคาใน `packages/shared/src/` คำนวณตอน build) และ `supported_kinds` (ชนิดแถวของ `POST /v1/pos/push` ที่รุ่นนี้รับ) + `supported_fields` (รายชื่อฟิลด์ของ `data` ต่อชนิด ฟิลด์ซ้อนเขียนแบบจุด เช่น `lines.milk` — แท็บเล็ตเก็บแถวที่ใช้ฟิลด์นอกรายการไว้รอ ไม่ส่ง) · กติกาปล่อยรุ่น: **dayo deploy ก่อน POS เสมอ** · ตั้งแต่ก้อนค่าใช้จ่าย (P4) มี `expense_categories` ระดับเดียวกับ `staff` · รูป JSON ตามสเปก POS §4.4 (ล็อก)
  3. scope ใหม่ `staff:read` เพิ่มในรายการที่ `create_api_client`/`save_api_client` ยอมรับ
  4. **CORS** ที่จุดเดียวใน `apps/web/src/lib/api/response.ts` (`apiHandler` — ที่เดียวกับสวิตช์ 404 ของ `API_V1_ENABLED` · ค่า env อ่านผ่าน `lib/platform.ts` ตาม ADR-0033): origin ที่อนุญาต = env ใหม่ `POS_ORIGINS` (คั่นจุลภาค · ไม่ตั้ง = ไม่มี CORS) · **ทุกคำตอบใต้ `/api/v1/*` รวม error ทุกชนิด** (404 จากสวิตช์ · 401 · 403 · 422 · 429 · 5xx) มี `Access-Control-Allow-Origin: <origin ที่ตรง>` + `Vary: Origin` + `Access-Control-Expose-Headers: Retry-After` · **`OPTIONS` ตอบ 204 เสมอ** แม้ API ปิด ไม่แตะฐานข้อมูล พร้อม `Allow-Headers: Authorization, Content-Type` · `Allow-Methods: GET, POST, OPTIONS` · `Max-Age: 7200` · เหตุผล: ไม่มีหัว CORS เบราว์เซอร์จะซ่อนสถานะ 401/404/429 จาก JS (เห็นเป็นเน็ตหลุด) และอ่าน `Retry-After` ไม่ได้
  5. หน้า `/settings/api-clients`: ตอนสร้างคีย์แสดง **QR ของคีย์** ข้างข้อความ (สร้างในเบราว์เซอร์ ไม่ส่งคีย์ไปที่อื่น) ให้แท็บเล็ตสแกน · แสดงครั้งเดียวเหมือนเดิม
  6. **parity กับ POS**: เพิ่มเคสในสเปก POS §5.3 (1–15) ลงเทสต์ shared = SQL ที่มีอยู่ · สคริปต์ `scripts/export-pos-parity.ts` **รันบน commit ที่ deploy อยู่จริง** ดึง catalog ด้วย **`api_pos_catalog` จริง** (ไม่ประกอบเอง) รันเคสกับ `quote_order` บน Supabase local แล้วเขียน `pos-parity.json` `{dayo_commit, pricing_files_sha256, catalog, cases:[{draft, expected}]}` ให้เจ้าของส่งต่อทีม POS ทุกครั้งที่ `files_sha256` เปลี่ยน
  7. **เปิดใช้จริง** (ขยาย ADR-0042): ตั้ง `API_V1_ENABLED=1` ใน production ได้เมื่อ (ก) ก้อนงาน POS 2 ผ่านเทสต์เชื่อมจริงกับ Supabase local ของ repo นี้ (ข) ตั้ง `POS_ORIGINS` แล้ว (ค) สร้างคีย์แท็บเล็ตแล้ว · endpoint เดิมทั้งหมดคงเดิม
- ทางเลือกที่ไม่เลือก: ขยาย `GET /v1/catalog` เดิม (เปลี่ยนรูปคำตอบที่เอกสารให้คนอื่นแล้ว) · ใช้ `etag` จากเวลาแก้ล่าสุด (ครอบไม่ครบทุกตาราง และเวลาชนกันได้) · ส่งต้นทุนให้แท็บเล็ต (ขัด ADR-0035 ข้อ 3) · endpoint พนักงานแยก (เพิ่มคำขอ และต้องคุมสองฉบับ)
- ผลที่ตามมา: migration ใหม่ (`catalog_versions` + trigger + `api_pos_catalog` + scope) · `apps/web/src/app/api/v1/pos/catalog/route.ts` · `lib/api/response.ts` (CORS · ค่า `POS_ORIGINS` อ่านผ่าน `lib/platform.ts`) · `.env.example` (`POS_ORIGINS`) · `settings/api-clients` (QR) · `scripts/export-pos-parity.ts` · DATA-CONTRACT §2.2/§3/§8 · API.md · SETUP/OPERATIONS (ขั้นเปิด API) · เทสต์: แก้ราคา → ฉบับเพิ่ม · รับเข้าแก้ `buy_price` → ฉบับไม่เพิ่ม · `known_version` ตรง → ไม่มี `catalog` · คำตอบไม่มี `costPerUseUnit`/`line_user_id` · preflight จาก origin ที่ไม่อนุญาต = ไม่มีหัว CORS · 401/404 (API ปิด)/429/5xx จาก origin ที่อนุญาต มีหัว CORS + `Vary: Origin` + `Expose-Headers: Retry-After` · `OPTIONS` = 204 แม้ API ปิด · คำตอบมี `pricing` `supported_kinds` `supported_fields` ทั้งสองแบบ · ขนาดคำตอบและ CPU ของ route วัดแล้วบันทึกไว้ (ถ้า parse+stringify เกิน 5 ms ให้ส่งต่อข้อความดิบ)
