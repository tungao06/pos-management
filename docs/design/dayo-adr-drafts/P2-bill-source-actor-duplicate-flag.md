# ADR-P2 (เลขถัดไปตอนรับเข้า) — บิลบอกแหล่งและผู้บันทึก · บิล POS อ่านอย่างเดียวบนเว็บ · ธงบิลน่าจะซ้ำ · ส่งบิลจาก POS แบบคำตัดสินรายแถว

- สถานะ: **เสนอ** · 25 ก.ย. 2569 (ร่างจากทีม POS — สเปก POS `docs/design/04-สเปกการเชื่อม-POS-กับ-dayo.md` §4.5–4.9 · เจ้าของตัดสิน Q51, Q52, Q53 (D75–D77) · แก้ตามรีวิวรอบ 1 ข้อ 1, 2, 4, 6, 8, 9, 10, 12, 13, 18, 19 และรีวิวรอบ 2 ข้อ N2, N3, N4, N5) · **แก้ ADR-0040 ข้อ 2** (วันยกเลิกของบิล POS) · **แก้ ADR-0035 ข้อ 5** และข้อความสถานะ **ADR-0006** (บอทไม่ใช่ "ทางสำรอง") · ขยาย ADR-0029, ADR-0035 ข้อ 2–3
- บริบท: เจ้าของตัดสินให้บันทึกขายได้ทั้งที่ POS และบอท "ตามสะดวก ไม่มีกติกา" (ไม่ใช่บอทเป็นทางสำรองแบบ ADR-0035 ข้อ 5) · ทุกบิลต้องบอกได้ว่าบันทึกที่ไหน โดยใคร · บิลที่ขายที่ POS ต้องมีผู้เขียนคนเดียว (แท็บเล็ต) จึงห้ามแก้บนเว็บ · ขายได้สองที่ทำให้คนบันทึกแก้วเดียวกันซ้ำได้ ต้องมีธงให้ตรวจแต่ห้ามบล็อก · แท็บเล็ตขายตอนออฟไลน์แล้วส่งตามทีหลัง ต้องการ (ก) ส่งหลายแถวในคำขอเดียวพร้อมคำตัดสินรายแถว ให้แถวเสียแถวเดียวไม่ทำคิวค้าง (ข) กันซ้ำด้วย id ของบิลในเครื่อง ไม่ใช่เลขใบเสร็จ — `create_order` (0008) คืน "ซ้ำ" เมื่อ `external_ref` ชน ติดตั้งแอปใหม่แล้วเลขวนซ้ำจะทำให้บิลใหม่หายเงียบ · ตรวจโค้ดพบว่าบิลออฟไลน์จะค้างถาวรเมื่อ: ยกเลิกในวันเดียวกันแต่ส่งถึงวันถัดไป (ADR-0040 ข้อ 2 เทียบกับ "วันนี้" ของเซิร์ฟเวอร์) · ผู้ขายถูกปลดก่อนบิลส่งถึง (`resolveStaffRef` รับเฉพาะ active) · ส่งช้ากว่าเพดานย้อนหลังของบทบาท (`dayo_check_sale_date`) · รหัสเมนู/ช่องทาง/วิธีชำระถูกเปลี่ยน (`save_menu_item` `save_channel` `save_payment_method` แก้ `code` ได้เมื่อส่ง id) · ค่าเริ่มต้นร้าน (นม, `maxQtyPerLine`) ถูกตีความ ณ ตอนบิลมาถึง ไม่ใช่ตอนขาย · และส่วนต่างราคา ≤ ฿1 มองไม่เห็น เพราะ dayo เก็บยอดที่ตัวเองคิดเฉพาะตอนติดธง
- ตัดสินใจ:
  1. **คอลัมน์ใหม่ของ `orders`**: `pos_order_id uuid` (unique partial `(api_client_id, pos_order_id)`) · `pos_queue_no int (1–9999)` · `pos_shift_id uuid` (**ไม่มี FK** — ผูกกะทีหลังได้ P3) · `pos_computed_total numeric(10,2)` (ยอดที่ระบบคิดเองของทุกบิล POS) · `catalog_version bigint` (ฉบับที่ใช้คิดราคา — P1) · `sold_at timestamptz` · `items_signature text` · check สำหรับแถวใหม่: `source='pos'` ⇒ `pos_order_id`, `external_ref`, `created_by` ไม่ว่าง · `sold_at` ของบอท/เว็บ = เวลาบันทึกเมื่อ `sale_date` = วันนี้ ไม่งั้น null · เติมของเก่า: `created_at` เมื่อวันที่ไทยตรง `sale_date`
  2. **แหล่ง** ใช้ `orders.source` ค่าเดิม `pos`/`line`/`web` (หน้าจอแสดง `line` ว่า "บอท") · **ผู้บันทึก** = `created_by` · เว็บ/บอทแสดง "แหล่ง · ผู้บันทึก" ทุกที่ที่แสดงบิล · บิล POS แสดง "ใบเสร็จ <external_ref> · คิว <pos_queue_no>"
  3. **`POST /v1/pos/push`** · RPC `api_pos_push(p_shop_id, p_api_client_id, p_scopes, p_rows)` ก้อนเดียว · ≤ 20 แถว/คำขอ · ≤ 256 KB · แต่ละแถว `{key:"<kind>:<uuid>", kind, data}` ทำใน savepoint ของตัวเอง · คำตอบ 200 `{server_time, results:[{key, status, reason?, detail?, data?}]}` เรียงตามแถว · `status` ∈ `accepted` `duplicate` `rejected` `deferred` · `reason` rejected ∈ `INVALID` `BAD_KEY` `UNKNOWN_CODE` `UNKNOWN_STAFF` `CONFLICT` `FORBIDDEN` · deferred ∈ `PARENT_PENDING` `BUSY` `CLOCK_AHEAD` `UNSUPPORTED` `SERVER_ERROR` · ชนิดในก้อนนี้ `order` และ `order_void` · รูปฟิลด์ตามสเปก POS §4.5 (ล็อก)
  4. **แผนที่ error → คำตัดสิน** (ตารางเต็มในสเปก POS §4.5 — ล็อก): `api_pos_push` จับทุก exception ของแถวใน savepoint · `DY422` → `INVALID` · คำนำหน้า `unknown_code:` (RPC ต้องใช้คำนำหน้านี้ตอนหาเมนู ตัวแปร ตัวเลือก ช่องทาง วิธีชำระไม่พบ) → `UNKNOWN_CODE` · หาพนักงานไม่พบ → `UNKNOWN_STAFF` · `DY403` → `FORBIDDEN` · บิลที่จะยกเลิกไม่พบ → `deferred PARENT_PENDING` · `DY409 external_ref_taken` → `CONFLICT` · `DY409 idempotency_in_progress`/`duplicate_event` → `deferred BUSY` · SQLSTATE `23502 23514 22001 22003 22007 22008 22021 22P02 22P05` → `INVALID` · `40001 40P01 55P03 57014` → `deferred BUSY` · `23505` → หาใหม่ตามข้อ 5 · **อื่นทั้งหมด (รวม `23503`) → `deferred SERVER_ERROR` เฉพาะแถวนั้น** + `console.error` (Discord — ADR-0044) · **ไม่มี error ของแถวใดทำให้ทั้งคำขอเป็น 5xx** · `detail` สะท้อนได้เฉพาะวันที่/เวลา รหัสเมนู-ช่องทาง-วิธีชำระ เลขใบเสร็จ SQLSTATE — ห้าม id พนักงาน ข้อความอิสระ หรือข้อความ error ดิบ
  5. **กันซ้ำ (แก้รีวิวข้อ 1, 8, N2) — ลำดับล็อก**: แถว `order` ตรวจ **ก่อนเรียก `create_order`**: **(1) เทียบ hash ของ key กันซ้ำก่อนเสมอ** — มี key ใน `api_idempotency_keys` (ผลสำเร็จภายใน 30 วัน): hash เท่า → `duplicate` ผลเดิม · hash ต่าง → `CONFLICT` แล้วหยุด · ไม่มี → (2) (ก) มี `(api_client_id, pos_order_id)` แล้ว → `duplicate` (ข) มี `(api_client_id, external_ref)` แต่ `pos_order_id` ต่าง/ว่าง → **`CONFLICT` เสมอ ห้ามเป็น `duplicate`** (ค) ไม่พบ → สร้าง · ทางลัด external_ref ใน `create_order` ต้องเทียบ `pos_order_id` ด้วย ไม่ตรง → `DY409 external_ref_taken` · `api_idempotency_keys` (`endpoint='pos_push'`, `request_hash = sha256(data::jsonb::text)`) **เก็บเฉพาะผลที่บันทึกสำเร็จ** — ผล `rejected`/`deferred` ไม่ถูกเก็บ ส่ง key เดิมด้วยข้อมูลที่ owner แก้แล้วได้ · key เดิม + เนื้อหาต่างจากที่เคยสำเร็จ = `CONFLICT` · หลัง `heartbeat` ลบคีย์ (30 วัน) ยังใช้ข้อ (ก)(ข) · ข้อจำกัดที่ยอมรับ: หลังคีย์หมดอายุ `pos_order_id` เดิมเนื้อหาต่าง = `duplicate` (บิลอยู่ในฐานแล้ว ไม่มีเงินหาย)
  6. แถว `order` เรียก `create_order` ภายใน (actor = `{api_client_id, staff_id}`) · `receipt_no` → `external_ref` · `totals` → `pos_amounts` · เก็บ `pos_computed_total` ทุกบิล และตอบ `computed_total` ในคำตอบ (ส่วนต่างทุกขนาดเห็นได้ ไม่ใช่เฉพาะ > ฿1) · `skip_promotion_ids`/`no_promotions` ส่งต่อไปยังฟิลด์ `skip_promotions`/`no_promotions` ที่ SQL มีอยู่แล้ว (ไม่ใช่ฟิลด์ใหม่) · `sale_time` = `to_char(sold_at at time zone 'Asia/Bangkok','HH24:MI')` (ตัดวินาที) · **ค่าที่ตีความแล้วจากแท็บเล็ต**: `milk` บังคับไม่ null · เกรดมัตจะบังคับไม่ null · **ไม่ตรวจ/บีบ qty กับ `maxQtyPerLine` สำหรับบิล POS** (`dayo_impl_price_line` ข้ามการบีบเมื่อ `p_include_inactive`/บิล POS · เพดาน 1–999 ตาม check) · `bill_discount` ส่งทั้ง `baht` และ `percent` = `INVALID` · **บิล POS ไม่ถูกปฏิเสธเพราะแคตตาล็อกเปลี่ยนหลังขาย**: `include_inactive` ครอบตัวเลือก ช่องทาง วิธีชำระ (ไม่ใช่แค่เมนู) · ปฏิเสธเฉพาะรหัสที่ไม่มีในร้านเลย · `sale_date` ต้องเท่ากับวันที่ไทยของ `sold_at` และอยู่ในช่วง วันนี้−60 วัน ถึง วันนี้ (ไม่ใช้เพดานย้อนหลังตามบทบาท) · `sold_at` เกินเวลาเซิร์ฟเวอร์ + 5 นาที → `deferred CLOCK_AHEAD` (แถวรอ ไม่หาย · ฝั่งแท็บเล็ตนาฬิกาเพี้ยนแค่เตือน ไม่บล็อกการขาย ตาม หลักเดิมของ D58 ของ POS ที่ยกมาใช้ต่อ — รอบันทึกเป็น D79) · ช่วงก้อนนี้แท็บเล็ตส่ง `shift_id: null` เสมอ · `staff_id` รับพนักงานสถานะ `active` หรือ `removed` (การระบุผู้ทำเท่านั้น ตาม ADR-0040 ข้อ 1)
  7. **แก้ ADR-0040 ข้อ 2**: แถว `order_void` ยกเลิกได้เมื่อบิลเป็น `source='pos'` ของ client เดียวกัน **และวันที่ไทยของ `voided_at` (เวลาจากแท็บเล็ต เชื่อได้แบบเดียวกับ `sold_at` — ADR-0040 ข้อ 4) เท่ากับ `sale_date`** (ไม่ตรง = `FORBIDDEN`) · `voided_at ≥ sold_at` (ไม่ตรง = `INVALID`) · `voided_at` เกินเวลาเซิร์ฟเวอร์ + 5 นาที = **`deferred CLOCK_AHEAD`** (ไม่ใช่ rejected) · เก็บ `approved_by` ใน `audit_log.after` · **การคืนเงินสดไม่อยู่ในแถวนี้** — แหล่งเดียวคือ `cash_movement` `VOID_REFUND` (P3) · `VOID_REFUND` ที่เกิดก่อนก้อนกะ (P3) ใช้งานจริงเป็นข้อมูลในเครื่องเท่านั้น ไม่ถูกส่งมาที่นี่ · ยกเลิกซ้ำ = `duplicate` · `PATCH /v1/orders/{order_no}` เดิมคงกติกา "วันนี้"
  8. **ความเข้ากันได้ของรุ่น** (ตัดสินโดยผู้คุมงาน): ฟิลด์หรือชนิดแถวที่ยังไม่รู้จัก = `deferred UNSUPPORTED` (ไม่ใช่ rejected) · dayo deploy ก่อน POS เสมอ · E1 ส่ง `supported_kinds` และ `supported_fields` (P1) ซึ่งต้องตรงกับที่ `api_pos_push` รับจริง (เทสต์: ทุกฟิลด์ในรายการผ่าน · ฟิลด์นอกรายการ = `UNSUPPORTED`)
  9. **บิล POS อ่านอย่างเดียวบนเว็บและบอท**: `update_order`/`cancel_order` ที่ actor ไม่มี `api_client_id` กับบิล `source='pos'` → `DY403 pos_bill_read_only` (รวม owner) · เว็บซ่อนปุ่มแก้/ยกเลิก · flow `edit` ของบอทข้ามบิล POS
  10. **ธงบิลน่าจะซ้ำ**: บิล A, B ติดธงเมื่อ `status='ok'` ทั้งคู่ · `source` ต่างกัน · `sale_date` เดียวกัน · `sold_at` ไม่ว่างและห่างกัน ≤ 10 นาที · `total_amount` เท่ากัน · `items_signature` เท่ากัน (รวม `qty` ตามคีย์ `menu_code|size|sweetness|milk_code|grade_code` เรียงคีย์ ต่อด้วย `;` ไม่นับส่วนลด) · ตรวจใน RPC ทุกครั้งที่สร้างบิลหรือแก้รายการ (ลำดับที่มาถึงไม่มีผล) · ตาราง `order_duplicate_flags (id, shop_id, order_a_id, order_b_id, detected_at, status open/resolved_not_duplicate/resolved_cancelled, resolved_by, resolved_at, resolution_note)` unique คู่ · **ไม่บล็อกการบันทึก** · คำตอบของ push มี `duplicate_of` · owner ปิดธงบนแดชบอร์ด ("ไม่ซ้ำ" + หมายเหตุ) · ยกเลิกบิลใดบิลหนึ่ง → ปิดเองเป็น `resolved_cancelled` · แดชบอร์ด owner แสดงจำนวนธงเปิด · `ยอดวันนี้` ของ owner ในบอทเติม "⚠ บิลที่อาจซ้ำ N ใบ" (reply)
  11. `GET /v1/orders` เพิ่มฟิลด์ `sold_at` `created_by_name` `pos_receipt_no` `pos_queue_no` `catalog_version` `duplicate_suspect` (ไม่มีต้นทุน/กำไรตามเดิม) · แดชบอร์ดแสดงบิล POS ที่ `pos_computed_total ≠ total_amount` แยก "ต่างเล็กน้อย (≤ ฿1)" กับ `amount_mismatch`
  12. **รหัสที่มีบิลอ้างแล้วเปลี่ยนไม่ได้**: `menu_items.code` (Q51) · `sales_channels.code` · `payment_methods.code` (ผู้คุมงานขยายตามรีวิวข้อ 13) — `DY422` แบบเดียวกับรหัสตัวเลือกใน 0005 · เปลี่ยนชื่อ/ชื่อพ้องแทน
  13. **แก้ ADR-0035 ข้อ 5 / สถานะ ADR-0006** (เจ้าของยืนยัน Q53 · D77): หลังเชื่อม POS บันทึกขายได้ทั้ง POS บอท และเว็บเท่ากัน ตามสะดวก ไม่มีช่องทางหลัก/สำรอง · ข้อความใหม่ของ ADR-0035 ข้อ 5: "บอทและเว็บเป็นช่องทางบันทึกขายเท่ากับ POS ตลอดไป · ยอดทุกแหล่งรวมในตาราง `orders` เดียว" · สถานะ ADR-0006: "⚠ แทนที่โดย ADR-0011 (ที่เก็บ) และ ADR-P2 (บอทเป็นช่องทางหนึ่งในหลายช่องทาง ไม่ใช่ที่บันทึกหลักเพียงแห่งเดียว)"
  14. **บิล POS ของวันที่ปิดแล้ว** (Q52 · D76): แก้ไม่ได้ทั้งเว็บและแท็บเล็ต · ส่วนต่างแก้ด้วย `cash_movement` `PAID_IN`/`PAID_OUT` ในกะปัจจุบันพร้อมเหตุผลอ้างเลขใบเสร็จ (P3) หรือบันทึกเป็นค่าใช้จ่าย (P4)
- ทางเลือกที่ไม่เลือก: บล็อกบิลที่น่าจะซ้ำ (ลูกค้าสองคนสั่งเหมือนกันได้จริง — เจ้าของสั่งห้ามบล็อก) · ใช้ `POST /v1/orders` ทีละบิล (ไม่มีคำตัดสินรายแถว และกันซ้ำด้วยเลขใบเสร็จ) · ให้ owner แก้บิล POS บนเว็บ (สองผู้เขียน) · ตรวจซ้ำด้วยเวลา `created_at` (บิลแท็บเล็ตที่ส่งช้าจะห่างหลายชั่วโมงเสมอ) · ปล่อย error ที่ไม่ได้แผนที่เป็น 5xx ทั้งคำขอ (คิวของแท็บเล็ตค้างทั้งหมด) · เก็บผล rejected ใต้ key (แก้ข้อมูลแล้วส่งใหม่ไม่ได้)
- ผลที่ตามมา: migration ใหม่ (คอลัมน์ `orders` · `order_duplicate_flags` · `api_idempotency_keys.endpoint` เพิ่ม `pos_push` · แก้ `create_order` (ทางลัด external_ref เทียบ `pos_order_id` · `pos_computed_total`) `update_order` `cancel_order` `dayo_quote` (include_inactive) `dayo_impl_price_line` (ไม่บีบ qty บิล POS) `dayo_check_sale_date` (บิล POS) `save_menu_item` `save_channel` `save_payment_method` (ล็อกรหัส) `dashboard_*` `backup_dump_table` `bot_recent_orders`) · `app/api/v1/pos/push/route.ts` · `lib/api/orders.ts` · หน้า `/sales/[order_no]` · แดชบอร์ด · บอท (`ยอดวันนี้`, flow `edit`) · DATA-CONTRACT §2.4/§3/§8 · API.md · GLOSSARY ("บิลน่าจะซ้ำ", "แหล่ง") · เทสต์ตามเกณฑ์ก้อน 1 ในสเปก POS §9 (รวม: ใบเสร็จชน `pos_order_id` ใหม่ก่อน/หลังลบคีย์ = `CONFLICT` · rejected แล้วส่ง key เดิมข้อมูลใหม่ = `accepted` · ทุกแถวของตารางแผนที่ error · error ที่ไม่ได้แผนที่ = `deferred SERVER_ERROR` HTTP 200) และทุกไฟล์ fixture ของ POS (`packages/contracts/fixtures/dayo-api/`) ผ่าน
