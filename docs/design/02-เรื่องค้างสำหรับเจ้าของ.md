# เรื่องค้างที่รอเจ้าของอ่าน

ไฟล์นี้เป็นที่รวม **เรื่องที่ผมตัดสินใจเองไม่ได้** และ **ข้อควรรู้ก่อนเอาไปใช้จริง** เจ้าของอ่านตอนไหนก็ได้ ไม่ต้องรีบ — งานยังเดินต่อได้โดยไม่ต้องรอคำตอบ

เรื่องที่ผมตัดสินใจเองไปแล้วจะไม่อยู่ในนี้ แต่ถูกบันทึกไว้ใน `00-บันทึกการตัดสินใจ.md`

อัปเดตล่าสุด: 25 ก.ย. 2026 (ปรับตามสถาปัตยกรรม C1 — ใช้ฐานข้อมูลกลางเดียวกับ dayo ไม่มีเซิร์ฟเวอร์ POS แยกอีกต่อไป ดู D59–D66 ใน `00-บันทึกการตัดสินใจ.md`)

---

## ก. ต้องให้เจ้าของทำเอง (ผมทำแทนไม่ได้)

### ก-1 ตั้งค่าสำรองข้อมูลขึ้น OneDrive
ต้องรัน `rclone config` ครั้งเดียวด้วยบัญชี Microsoft ของเจ้าของเอง (ใช้แอปของ rclone เอง ไม่ต้องจดทะเบียนแอป ไม่ต้องผูกบัตร) แล้วเอา token ที่ได้ไปใส่เป็น GitHub secret ของ repo `dayo-shop-system` — ผมไม่เห็นและไม่ควรเห็น token นี้ · เมื่อ workflow ต่ออายุ token ให้เองในภายหลัง มันต้องเขียน token ใหม่กลับเข้า GitHub secret ตัวเดิม ซึ่งต้องมี **fine-grained personal access token (PAT) ของ GitHub ที่เจ้าของสร้างเอง** (จำกัดสิทธิ์แค่แก้ secret ของ repo นี้) ให้ workflow ใช้เขียนกลับ
**ต้องทำตอน:** ก่อนเปิดงาน backup อัตโนมัติ (บล็อก 1)

### ก-2 ตั้งรหัสเข้ารหัสไฟล์สำรอง
ไฟล์ `pg_dump` ที่จะขึ้น OneDrive ต้องเข้ารหัสด้วยรหัสที่เจ้าของถือไว้คนเดียว รหัสนี้เก็บเป็น **GitHub secret ด้วย** (เพื่อให้ workflow ทดสอบ restore รายเดือนถอดรหัสเองได้แบบอัตโนมัติ ไม่ต้องรอเจ้าของพิมพ์รหัส) **แต่เจ้าของยังต้องเก็บสำเนารหัสนี้ไว้นอก GitHub อีกที่หนึ่งด้วย** (เช่น password manager) เผื่อ GitHub ใช้ไม่ได้หรือ secret หาย — ถ้ารหัสหายไปทั้งสองที่ ไฟล์สำรองกู้ไม่ได้เลย
**ต้องทำตอน:** ก่อนเปิดงาน backup อัตโนมัติ (บล็อก 1)

### ก-3 ส่งร่าง ADR ใหม่ให้ฝั่ง dayo
งานบล็อก C1 มีบางจุดที่ต้องแก้ ADR ที่ dayo อนุมัติไปแล้ว (เช่น ADR-0026 เรื่องต้นทุน) กฎคือ agent ของ POS **แก้โค้ด/ตัดสินใจในฝั่ง dayo เองไม่ได้** ทำได้แค่เขียนร่าง ADR ใหม่ไว้ที่ `docs/design/dayo-adr-drafts/` (สถานะ "เสนอ") เจ้าของต้องเอาร่างพวกนี้ไปให้ session ของ dayo อ่านและตัดสินใจ/แก้จริงในฝั่งนั้นเอง
**ต้องทำตอน:** ทุกครั้งที่มีร่างใหม่โผล่ในโฟลเดอร์นั้น (ยังไม่มีร่างตอนนี้)

### ก-4 ออก API key ให้แท็บเล็ตบนเว็บของ dayo
พอบล็อก 1 (เปิด `/api/v1` ของ dayo) เสร็จ ต้องเข้าเว็บของ dayo แล้วออก API key ให้แท็บเล็ตใช้เชื่อมต่อ — เป็นขั้นที่ต้องกดเองบนเว็บ dayo ไม่มีสคริปต์ทำแทน
**ต้องทำตอน:** พอบล็อก 1 เสร็จ ก่อนเริ่มบล็อก 2

### ก-5 ลบโฟลเดอร์ worktree ของแผน 5 ทั้ง 3 โฟลเดอร์
เพราะเซิร์ฟเวอร์ POS ของแผน 5/5b/5c ไม่ไปต่อแล้ว (เก็บ branch ไว้เป็น archive อ้างอิงเท่านั้น) โฟลเดอร์ทำงานที่แยกไว้ไม่ต้องใช้แล้ว ลบโฟลเดอร์ได้เลย (branch ในนั้นยังอยู่ใน git ไม่หายไปไหน):
```
git worktree remove ../pos-management-5
git worktree remove ../pos-management-5-pos
git worktree remove ../pos-management-5-pull
```
**ต้องทำตอน:** เมื่อไหร่ก็ได้ ไม่รีบ

### ก-6 ตั้ง Discord webhook ของช่อง `#dayo-ระบบ`
การแจ้งเตือนเมื่อ backup ล้มเหลวเปลี่ยนไปแจ้งที่ **Discord ช่อง `#dayo-ระบบ`** ตาม ADR-0044 (ไม่ใช่ไลน์แล้ว) ถ้าช่องนี้ยังไม่มี webhook ต้องสร้าง webhook ของ Discord เอง แล้วใส่ URL เป็น GitHub secret ให้ workflow เรียกแจ้งเตือนได้
**ต้องทำตอน:** ก่อนเปิดงาน backup อัตโนมัติ (บล็อก 1)

## ข. เรื่องที่อยากให้เจ้าของรู้ (ผมจัดการต่อเองได้ แต่ควรรับทราบ)

### ข-1 ชื่อสินค้าที่ยาวเกินไปอาจทำให้ข้อมูลตกค้าง
เรื่องนี้ยังไม่หายไปแม้เปลี่ยนมาใช้ dayo เป็นฐานข้อมูลกลาง — ตอนนำเข้า Excel แบบ "แทนที่ทั้งหมด" (D60) ถ้าตั้งชื่อสินค้ายาวผิดปกติ อาจทำให้แถวนั้นนำเข้าไม่ผ่านและค้างอยู่ในคิว
**แผน:** จะไปปิดช่องนี้ตอนทำหน้านำเข้า/ตรวจไฟล์ (บล็อก 1–2) — ระหว่างนี้ขอแค่ไม่ตั้งชื่อสินค้ายาวผิดปกติ

### ข-2 การทดสอบบนแท็บเล็ตจริงยังไม่ได้ทำ
ตามที่ตกลงกันไว้ (D51) การทดสอบบนเครื่องจริงยังเลื่อนไปทำท้ายสุดของลำดับงาน 6 บล็อก (D65) ทุกอย่างตอนนี้ผ่านการทดสอบอัตโนมัติบนคอมพิวเตอร์เท่านั้น
**ผลที่ตามมา:** อาจเจอเรื่องจอ ขนาดปุ่ม หรือความเร็วบนเครื่องจริง ที่การทดสอบแบบนี้จับไม่ได้

## ค. เรื่องที่รอจนกว่าจะถึงแผนถัดไป (ไม่ต้องทำอะไรตอนนี้)

- **ค-1** ตัวตรวจความถูกต้องย้อนหลังของต้นทุนและยอดบิล (invariant check รายคืน) ยังอยู่ในแผนหลัง ๆ เหมือนเดิม แต่ตอนนี้จะตรวจกับฐานข้อมูลกลางของ dayo แทนฐานข้อมูล POS เอง

---

## ไม่ต้องทำแล้ว (เปลี่ยนเป็น C1)

รายการต่อไปนี้เคยอยู่ใน "ก./ข./ค." ของไฟล์นี้ แต่ **ไม่เกี่ยวแล้ว** ตั้งแต่ตัดสินใจใช้สถาปัตยกรรม C1 (D59: ไม่มีเซิร์ฟเวอร์ POS แยก ใช้ Supabase ของ dayo เป็นฐานข้อมูลกลางเดียว) — เก็บไว้ให้ดูเป็นประวัติ ไม่ต้องทำอะไรกับข้อพวกนี้อีก

- **สมัครบัญชีโฮสติ้ง Render/Neon ของ POS เอง** — ไม่ต้องทำ เพราะไม่มีเซิร์ฟเวอร์/ฐานข้อมูล POS แยกให้สมัครแล้ว ใช้ Supabase ของ dayo ที่มีอยู่แล้ว
- **รหัสลงทะเบียนเครื่อง (`REGISTRATION_CODE`)** — ไม่ต้องทำ เพราะไม่มี auth แบบนั้นของเซิร์ฟเวอร์ POS เองอีกต่อไป การผูกแท็บเล็ตเข้ากับร้านเปลี่ยนไปใช้กลไกของ dayo API แทน (ออกแบบจริงในบล็อก 2)
- **ทดสอบสัญญาณปิดโปรแกรมแบบสุภาพ (SIGTERM) บน Linux** — ไม่ต้องทำ เพราะไม่มีเซิร์ฟเวอร์ POS ของตัวเองให้ปิดโปรแกรม
- **การป้องกันการยิงถล่มเซิร์ฟเวอร์ที่ชั้น edge (Cloudflare rate limit) ของเซิร์ฟเวอร์ POS** — ไม่ต้องทำ เพราะไม่มีเซิร์ฟเวอร์ POS ให้ป้องกัน (ฝั่ง dayo มีการป้องกันของตัวเองอยู่แล้ว)
- **ฝั่งเซิร์ฟเวอร์ POS เขียนข้อมูลแก้ไขเองไม่ได้ (เดิมอยู่แผน 6)** — ไม่ต้องทำ เพราะไม่มีเซิร์ฟเวอร์ POS ให้เพิ่มสิทธิ์เขียน ข้อมูลหลักแก้ที่ dayo web อยู่แล้ว
- **หน้าจัดการข้อมูลหลัก — สินค้า/สูตร/ราคา (เดิมอยู่แผน 5c)** — ไม่ต้องทำ เพราะ dayo web มีหน้าจัดการข้อมูลหลักของตัวเองอยู่แล้ว ไม่ต้องสร้างซ้ำฝั่ง POS
