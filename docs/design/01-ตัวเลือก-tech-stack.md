## 1. หลักคิดก่อนเลือกภาษา

**ภาษาของเซิร์ฟเวอร์ไม่ใช่คอขวดของ POS ร้านเดียว** ร้านนี้มีไม่กี่ร้อยบิลต่อวัน Node ธรรมดารับได้สบายหลายพันเท่า

ความเร็วที่ผู้ใช้รู้สึกจริงมาจาก **การอ่าน/เขียนฐานข้อมูลในเครื่อง** (ระดับมิลลิวินาที ไม่ต้องรอเน็ต) ไม่ใช่จากภาษาของ backend

ความถูกต้องมาจาก 4 อย่าง ไม่ใช่จากภาษา:
1. **ตรรกะเรื่องเงินและสต็อกอยู่ในที่เดียว** — ใช้โค้ดชุดเดียวกันทั้งในเครื่องและบนเซิร์ฟเวอร์ ไม่มีทางที่สองฝั่งจะคำนวณราคาไม่ตรงกัน
2. **type ต่อเนื่องตั้งแต่ฐานข้อมูลถึงหน้าจอ** — เปลี่ยน schema แล้ว compiler ชี้จุดที่พังให้ทันที
3. **property-based test** กับ invariant เช่น "Σ บรรทัด = หัวบิล", "ยอดสต็อกในแคช = ผลรวมของ movement"
4. **constraint ในฐานข้อมูล** (CHECK, UNIQUE, FK) เป็นด่านสุดท้าย

→ ข้อ 1 คือเหตุผลชี้ขาด: **ถ้าเครื่องกับเซิร์ฟเวอร์ใช้คนละภาษา ตรรกะราคาและการตัดสต็อกต้องเขียนสองครั้ง** ซึ่งเป็นแหล่งบั๊กเรื่องเงินที่แย่ที่สุด

## 2. เปรียบเทียบตัวเลือก

| ตัวเลือก | ข้อดี | ข้อเสีย | สรุป |
|---|---|---|---|
| **A. TypeScript ทั้งระบบ** | ตรรกะโดเมนชุดเดียวใช้ทั้งเครื่องและเซิร์ฟเวอร์ · ใช้ความถนัดเดิมได้เต็มที่ · ecosystem offline/SQLite/ORM ครบ · หน้าจอเดียวใช้ได้ทุกอุปกรณ์ | runtime ช้ากว่า Go/Rust (ไม่มีผลในงานนี้) · ถ้าวันหน้าต้องใช้ SDK native ของ SUNMI ต้องห่อด้วย Capacitor/Tauri | ⭐ **แนะนำ** |
| **B. Flutter (Dart) + backend TS** | แอป native บนแท็บเล็ตลื่นมาก · ต่อเครื่องพิมพ์/บลูทูธตรงได้ · มี `drift` (SQLite) ที่ดี | 2 ภาษา → ตรรกะเงินเขียน 2 ชุด หรือต้องย้ายทุกอย่างไปอยู่ฝั่งเครื่อง · ภาษาใหม่ · back office บนเว็บทำซ้ำ | เหมาะถ้า hardware เป็นเรื่องหลัก — ซึ่งถูกเลื่อนไปแล้ว (D4) |
| **C. React + backend Go หรือ Rust** | เซิร์ฟเวอร์เร็วมาก ใช้หน่วยความจำน้อย | ความเร็วที่ไม่มีใครต้องการ · ตรรกะเงินเขียน 2 ภาษา | ❌ ความเสี่ยงด้านความถูกต้องสูงกว่าที่ได้ |
| **D. Kotlin native Android** | ต่อ SUNMI/อุปกรณ์ได้ดีที่สุด | ล็อกกับ Android · back office ต้องทำแยก · 2 ภาษา | ❌ ขัดกับ D2 (ยังไม่ผูกอุปกรณ์) |

## 3. Stack ที่แนะนำ (ตัวเลือก A)

```
pos-management/                 monorepo (pnpm workspaces + Turborepo)
├── packages/
│   ├── domain/        ⭐ TypeScript ล้วน ไม่มี I/O
│   │                   คำนวณราคา · ตัดสต็อกตามสูตร · เลขที่บิล · คำนวณกะ/เงินสด · กฎภาษี
│   │                   ทดสอบด้วย Vitest + fast-check (property-based)
│   ├── contracts/     Zod schema ของข้อมูลที่ sync ระหว่างเครื่องกับเซิร์ฟเวอร์
│   └── db-schema/     Drizzle schema (ฝั่งเครื่อง + ฝั่งเซิร์ฟเวอร์) + migration
├── apps/
│   ├── pos/           React + Vite + TanStack Router · ติดตั้งเป็น PWA
│   │                   ฐานข้อมูลในเครื่อง: SQLite (WASM) บน OPFS ใน Web Worker
│   ├── api/           NestJS บน Node LTS + PostgreSQL + Drizzle  (Render + Neon, ฟรี ไม่ผูกบัตร)
│   │                   หน้าที่: รับ sync · เป็นเจ้าของข้อมูลอ้างอิง · รายงาน · สำรองข้อมูล
│   └── print-agent/   (ภายหลัง ตาม D4)
```

### ทำไมแต่ละชิ้น

| ชิ้น | เลือก | เหตุผล | ทางเลือกอื่น |
|---|---|---|---|
| ภาษา | **TypeScript (strict)** | ตรรกะชุดเดียวทั้งสองฝั่ง ใช้ความถนัดเดิม | — |
| Monorepo | **pnpm + Turborepo** | แชร์ package `domain` ได้โดยตรง build/test เฉพาะส่วนที่เปลี่ยน | Nx (หนักกว่า) |
| หน้าจอ POS | **React + Vite** (ไม่ใช่ Next.js) | POS ออฟไลน์เป็น SPA ล้วน ไม่ต้องการ SSR · Vite เริ่มเร็ว build เร็ว | Next.js — ได้ประโยชน์น้อยเมื่อทุกอย่างรันในเครื่อง |
| Routing / state ที่มาจาก DB | **TanStack Router + TanStack Query** | type-safe route · cache/invalidate ข้อมูลจาก SQLite ได้ง่าย | React Router |
| ฐานข้อมูลในเครื่อง | **SQLite WASM บน OPFS** | SQLite คือฐานข้อมูลที่ผ่านการใช้งานจริงมากที่สุดในโลก · มี transaction และ constraint จริง · อ่านเขียนระดับมิลลิวินาที | **PGlite** (Postgres ใน WASM) — ได้ dialect เดียวกับเซิร์ฟเวอร์ แต่ใหม่กว่า หนักกว่า |
| ORM | **Drizzle** | type-safe · SQL-first ไม่ซ่อน query · รองรับทั้ง SQLite และ Postgres | Kysely |
| Validation / สัญญา API | **Zod** | ใช้ schema เดียวทั้ง validate ขาเข้าและสร้าง type | Valibot (เล็กกว่า) |
| Backend | **NestJS** (ตัดสินใจ D13) | ถนัดอยู่แล้ว · โครงสร้าง module/DI ช่วยเมื่อระบบโตขึ้น (เดลิเวอรี, print-agent, LINE) · ใช้ Drizzle เป็น ORM ไม่ใช้ TypeORM เพื่อแชร์ schema กับฝั่งเครื่อง · รันบน Render free ที่ถูก ping ให้ตื่นตลอด · รวม LINE webhook/LIFF API ไว้ใน app เดียว | Hono — เล็กและเบากว่า แต่ผลต่างไม่มากในงานนี้ |
| ฐานข้อมูลเซิร์ฟเวอร์ | **PostgreSQL** | constraint เข้ม · sequence สำหรับ sync cursor · รายงานเชิงวิเคราะห์ | — |
| Test | **Vitest + fast-check + Playwright** | unit + property-based + end-to-end ตามลำดับ | — |
| ทางหนีไปใช้ native (อนาคต) | **Capacitor** หรือ **Tauri 2** | ห่อแอปเว็บเดิมเพื่อเรียก SDK เครื่องพิมพ์ SUNMI / บลูทูธ โดยไม่เขียนหน้าจอใหม่ | — |

### จุดที่ต้องพิสูจน์ด้วย spike ก่อนยึดเป็นแผนจริง

1. **SQLite WASM + OPFS บน Chrome Android และ Safari iPad** — ความทนทานของข้อมูลเมื่อปิดแอป/รีสตาร์ทเครื่อง · VFS แบบไหนที่ไม่ต้องตั้ง header COOP/COEP · การขอ persistent storage
2. **Drizzle กับ SQLite ที่รันใน Web Worker** — driver แบบ proxy ทำงานกับ transaction ได้ถูกต้องหรือไม่
3. **การแชร์ schema ระหว่าง SQLite กับ Postgres** — Drizzle แยก `sqliteTable` กับ `pgTable` จึงต้องมี schema 2 ชุด → ต้องมี **เทสต์ตรวจว่าสองชุดตรงกัน** (หรือเลือก PGlite เพื่อใช้ dialect เดียว)

## 4. ข้อแลกเปลี่ยนที่ยอมรับ

- **ไม่ได้ความเร็ว runtime สูงสุด** — แลกกับการมีตรรกะเงินชุดเดียว
- **ยังไม่ได้ native** — แลกกับการไม่ผูกอุปกรณ์ในระยะแรก (D2) และมีทางหนีผ่าน Capacitor/Tauri
- **schema 2 dialect** (ถ้าใช้ SQLite ในเครื่อง) — แลกกับความทนทานของ SQLite · แก้ด้วยเทสต์ตรวจความตรงกัน
