## 1. หลักคิด

1. **หัวหน้าทีม (เซสชันหลัก) คิดและตัดสิน ลูกทีมลงมือ** — งานที่มีสเปกและเทสต์ชัดให้ Sonnet · งานที่ผิดแล้วเสียเงินหรือข้อมูลเพี้ยน (สูตรเงิน, การส่งข้อมูลกันซ้ำ, สิทธิ์, สถาปัตยกรรม) ให้ Opus
2. **งานอ่าน-สรุปปริมาณมากให้ Haiku** — รันเทสต์ ค้นเอกสาร · log ยาวไม่ไหลเข้าเซสชันหลัก
3. **Fable ไม่อยู่ในทีมประจำ** — เรียกเฉพาะตอน Opus ติดปัญหาเดิม 2 รอบ
4. **ไม่แตก agent เกินจำเป็น** — agent ทุกตัวต้องโหลดบริบทใหม่หลายพัน token · งานแก้ 1–2 ไฟล์หัวหน้าทำเอง · งานเล็กรูปแบบเดียวกันหลายไฟล์รวมเป็นงานเดียว
5. **เทสต์คือสัญญา** — ลูกทีมทำงานได้ดีเพราะมีเทสต์ (โดยเฉพาะ parity test กับสูตรเงินของ dayo) คอยตรวจผล ไม่ใช่เพราะเชื่อใจ
6. **สองระบบ สองทีม หนึ่งสัญญา** — โค้ดฝั่ง dayo แก้ใน session ของ repo dayo ด้วยทีมของมันเอง · ทีม POS อ่าน repo dayo ได้อย่างเดียว · ทั้งสองทีมยึด **สัญญา API** ในสเปก `docs/design/04-*` เป็นตัวเชื่อม

- `code-reviewer` ต้องให้ **สองคำตัดสิน** (ตรงสเปก + คุณภาพ) ตามรูปแบบ subagent-driven-development ที่ใช้มาตั้งแต่แผน 1

## 3. Workflow มาตรฐานของ 1 แผน

```
เจ้าของ ──"เริ่มงานก้อน N"──▶ หัวหน้า (Opus)
  1. architect เขียนแผนจากสเปก + ตารางงานขนาน + จุดขัด D/ADR
       └─ มีจุดขัด หรือต้องเปลี่ยนฝั่ง dayo → หัวหน้าถามเจ้าของก่อน
  2. หัวหน้าตรวจแผนเทียบสเปก แล้วแบ่งเป็น "สาย" (stream)
       · สายละ 1 git worktree + 1 ledger (.superpowers/sdd/<แผน>/progress.md)
       · ขนานได้เฉพาะสายที่ไม่แตะ package เดียวกัน และไม่รอ interface ของกัน
       · สูงสุด 4 agent พร้อมกัน
  3. ในแต่ละสาย ทำทีละงาน:
       implementer (domain / sync / ui) → test-runner
         → code-reviewer (+ security-reviewer ถ้าแตะ PIN/สิทธิ์/key/สำรอง)
         → มีข้อที่ต้องแก้: ส่งกลับ implementer ตัวเดิม (SendMessage) รอบ 1–3
                            รอบ 4–5 ใช้ implementer ใหม่ที่โมเดลสูงขึ้น 1 ขั้น
         → ผ่าน: บันทึกลง ledger ว่า "Task N: complete"
  4. จบทุกงานในสาย → ตรวจทั้งสาย (Opus) → แก้ 1 รอบ → ตรวจซ้ำเฉพาะจุด
  5. รวมสายเข้า main แบบ --no-ff หลังผ่านการตรวจ → รันเทสต์ทั้ง repo → push
  6. docs-writer อัปเดตบันทึกการตัดสินใจ/เรื่องค้าง → หัวหน้าสรุปให้เจ้าของ
```

**กติกาการส่งงาน**
- สั่งงานด้วย **ข้อความครบในตัว**: เป้าหมาย, path ของ brief (ไฟล์), interface จากงานก่อนหน้า, เกณฑ์เสร็จ, สิ่งที่ห้ามทำ — agent ไม่เห็นประวัติแชทของหัวหน้า
- ส่งของให้กันเป็น **ไฟล์** (brief, report, review package) ไม่แปะเนื้อหายาวในข้อความ
- ขอผลตอบกลับเป็น **สรุปสั้น**: สถานะ, commit, ผลเทสต์ 1 บรรทัด, ข้อกังวล
- งานต่อเนื่องใช้ agent ตัวเดิม (resume) · ระบุโมเดลทุกครั้งที่สั่ง (ไม่ระบุ = ได้ Opus ราคาแพง)
- ข้อขัดแย้งระหว่างทำงาน หัวหน้าตัดสินเองแล้วบันทึกใน ledger เป็น `Ruling: <ตัดสินอะไร> — <เพราะ> — <ถ้าผิดเสียอะไร>` · หยุดถามเจ้าของเฉพาะเรื่องที่ย้อนไม่ได้ เรื่องความปลอดภัย หรือเรื่องที่กระทบภายนอก

**บทเรียนจากแผน 1–5 (บังคับ)**
- ห้าม `git checkout -- <ไฟล์>` / `git reset --hard` เพื่อย้อนงาน — เคยลบงานที่ยังไม่ commit ทิ้งไปแล้ว · ถ้าต้องย้อน ให้สำรองไฟล์ไว้นอก repo ก่อน
- ผู้ตรวจที่ลองแก้โค้ดเพื่อพิสูจน์ (mutation/probe) ต้องคืนค่าเดิมและลบไฟล์ probe ก่อนตอบ · หัวหน้าตรวจ `git status` ทุกครั้งหลังผู้ตรวจจบ
- ถ้าโควตาหมดกลางงาน: ตรวจ `git status` ทุก worktree → ย้อนการแก้ที่ผู้ตรวจทิ้งไว้ → รันเทสต์ทั้ง repo → commit งานจริงที่ค้าง → ทำต่อจาก ledger (อย่าเชื่อความจำ)
- implementer ห้ามสร้าง agent ต่อ (ตั้งไว้แล้วที่ spawn depth = 1)

## 4. การทำงานขนานข้ามสองระบบ

ลำดับงาน 6 ก้อน (ตามที่เจ้าของเลือกใน Q35):

| ก้อน | งาน | ทีมหลัก | ขนานกับ |
|---|---|---|---|
| 1 | เปิด API, พนักงานใน API, ช่องทาง/ผู้บันทึกของบิล, เตือนบิลซ้ำ, สำรองอัตโนมัติ | **ทีม dayo** | ก้อน 2 (ฝั่ง POS ทำกับ mock server จากสัญญา) |
| 2 | POS ขายด้วยเมนู/ราคา/โปรกลาง ทำงานออฟไลน์ ส่งบิลขึ้น | **ทีม POS** | ก้อน 1 |
| 3 | กะ/เงินสด/ใบปิดกะ | dayo (ตาราง+RPC) ∥ POS (หน้าจอ+ส่งข้อมูล) | — |
| 4 | ค่าใช้จ่าย + กำไรสุทธิ | dayo ∥ POS | — |
| 5 | ต้นทุนถัวเฉลี่ย | dayo เป็นหลัก | POS แค่แสดงผล |
| 6 | ตอกบัตร + เงินเดือน | dayo ∥ POS | — |

- ก่อนเริ่มแต่ละก้อน `architect` ของ POS **ล็อกสัญญา API ของก้อนนั้น** ในสเปก (ชื่อ endpoint, ฟิลด์, หน่วย, การกันซ้ำ, ตัวอย่าง request/response) แล้วเจ้าของส่งให้ session ของ dayo
- สองทีมทำพร้อมกันได้เพราะต่างคนต่างทดสอบกับสัญญาเดียวกัน · ฝั่ง POS ใช้ mock server ที่สร้างจาก `packages/contracts`
- จุดรวม: เทสต์เชื่อมจริงกับ Supabase local ของ dayo **ก่อน** เปิดใช้งาน · ถ้าสัญญาต้องเปลี่ยน ให้แก้ในสเปกก่อน แล้วทั้งสองทีมทำตาม

**ใครทำอะไรในแต่ละก้อน (ฝั่ง POS)**

| ก้อน | หลัก | ช่วย | ตรวจ |
|---|---|---|---|
| 2 ขายด้วยเมนูกลาง | domain-engineer (สูตรราคา + ตัวแปลงเงิน) → sync-engineer (ดึงเมนู/ส่งบิล) ∥ pos-ui-developer (หน้าจอขาย) | test-runner, docs-researcher (API dayo) | code-reviewer + **security-reviewer** (API key ของแท็บเล็ต) |
| 3 กะ/เงินสด | domain-engineer → sync-engineer ∥ pos-ui-developer | test-runner | code-reviewer |
| 4 ค่าใช้จ่าย | domain-engineer ∥ pos-ui-developer | test-runner | code-reviewer |
| 5 ต้นทุนถัวเฉลี่ย | (ฝั่ง dayo) · pos-ui-developer แสดงผล | — | code-reviewer |
| 6 ตอกบัตร/เงินเดือน | domain-engineer → sync-engineer ∥ pos-ui-developer | test-runner | code-reviewer + **security-reviewer** (PIN) |
| ทดสอบแท็บเล็ตจริง (D51) | เจ้าของ + devops | docs-writer (คู่มือ) | — |

## 6. คุมค่าใช้จ่ายและโควตา

| มาตรการ | ตั้งไว้ที่ |
|---|---|
| agent สร้าง agent ต่อไม่ได้ | `.claude/settings.json` → `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1` |
| รันพร้อมกันสูงสุด 4 agent | `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS=4` |
| agent Haiku มีเพดานรอบ | `maxTurns` ในไฟล์ agent |
| effort ต่ำสำหรับงานเอกสาร สูงเฉพาะงานเสี่ยง | ไฟล์ agent |
| อ่านค่าลับไม่ได้ (ทั้ง POS และ dayo) | `permissions.deny` |
| push/deploy/ตั้ง secret ต้องถามก่อน | `permissions.ask` |

**ถ้าโควตาตึง:** ให้หัวหน้าใช้ Sonnet และคง Opus ไว้แค่ `architect`, `domain-engineer`, `sync-engineer`, `security-reviewer`
**บันไดยกระดับเมื่อ agent ติด:** Haiku → Sonnet → Opus → Fable · ติด 2 รอบที่ระดับใดให้ยกขึ้น 1 ขั้น (สั่งรายครั้ง ไม่แก้ไฟล์ agent)

## 7. เมื่อไรควรปรับทีม

- agent ใดถูกเรียกน้อยกว่า 1 ครั้งต่อ 3 แผน → รวมงานเข้าหัวหน้าแล้วลบไฟล์ agent
- test-runner สรุปผิดบ่อย → เปลี่ยนเป็น Sonnet effort low
- code-reviewer พลาดสิ่งที่ security-reviewer เจอซ้ำ ๆ → เพิ่ม checklist ใน code-reviewer
- โมเดลรุ่นใหม่ออก → alias (`opus`/`sonnet`/`haiku`) ขยับตามเอง · ทบทวนตารางข้อ 2 แล้วบันทึกเป็น D ใหม่
