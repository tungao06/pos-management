# ประเมินสถาปัตยกรรม: POS กับระบบ LINE bot (dayo-shop-system)

เขียนเมื่อ 25 ก.ย. 2026 · ตอบคำถามเจ้าของ: "ให้ LINE bot ถือสูตร POS จัดการเงิน/บัญชี/บริหารร้าน ขายได้ทุกที่ ควรเก็บยอดขายที่ไหน sync อย่างไร หรือรวมเป็นระบบเดียว ฐานข้อมูลเดียว"

สถานะ: **รอเจ้าของเลือกทาง** — ยังไม่มีการแก้โค้ดใด ๆ

---

## 1. สรุปคำตอบ

1. **ยอดขายต้องอยู่ในฐานข้อมูลเดียวบนเซิร์ฟเวอร์ ที่ทุกช่องทางเขียนเข้าได้** ห้ามแยกไว้สองฐาน และห้ามเก็บไว้แค่ในแท็บเล็ต เพราะบอทบันทึกขายแบบออนไลน์ ส่วน POS บันทึกแบบออฟไลน์แล้วส่งตามทีหลัง ที่ที่ทั้งสองส่งถึงได้มีแค่ฝั่งเซิร์ฟเวอร์
2. **การ sync ต้องเป็น "ข้อมูลแต่ละชิ้นมีเจ้าของคนเดียว ที่เหลือเป็นสำเนาทางเดียว"** ไม่มีการ sync สองทางของข้อมูลชิ้นเดียวกันระหว่างสองฐาน — จุดนั้นคือจุดที่เงินเพี้ยน
3. **คำแนะนำ: ทาง C1 — ฐานข้อมูลเดียว (Supabase ของระบบ LINE bot) แต่ให้ POS เป็นเครื่องมือจัดการเงินและบริหารร้าน**

ข้อ 3 ตอบความต้องการของคุณได้ครบทั้งสามข้อ เพราะ **"ระบบไหนเป็นเครื่องมือทำงานเรื่องเงิน" กับ "ตัวเลขเก็บอยู่ในฐานไหน" เป็นคนละคำถามกัน** POS เป็นหน้าจอที่ใช้ปิดกะ นับเงิน ดูใบปิดกะ ดูกำไรได้ โดยตัวเลขทั้งหมดอยู่ในฐานเดียวกับยอดขายจากบอท

ข้อเสนอเดิมของคุณ (ทาง B) ได้บัญชีที่เข้มกว่าจริง แต่ต้องแลกด้วยการเก็บยอดขายไว้สองฐานแล้ว sync สองทาง และต้องรื้อระบบที่ใช้งานจริงแล้วเกือบทั้งระบบ — ความแม่นของบัญชีที่ได้มาจะถูกกินด้วยความเสี่ยงที่ตัวเลขสองฝั่งไม่ตรงกัน ส่วนที่ดีของทาง B (บัญชีแบบห้ามแก้ ต้นทุนถัวเฉลี่ยจากราคาซื้อจริง) **ย้ายเข้าฐานเดียวได้** โดยไม่ต้องมีฐานที่สอง

## 3. ข้อเท็จจริงที่ใช้ประเมิน

**ระบบ LINE bot (dayo-shop-system)**
- ใช้งานจริงแล้ว (เฟส 12) · โค้ดราว 60,000 บรรทัด (เว็บ 16k · บอท 20k · โค้ดร่วม 14k · migration 9k)
- Supabase (Postgres) + Cloudflare Workers ฟรีทั้งหมด
- บันทึกบิลด้วย RPC `create_order` ก้อนเดียว: ออกเลข `L260925-001` · คิดราคา · แช่แข็งต้นทุน · **ตัดสต๊อกในธุรกรรมเดียวกัน** · กันซ้ำด้วย `external_ref` / `event_id` / `confirm_token`
- แก้บิลด้วย `update_order` (มี version กันชน + `audit_log`) · owner แก้ได้ทุกบิลทุกวัน
- ต้นทุน = สูตร × ราคาวัตถุดิบ (ต้นทุนมาตรฐาน ADR-0026) · ไม่มีขั้นต้มเบส · ไม่มีกะ/ลิ้นชัก/ใบปิดกะ
- ลิมิต: Workers 100,000 คำขอ/วันรวมทั้งบัญชี · CPU 10 ms/คำขอ · Supabase 500 MB/โปรเจกต์ · พักเมื่อเงียบ 7 วัน · **ไม่มีสำรองอัตโนมัติ**
- API `/api/v1` สร้างไว้แล้วสำหรับ POS แต่ปิดอยู่ (ADR-0042)

**POS (pos-management)**
- ยังไม่ขึ้นใช้งาน · โค้ดราว 14,000 บรรทัดบน main (+ เซิร์ฟเวอร์แผน 5 บนสาขาที่ยังไม่ merge)
- ขายออฟไลน์ได้ (SQLite ในแท็บเล็ต) · เงินเป็นสตางค์จำนวนเต็ม
- **บัญชีเข้มกว่า**: ตารางบัญชีห้ามแก้ห้ามลบ (บังคับด้วย trigger) · event ของบิลต่อกันเป็นโซ่แฮช · ต้นทุนถัวเฉลี่ยจากราคาซื้อจริง · กะ ลิ้นชัก ใบปิดกะ เงินขาด/เกิน
- ไม่มีโปรโมชั่น · ไม่มีค่าใช้จ่ายร้าน/กำไรสุทธิ/เงินเดือน

## 4. ยอดขายควรเก็บที่ไหน

**ที่เดียว บนเซิร์ฟเวอร์** เหตุผล:

- บอททำงานบนคลาวด์และต้องออนไลน์เสมอ → มันเขียนได้แค่ฐานบนเซิร์ฟเวอร์
- POS ขายตอนเน็ตหลุดได้ → มันต้องมีสำเนาในเครื่องเสมอ แต่สำเนานั้นเป็นแค่ **ที่พักรอส่ง** ไม่ใช่ต้นฉบับ
- ถ้าให้ฐานสองฐานเก็บยอดขายคนละส่วน รายงานทุกหน้าต้องรวมสองแหล่ง และทุกครั้งที่แหล่งหนึ่งส่งไม่ถึง รายงานจะผิดเงียบ ๆ

ห้ามทำสองแบบนี้:
- ❌ เก็บยอดขายในสองฐาน แล้ว sync หากัน (ทาง B)
- ❌ ให้แท็บเล็ตเป็นต้นฉบับยอดขาย — แท็บเล็ตหาย = ประวัติหาย และบอทเขียนเข้าไปไม่ได้

## 5. Sync อย่างไรให้ไม่เพี้ยน

กฎเดียว: **ข้อมูลแต่ละชิ้นมีเจ้าของที่เขียนได้คนเดียว ที่อื่นเป็นสำเนาทางเดียว**

| ข้อมูล | เจ้าของ | ทางไหล |
|---|---|---|
| เมนู สูตร ราคา โปร ช่องทาง พนักงาน | ฐานกลาง (แก้ที่เว็บ) | ฐานกลาง → แท็บเล็ต (ดึงเฉพาะที่เปลี่ยน ด้วย `updated_since`) |
| บิลที่ขายที่ POS | POS สร้าง ฐานกลางเก็บ | แท็บเล็ต → ฐานกลาง ทางเดียว กันซ้ำด้วยคีย์ของบิล ส่งซ้ำได้ไม่เกิดบิลซ้ำ |
| บิลที่ขายที่บอท | บอทสร้าง ฐานกลางเก็บ | บอท → ฐานกลางตรง ๆ (ทำอยู่แล้ว) |
| แก้/ยกเลิกบิล | **ที่ที่สร้างบิลนั้นเท่านั้น** (+ owner) | ทางเดียวกับตอนสร้าง |
| กะ เงินสด ใบปิดกะ | POS สร้าง ฐานกลางเก็บ | แท็บเล็ต → ฐานกลาง ทางเดียว |

ตัวอย่างสิ่งที่พังเมื่อ sync สองทาง (ทุกข้อเกิดได้จริงในทาง B):
- พนักงานยกเลิกบิลในบอทตอนบ่าย การส่งต่อไป POS ล้ม → **บัญชีใน POS ยังนับบิลนั้นเป็นรายได้** ขณะที่บอทบอกว่ายกเลิกแล้ว
- เจ้าของแก้บิลในเว็บ พร้อมกับที่แท็บเล็ตส่งการแก้บิลเดียวกันขึ้นมา → ต้องตัดสินว่าใครชนะ และฝั่งที่แพ้จะเห็นตัวเลขที่ไม่ใช่ของตัวเอง
- แก้สูตรในเว็บตอนเช้า ฝั่งบัญชีดึงสูตรใหม่ช้าไป 10 นาที → บิลช่วงนั้นตัดสต๊อกด้วยสูตรเก่า

## 6. ทางเลือก

### ทาง A — ศูนย์กลางอยู่ที่ LINE bot + เซิร์ฟเวอร์ POS ตัวเล็กเก็บเงินสด (ที่ตกลงไว้ในรอบ 1–3)

```
เว็บ/บอท ──เขียน──▶ Supabase (เมนู · สต๊อก · ยอดขายทุกบิล)
                        ▲ บิล            │ เมนู
แท็บเล็ต POS ───────────┘               ▼
     │ กะ/เงินสด/ใบปิดกะ
     ▼
เซิร์ฟเวอร์ POS (Neon + Render) + หน้ารายงานเงินสด
```

- ✅ ยอดขายชุดเดียว · รื้อฝั่ง LINE bot น้อย · ใช้งานเซิร์ฟเวอร์แผน 5 ต่อได้เกือบทั้งหมด
- ⚠️ ระบบหลังบ้านสองชุด (บัญชี 5 บริการ: Supabase, Cloudflare, Neon, Render, Pages) · สำรองข้อมูลสองที่ · เจ้าของดูรายงานสองที่ (ยอดขาย/กำไรที่เว็บ · เงินสดที่ POS)
- ⚠️ Render ฟรีหลับเมื่อไม่มีคนเรียก 15 นาที ต้องมีตัว ping ปลุก
- ⚠️ ต1 ได้แค่ครึ่งเดียว: POS ถือเรื่องเงินสด แต่กำไร/ต้นทุน/สต๊อกอยู่อีกระบบ

### ทาง B — ข้อเสนอของคุณ: LINE bot ถือสูตร · POS ถือเงิน/บัญชี/บริหาร · ขายได้ทุกที่

```
เว็บ ──สูตร──▶ Supabase ──สูตร──▶ เซิร์ฟเวอร์ POS (บัญชี · สต๊อก · ต้นทุน · ยอดขายทุกบิล)
บอท ──บิล──▶ Supabase ──ส่งต่อบิล──▶        ▲             │
                     ◀──ยอดวันนี้/รายงาน───┘             │
แท็บเล็ต POS ───────────── บิล/กะ/เงินสด ─────────────────┘
```

สิ่งที่ต้องทำเพิ่มถึงจะใช้ได้:
- ฝั่ง LINE bot: `create_order` เลิกตัดสต๊อกเอง · ส่งต่อทุกบิล/การแก้/การยกเลิกไปเซิร์ฟเวอร์ POS พร้อมคิวส่งซ้ำ (เซิร์ฟเวอร์ POS อาจหลับอยู่ และ LINE ต้องตอบเร็ว) · หน้าสต๊อก แดชบอร์ด "ยอดวันนี้" เตือนของใกล้หมด รายงาน 08:00 ต้องไปอ่านจาก POS · กลับคำ ADR-0026, 0029, 0032, 0035 และอื่น ๆ
- ฝั่ง POS: เซิร์ฟเวอร์กลายเป็นระบบบัญชีเต็มรูป · ต้องมีหลังบ้านบนเว็บสำหรับรับของ/นับสต๊อก/รายงาน · ต้องเปิด API ให้ระบบ LINE bot เข้ามาส่งบิล
- ✅ ได้บัญชีที่เข้มที่สุด (ห้ามแก้ · ต้นทุนถัวเฉลี่ยจริง)
- ❌ **ยอดขายอยู่สองฐาน sync สองทาง** — ความเสี่ยงหลักตามข้อ 5
- ❌ รื้อระบบที่ใช้งานจริงแล้วเกือบทั้งระบบ
- ❌ เลขบิลสองชุด (`L260925-014` ของบอท กับเลขของ POS) ต้องรวมกันในรายงาน
- ❌ บอท (ที่พนักงานใช้ทุกวัน) ต้องถามข้ามระบบทุกครั้งที่ดู "ยอดวันนี้"

### ทาง C1 — ฐานเดียว Supabase · POS เป็นเครื่องมือเรื่องเงินและบริหาร (แนะนำ)

```
เว็บ/บอท ──เขียน──▶ Supabase ◀── บิล · กะ · เงินสด · ใบปิดกะ ── แท็บเล็ต POS
                     (ทุกอย่าง)  ── เมนู · พนักงาน · บิลจากบอท ──▶  (หน้าจัดการเงิน/บริหาร)
```

- ข้อมูลทุกชิ้นอยู่ในฐานเดียว ยอดขายจากบอทและ POS อยู่ในตาราง `orders` เดียวกัน
- เพิ่มตาราง กะ/เงินสด/ใบปิดกะ เข้า Supabase (ADR ใหม่ฝั่งนั้น) ตัวเก็บแบบห้ามแก้ใช้ trigger เหมือนที่ POS ทำ
- แท็บเล็ต POS เป็นเครื่องมือเรื่องเงิน: ปิดกะ นับเงิน ใบปิดกะ ขาด/เกิน และหน้ารายงานเงิน (อ่านจากฐานกลาง)
- ถ้าต้องการต้นทุนถัวเฉลี่ยจากราคาซื้อจริง ย้ายวิธีคิดของ POS เข้าไปในฐานกลางได้ (เปลี่ยน ADR-0026 เป็นขั้นแยก ไม่บังคับทำตอนนี้)
- ✅ ต1 ต2 ต3 ต4 ครบ · sync น้อยที่สุด (แท็บเล็ต ↔ ฐานกลาง คู่เดียว) · สำรองที่เดียว · รายงานที่เดียว
- ⚠️ **กลับคำตอบ Q7 (ข) และ Q14 (ค)** ที่คุณเลือกไว้ — เซิร์ฟเวอร์ POS ถูกตัดออก หน้ารายงานเงินสดย้ายไปอ่านฐานกลาง
- ⚠️ **งานเซิร์ฟเวอร์แผน 5 ที่ทำคืนนี้ส่วนใหญ่ไม่ได้ใช้** (ตัวรับข้อมูล ตัวลงทะเบียนเครื่อง ตัวดึงข้อมูล) — ตัวส่งข้อมูลฝั่งแท็บเล็ตยังใช้แนวคิดเดิมได้ ส่วนแผนสำรอง `pg_dump` → R2 จาก 5b ใช้กับ Supabase ได้เลย (ปิดช่องโหว่ "ไม่มีสำรองอัตโนมัติ" ของฝั่งนั้นไปด้วย)
- ⚠️ ทุก endpoint ที่ POS เรียกต้องเบา (CPU 10 ms) งานหนักอยู่ใน RPC ของ Postgres — ตามแบบที่ฝั่งนั้นทำอยู่แล้ว
- ⚠️ ฝั่ง LINE bot ต้องแก้ปานกลาง ผ่านกระบวนการ ADR ของมันเอง (ตามคำตอบ Q13)

### ทาง C2 — รวมเข้าฝั่ง POS (ย้ายบอทและเว็บมาอยู่บนเซิร์ฟเวอร์ POS)

ไม่แนะนำ: ต้องเขียนระบบที่ใช้งานจริงแล้ว 60,000 บรรทัดใหม่บนฐานใหม่ ได้ผลลัพธ์เท่ากับ C1 ในราคาที่แพงกว่ามาก

## 7. ตารางเปรียบเทียบ

| เกณฑ์ | A | B | C1 |
|---|---|---|---|
| ยอดขายชุดเดียว | ✅ | ❌ สองฐาน | ✅ |

## 8. ความเสี่ยงที่มีในทุกทาง

1. **ฐานข้อมูลฟรี 500 MB** — ยอดขาย รายการ การเคลื่อนไหวสต๊อก และ audit_log สะสมไปเรื่อย ๆ **ยังไม่มีใครประเมินว่าจะเต็มเมื่อไหร่** ต้องวัดจากข้อมูลจริงของร้านก่อนเลือก แล้ววางแผนย้ายข้อมูลเก่าออกก่อนถึงราว 70% (ทาง B ก็เจอเพดานเดียวกันที่ Neon)
2. **สำรองข้อมูลต้องกดเอง** ฝั่ง LINE bot ไม่มีสำรองอัตโนมัติ — ทาง C1 ปิดได้ด้วยงานสำรองอัตโนมัติจากแผน 5b
3. **คนบันทึกบิลซ้ำ** เมื่อขายได้สองที่ ระบบแยกไม่ออกว่าบิลสองใบเป็นแก้วเดียวกันหรือลูกค้าสองคน — กันได้ด้วยหน้าจอ (POS แสดงบิลจากบอทของวันนั้น บอทแสดงบิลจาก POS) และกติกาของร้าน ไม่ใช่ด้วยโค้ด
4. **เมนูในแท็บเล็ตเก่ากว่าของจริง** ตอนออฟไลน์ → ติดธงยอดไม่ตรง (Q17 จัดการแล้ว: ใช้ราคาที่เก็บเงินจริง + ส่งฉบับเมนูไปด้วย)
5. **โค้ดคิดราคาใช้ร่วมข้ามสอง repo** ต้องมีเลขรุ่นและเทสต์เทียบตัวเลข (Q8)
6. **โควตา 100,000 คำขอ/วันใช้ร่วมกับบอท** — POS เพิ่มราวไม่กี่ร้อยคำขอ/วัน ไม่น่ากังวล

## 9. คำแนะนำ

**ทาง C1** เพราะเป็นทางเดียวที่ได้ครบทั้งสี่ข้อ: POS เป็นเครื่องมือเรื่องเงินและบริหาร (ต1) ขายได้ทุกที่ (ต2) ตัวเลขชุดเดียว (ต3) และร้านสองคนดูแลระบบหลังบ้านชุดเดียว (ต4)

สิ่งที่ต้องยอมรับถ้าเลือก C1:
- กลับคำตอบ Q7 (ข) และ Q14 (ค)
- เซิร์ฟเวอร์ที่ทำคืนนี้ส่วนใหญ่ไม่ได้ใช้ — ผมเคยแนะนำทางนี้ไว้ในรอบ 2 (Q7 ก) และงานที่ทำไปแล้วไม่ควรเป็นเหตุผลให้เลือกทางที่แย่กว่า
- ต้องแก้ฝั่ง LINE bot ปานกลาง ผ่าน ADR ของมันเอง

C1 ต่างจากที่ตกลงไว้ในรอบ 1–3 เพียงสามจุด: ตัดเซิร์ฟเวอร์ POS · กะ/เงินสด/ใบปิดกะไปอยู่ฐานกลาง · ยอมให้ขายได้ทั้ง POS และบอทตามปกติ (Q3 เดิมจำกัดไว้)

## 10. ยังต้องตัดสินหลังเลือกทาง

- "บัญชี/เรื่องเงิน/บริหารร้าน" รวมอะไรบ้าง — แค่เงินสด/กะ/ใบปิดกะ · หรือรวมต้นทุนจริง · ค่าใช้จ่ายร้าน · กำไรสุทธิ · เงินเดือน
- จะเปลี่ยนวิธีคิดต้นทุนฝั่งกลางเป็นถัวเฉลี่ยจากราคาซื้อจริงไหม และเมื่อไหร่
- กติกากันบิลซ้ำเมื่อขายได้สองที่
- ขนาดฐานข้อมูลจริงและแผนย้ายข้อมูลเก่า

## 11. ถ้ารวมฐาน (ทาง C1) ต้องแก้อะไรบ้าง

**คำตอบสั้น: ตัวการรวมฐานเองไม่ใช่งานใหญ่ และรวมแล้วงานทั้งหมดน้อยกว่าทาง A** งานก้อนใหญ่จริงคือการทำให้ POS "พูดภาษาเมนูและราคา" ของระบบ LINE bot ซึ่ง **ต้องทำอยู่แล้วในทุกทาง** (A, B, C1) ทันทีที่ระบบนั้นเป็นเจ้าของเมนู

"รวมฐาน" หมายถึงรวม **ฐานฝั่งเซิร์ฟเวอร์** เท่านั้น — SQLite ในแท็บเล็ตยังอยู่ เพราะการขายตอนเน็ตหลุดต้องมีมันเสมอ

### 11.1 งานที่ต้องทำไม่ว่าเลือกทางไหน (ก้อนใหญ่)

| งาน | รายละเอียด |
|---|---|
| ปรับตารางเมนูในแท็บเล็ตให้เหมือนฝั่งนั้น | POS: `product` · `product_variant` · `size` · `sweetness_level` · `price` · `channel` / ฝั่งนั้น: `menu_items` · `menu_variants` (เมนู × ขนาด × ความหวาน ราคากรอกเอง) · `menu_options` · `sales_channels` (บวก % / บวกบาท / ปัดขึ้น / ค่าธรรมเนียม) · `payment_methods` · `promotions` — แนะนำให้ตารางในแท็บเล็ต **ลอกโครงของฝั่งนั้นมาตรง ๆ** แทนการแปลไปมา ซึ่งจะเสียข้อมูลระหว่างทาง |
| เปลี่ยนตัวคิดราคา | เลิกใช้ `packages/domain/src/pricing.ts` ของ POS ใช้โค้ดคิดราคาของฝั่งนั้น (Q8) |
| หน้าขาย | เพิ่มการเลือก นมโอ๊ต / เกรดผง · โปรโมชั่นอัตโนมัติ + ปุ่ม "ไม่ใช้โปร" · ราคาตามช่องทาง (`SellScreen` · `ItemDialog` · `CartPanel` · `DiscountDialog`) |
| ที่มาของเมนู | เลิกนำเข้าจาก Excel (แผน 1) → ดึงจาก `GET /v1/catalog` |
| แปลงบิลตอนส่ง | สตางค์จำนวนเต็ม → บาททศนิยม 2 ตำแหน่ง (×100 แปลงตรง ไม่มีปัดเศษ) · เลขบิล POS → `external_ref` · รายการ → `order_items` |
| พนักงาน | ดึงรายชื่อ+บทบาทจากฝั่งนั้น ตั้ง PIN ที่แท็บเล็ต (Q9) |
| ซ่อนงานสต๊อก | หน้ารับของ ต้มเบส ปรับยอด นับสต๊อก (Q11) |

### 11.2 งานที่เพิ่มขึ้นเพราะรวมฐาน (ก้อนเล็ก–กลาง · อยู่ฝั่ง LINE bot)

- ตารางใหม่ 4 ตาราง: กะ · เงินเข้า-ออกลิ้นชัก · การนับเงิน · ใบปิดกะ + trigger ห้ามแก้ห้ามลบ (ลอกแบบจาก POS)
- RPC เปิดกะ / บันทึกเงินเข้า-ออก / ปิดกะพร้อมใบปิดกะ + endpoint ใต้ `/api/v1` ที่เบาพอกับ CPU 10 ms
- หน้ารายงานเงินสด/ใบปิดกะ/ขาด-เกิน (Q14) — จะอยู่ในแอป POS หรือบนเว็บฝั่งนั้นก็ได้ อ่านจากฐานเดียวกัน
- ทั้งหมดผ่าน ADR ใหม่ฝั่งนั้น ทำในเซสชันของโปรเจกต์นั้น (Q13)

### 11.3 งานที่หายไปเพราะรวมฐาน

- เซิร์ฟเวอร์ POS ทั้งตัว (NestJS + Neon) — ยังอยู่แค่บนสาขา ไม่ได้ merge เข้า main จึงไม่ต้องรื้ออะไร
- แผนขึ้นระบบ 5b ส่วน Render/Neon/ตัว ping ปลุก
- แท็บเล็ตคุยกับเซิร์ฟเวอร์ **สองตัว** (ทาง A) → เหลือตัวเดียว
- การสำรองข้อมูลที่สอง — และงานสำรองอัตโนมัติของ 5b ย้ายไปใช้กับ Supabase ได้ ปิดช่องโหว่ "สำรองต้องกดเอง" ของฝั่งนั้นด้วย

### 11.4 หลุมที่เจอตอนเทียบโค้ดจริง

1. **ฝั่งนั้นคิดเงินเป็นทศนิยมบาทแล้วปัด 2 ตำแหน่ง** (`round2` ใน `packages/shared/src/money.ts`) ส่วน POS บังคับสตางค์จำนวนเต็มทุกจุด — ตาม Q8 ให้ใช้กติกาของฝั่งนั้นเป็นตัวจริง แล้วแปลงผลลัพธ์เป็นสตางค์ที่ขอบ ต้องมีเทสต์เทียบตัวเลขข้ามสองระบบกับกรณีที่ทศนิยมมักพลาด (เช่นส่วนลดเปอร์เซ็นต์)
2. **โซ่แฮชของ event บิลไม่มีที่อยู่ในฝั่งนั้น** — เก็บไว้ในแท็บเล็ต (+ สำรอง) หรือเพิ่มตารางฝั่งนั้น ต้องตัดสินภายหลัง ขึ้นกับว่าให้น้ำหนักการตรวจย้อนแค่ไหน
3. **กะที่ข้ามเที่ยงคืน** — API ฝั่งนั้นยอมให้ยกเลิกบิลจาก POS ได้เฉพาะ "วันขาย = วันนี้" ส่วน POS ยอมให้ยกเลิกได้ทั้งกะ บิลก่อนเที่ยงคืนในกะเดียวกันจะยกเลิกไม่ได้หลังเที่ยงคืน ต้องตกลงกติกาให้ตรงกัน
4. **ข่าวดี:** POS รับเงินวิธีเดียวต่อบิลอยู่แล้ว ตรงกับฝั่งนั้นที่เก็บวิธีชำระช่องเดียว ไม่ต้องแก้

### 11.5 ขนาดงานโดยประมาณ

| ฝั่ง | งาน | ขนาด |
|---|---|---|
| LINE bot | ADR + migration 4 ตาราง + RPC + endpoint + ส่งรายชื่อพนักงาน + ช่องฉบับเมนู + บิลจาก POS ห้ามแก้บนเว็บ + ดึงบิลเงินสดจากบอทตอนปิดกะ | 1 แผน |
| POS | เมนูและราคาตามแบบฝั่งนั้น + หน้าขาย (โปร/ตัวเลือก) | 1 แผน (ก้อนใหญ่สุด) |
| POS | ตัวส่งบิล/กะ/เงินสดไปฝั่งนั้น (ใช้แนวคิดตัวส่งจากแผน 5 Task 9) + ดึงเมนู | 1 แผน |
| POS | หน้ารายงานเงินสด + ซ่อนงานสต๊อก + ลบของที่ไม่ใช้ | 1 แผนเล็ก |

เทียบกับทาง A: ทาง A ต้องทำสามแผนฝั่ง POS เหมือนกัน **บวก** ทำเซิร์ฟเวอร์ POS ให้จบ ขึ้นระบบ และดูแลมันต่อไป
