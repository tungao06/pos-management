### ผลที่ตามมาจากรอบที่ 1

- **ไม่ใช้ POS สำเร็จรูประหว่างทาง** — ไม่มีเดดไลน์ จึงสร้างเองได้เต็มที่
- **อุปกรณ์ต่อพ่วงทั้งหมดเลื่อนออกไป** → ระยะแรกไม่ต้องตัดสินใจเรื่องเครื่องพิมพ์ ลิ้นชัก หรือ OS ของแท็บเล็ต
- **"ความถูกต้อง" เป็นข้อกำหนดหลัก** → ตรรกะเรื่องเงินและสต็อกต้องอยู่ในที่เดียว มีเทสต์แบบ property-based และมีการตรวจ invariant อัตโนมัติ
- **ร้าน 2 คน** → ระบบสิทธิ์ไม่ต้องซับซ้อน แต่**ทุกการกระทำยังต้องระบุตัวคนทำ** เพื่อให้ตรวจสอบย้อนหลังได้

### ผลที่ตามมาจากรอบที่ 2

- **แบบร่าง modifier ที่มี `factor` ตัวเลข (จาก 05-โครงสร้างข้อมูลฯ) ถูกแทนที่** ด้วย recipe ต่อ (variant, sweetness) เพราะสูตรจริงไม่ได้ scale เชิงเส้นตัวเดียว
- **มีชั้น "prepared item"** เพิ่มจากที่เคยออกแบบ → หน้าจอทำเบส + สต็อกเบส + วันหมดอายุ
- **เงื่อนไขโฮสติ้งฟรีกำหนดพฤติกรรม sync** (ไม่ sync ตอนปิดร้าน) → ต้องอยู่ใน spec
- NestJS แทน Hono → ใช้ `@nestjs/*` + Drizzle (ไม่ใช่ TypeORM/Prisma) เพื่อแชร์ schema กับฝั่งเครื่อง

### ผลที่ตามมาจากรอบที่ 3

- **เซิร์ฟเวอร์กลายเป็นต้นทางของออเดอร์ได้** (LINE) → กฎ "ธุรกรรมไหลขึ้นอย่างเดียว" เปลี่ยนเป็น "ธุรกรรมมี `origin` (device/server) และ **ทุกการเปลี่ยนสถานะยังเกิดที่เครื่องขาย**" · แท็บเล็ตต้อง pull ออเดอร์ขาเข้าขณะเปิดกะ

- spec ต้องเพิ่ม: ตาราง `customer`, ฟิลด์ต้นทาง/สถานะออเดอร์ LINE, โมดูล LINE ใน API, โหมดลูกค้าใน PWA
