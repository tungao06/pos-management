# โครงสร้างข้อมูลและสถาปัตยกรรม

บริบทที่สมมติ: ร้านเดียว, 1–3 แท็บเล็ต, เมนูชาไทย/ชาเขียว/มัทฉะ, น่าจะยังไม่ถึงเกณฑ์ VAT 1.8 ล้าน, นักพัฒนาคนเดียว

---

## 1. เมนูและตัวเลือก — การตัดสินใจที่สำคัญที่สุด

### 1.1 การแบ่ง 3 ทาง

Square Catalog API เป็นตัวอย่างที่มีเอกสารดีที่สุดและกฎของเขาถูกต้อง: **variant** = สิ่งที่มี SKU และราคาของตัวเอง และเราจะนับสต็อกมัน · **modifier** = สิ่งที่บวกเพิ่มจากราคาฐานและใช้ได้ข้าม variant · **ราคาอยู่ที่ variant ไม่ใช่ที่ product**

| แกน | โมเดลเป็น | เหตุผล |
|---|---|---|
| **ขนาด S/M/L** | **variant** | คนละราคา คนละ SKU แก้ว ปริมาณในสูตรต่างกัน |
| **ร้อน / เย็น / ปั่น** | **variant** | สูตรต่างกันจริง (ปั่นใช้น้ำแข็งเป็นเนื้อ ไม่ใส่น้ำ) คนละแก้ว บางทีคนละราคา บางทีขายไม่ได้ |
| **ความหวาน 0/25/50/75/100%** | **modifier ราคา 0 + มี `factor` เป็นตัวเลข** | ไม่กระทบราคา แต่ต้องคูณปริมาณไซรัปในสูตร |
| **ระดับน้ำแข็ง ไม่ใส่/น้อย/ปกติ/เยอะ** | **modifier ราคา 0 + `factor`** | เหมือนกัน |
| **ท็อปปิ้ง (ไข่มุก เจลลี่ พุดดิ้ง เฉาก๊วย)** | **modifier มีราคา + เลือกจำนวนได้ + มีสูตรของตัวเอง** | บวกราคา + ดึงวัตถุดิบของตัวเอง |
| **ฐานนม (สด/โอ๊ต/อัลมอนด์/ข้นจืด)** | **modifier มีราคา + แทนที่วัตถุดิบ** | สลับวัตถุดิบ ไม่ใช่เพิ่ม |
| **ช็อตพิเศษ / เพิ่มมัทฉะ** | **modifier มีราคา + เพิ่มวัตถุดิบ** | |

### ⚠️ ความผิดพลาด 2 ด้านที่สมมาตรกัน
- **แตกทุก combination เป็นสินค้า** → 3 ขนาด × 3 อุณหภูมิ × 5 ความหวาน × 4 น้ำแข็ง = **180 SKU ก่อนนับท็อปปิ้ง**
- **ทำขนาดเป็น modifier** → ตัดแก้วตามขนาดไม่ได้ ทำสูตรต่อขนาดไม่ได้ ตั้งราคาท็อปปิ้งต่อขนาดไม่ได้

### ⭐ `factor` คือจุดที่ POS สำเร็จรูปทำไม่ได้
Loyverse ระบุในเอกสารเองว่า **"Modifiers do not have stock tracking"** → ไข่มุก เจลลี่ ช็อตพิเศษที่ขายเป็น modifier สร้างรายได้แต่**ไม่เคยตัดวัตถุดิบเลย** และหวาน 50% กับ 100% ตัดไซรัปเท่ากัน
ถ้าเราเก็บ `factor` เป็นตัวเลข ระบบจะรู้ว่า "หวาน 50%" = ไซรัป × 0.5 จริงๆ — **ทำให้ความหวานเป็นข้อมูลที่เครื่องอ่านได้ ไม่ใช่ข้อความที่พิมพ์ลงกระดาษเฉยๆ**

### 1.2 Schema แคตตาล็อก

```sql
category(id, code, name_th, name_en, sort, is_active)

product(id, code, name_th, name_en, category_id,
        base_price_minor,            -- เป็น template เท่านั้น ราคาจริงอยู่ที่ variant
        tax_group_id, station,       -- 'BAR' | 'KITCHEN'
        image_url, sort, is_active, archived_at)

-- แกนตัวเลือก (ขนาด, อุณหภูมิ)
option_type(id, code, name_th, sort)                    -- 'SIZE', 'TEMP'
option_value(id, option_type_id, code, name_th, sort,
             recipe_scale numeric)                       -- S=0.75 M=1.0 L=1.35
product_option(product_id, option_type_id, sort)

variant(id, product_id, sku,
        option_signature,            -- 'SIZE:M|TEMP:ICED' แบบ canonical
        price_minor,                 -- ⭐ ราคาสัมบูรณ์ ตัดสินตอนบันทึกใน admin
        cup_ingredient_id,           -- แก้ว SKU ไหนที่ตัด
        is_default, is_active,
        UNIQUE(product_id, option_signature))
variant_option_value(variant_id, option_value_id,
        UNIQUE(variant_id, option_type_id))
```

⭐ **เก็บราคา variant เป็นค่าสัมบูรณ์ ไม่ใช่ส่วนต่างที่คำนวณตอนอ่าน**
คำนวณจาก template ส่วนต่างในหน้า admin แล้ว**แช่แข็งไว้** ถ้าคำนวณตอนอ่าน การแก้ราคาฐานทีเดียวจะเขียนราคาทุก variant ใหม่เงียบๆ และตอบคำถาม "ทำไมบิลนี้ 55 บาท" ไม่ได้อีกเลย

```sql
modifier_group(id, code, name_th,
        selection_type,              -- 'SINGLE' | 'MULTI'
        min_select, max_select,
        allow_quantity bool, max_total_quantity,
        price_behavior,              -- 'SUM' | 'MAX' | 'FREE_N_THEN_SUM'
        free_quantity,               -- สำหรับ "ท็อปปิ้ง 2 อย่างแรกฟรี แล้วชิ้นละ 10"
        is_recipe_affecting bool,
        sort, is_active)

modifier_option(id, group_id, code, name_th,
        price_delta_minor,
        factor numeric,              -- ⭐ 1.00 / 0.75 / 0.50 / 0.25 / 0.00
        is_default, sort, is_active)

-- ผูก group เข้ากับสินค้า หรือเข้ากับทั้งหมวด (ประหยัดเวลากรอกมาก)
product_modifier_group(product_id, group_id, sort,
        override_min, override_max, is_required)
category_modifier_group(category_id, group_id, sort, ...)

-- ไข่มุก +5 บนขนาด S แต่ +10 บนขนาด L
modifier_option_price_override(modifier_option_id, option_value_id, price_delta_minor)
```

คำศัพท์ `min_select` / `max_select` / `allow_quantity` / `is_default` ลอกมาจาก Square ตรงๆ (`min_selected_modifiers`, `max_selected_modifiers`, `allow_quantities`, `on_by_default`) — ผ่านการใช้งานจริงมาแล้ว คุ้มที่จะลอกทั้งดุ้น

### 1.3 การคำนวณราคา — ฟังก์ชันบริสุทธิ์ ที่เดียว เทสต์หนัก

```
ราคา variant     = variant.price_minor
mod_delta(m)     = override_ตามขนาด(m) ?? m.price_delta_minor
ยอดต่อกลุ่ม(g)    SUM     → Σ mod_delta(m) × qty(m)
                 MAX     → max(mod_delta(m))
                 FREE_N  → Σ เฉพาะที่เกิน free_quantity
ราคาต่อหน่วย     = ราคา variant + Σ ยอดต่อกลุ่ม(g)
ยอดก่อนลด       = ราคาต่อหน่วย × จำนวนในบรรทัด
ส่วนลดบรรทัด     = ส่วนลดระดับบรรทัด + ส่วนแบ่งจากส่วนลดระดับบิล
ยอดสุทธิบรรทัด   = ยอดก่อนลด − ส่วนลดบรรทัด
ภาษีบรรทัด      = tax_group คิดจากยอดสุทธิ (inclusive หรือ additive)
ยอดรวมบิล       = Σ ยอดสุทธิ + ค่าบริการ + ภาษี + ปัดเศษ
```

**กฎเหล็ก:**
- ⭐ **ใช้จำนวนเต็มหน่วยสตางค์ทุกที่ ห้ามใช้ float** ส่วนลด % บนราคาบาทจะสร้างเศษสตางค์ **เก็บความละเอียดไว้แล้วปัดครั้งเดียว**
- **ลดก่อนคิดภาษี** (เป็นมาตรฐานสากล และเป็นลำดับเดียวที่ make sense กับราคารวม VAT)
- ⭐ **ส่วนลดระดับบิลต้องกระจายกลับลงบรรทัด** ตามสัดส่วนยอดสุทธิ ใช้ **largest-remainder** เพื่อให้ Σ บรรทัด = หัวบิลเป๊ะ ถ้าข้ามขั้นตอนนี้ margin ต่อรายการเพี้ยนและภาษีบวกไม่ลง — เป็นบั๊กคลาสสิกที่มีเอกสารบันทึกไว้
- **เลือกปัดเศษระดับบรรทัด หรือ ระดับบิล อย่างใดอย่างหนึ่ง ห้ามผสม** — ร้านไทยราคารวมภาษี แนะนำ**ปัดระดับบิล ครึ่งขึ้น ถึงสตางค์** แล้วมี field `rounding_minor` แยกบนบิลถ้าจะปัดเป็นบาทถ้วน
- ⭐ **โหมด "ไม่มีภาษี" ต้องเป็นพลเมืองชั้นหนึ่ง ไม่ใช่ของแถม** ร้านต่ำกว่า 1.8 ล้านไม่ได้จด VAT และออกใบกำกับภาษีไม่ได้ **สร้างโหมดไม่มีภาษีก่อน แล้วค่อยสร้างอัตราภาษี**

### 1.4 ราคาต่อช่องทางขาย

รูปแบบมาตรฐานคือ `ItemVariationLocationOverrides` ของ Square (override ราคา/ความพร้อมขายต่อสาขาแบบเบาบาง) — เราขยาย "สาขา" เป็น **"ช่องทาง"**

```sql
price_channel(id, code, name,             -- DINE_IN, TAKEAWAY, GRAB, LINEMAN, SHOPEE, ROBINHOOD
        markup_mode,                       -- 'NONE' | 'PERCENT' | 'PRICE_LIST'
        markup_bp int,                     -- 2500 = +25%
        rounding_rule,                     -- 'NONE' | 'UP_TO_1' | 'UP_TO_5'
        commission_bp int,                 -- ค่า GP สำหรับรายงานรายได้สุทธิ
        tax_mode, is_active)

price_list(id, channel_id, name, effective_from, effective_to, is_active)
price_list_entry(price_list_id,
        variant_id NULL, modifier_option_id NULL,   -- ตั้งได้อย่างใดอย่างหนึ่ง
        price_minor)

channel_availability(channel_id, product_id | variant_id, is_available)
```

**ลำดับการหาราคา:** `price_list_entry` ที่ระบุชัด → `markup_bp` คูณราคาฐานแล้วปัดด้วย `rounding_rule` → ราคาฐาน

- `rounding_rule` มีเพราะเมนูบนแอปต้องขึ้น **65** ไม่ใช่ **63.25**
- ⭐ `commission_bp` มีเพราะ**ความผิดพลาดด้านราคาที่เจ้าของร้านทำบ่อยที่สุด**: GrabFood ~35% และ LINE MAN ~33% ของตลาดไทย ค่า GP สูงจนกระทรวงพาณิชย์เคยกดดันให้เพดาน 25% ในปี 2021 — **ที่ GP 30% เครื่องดื่ม 65 บาทบนแอปเหลือ 45.50 บาท ซึ่งน้อยกว่าขายหน้าร้าน 55 บาท** → รายงานต้องแสดง **รายได้สุทธิหลังหักคอมมิชชั่นต่อช่องทาง** ไม่งั้นเจ้าของจะ "โต" จนขาดทุน
- (Robinhood เคยไม่คิดค่าคอมมิชชั่น → เก็บเป็น field ต่อช่องทาง อย่า hardcode)

### 1.5 การขายพ่วง (upsell) และโปรโมชั่น — แยกจากส่วนลด

```sql
upsell_rule(id, trigger_kind,          -- 'PRODUCT'|'CATEGORY'|'CART_TOTAL'|'MODIFIER'
        trigger_ref_id, threshold_minor,
        suggest_kind,                  -- 'MODIFIER_OPTION' | 'PRODUCT'
        suggest_ref_id, bundle_price_minor,
        channel_id NULL, priority, max_per_order, active_from, active_to)

upsell_event(id, order_id, order_line_id, rule_id,
        outcome,                       -- 'SHOWN' | 'ACCEPTED' | 'DISMISSED'
        occurred_at)

promotion(id, code, kind,              -- 'BUY_X_GET_Y' | 'BUNDLE' | 'HAPPY_HOUR' | 'NTH_FREE'
        rule_json, stackable, priority, channel_scope, valid_from, valid_to,
        day_of_week_mask, time_from, time_to)
```

โปรโมชั่นทำงานเป็น pass ที่ประเมินตะกร้าแล้วสร้างแถว `order_discount` ที่ติด `source_promotion_id`
⭐ **ถ้าไม่มี `upsell_event` การขายพ่วงจะเป็นแค่ของประดับ** — เราจะไม่มีวันบอกเจ้าของได้ว่า "อัพไซส์ +10 มั้ยคะ" คุ้มกับความรำคาญหรือเปล่า

## 2. สต็อกตามสูตร (BOM)

### 2.1 หน่วย

ทำทุกวัตถุดิบให้อยู่บน **หน่วยฐานเดียว** (g / ml / ea) แล้วผูกทุกขนาดบรรจุจากซัพพลายเออร์เข้ากับหน่วยฐาน (รูปแบบเดียวกับ Restaurant365, Supy) — ซื้อมัทฉะถุง 1 กก. ใช้ครั้งละ 3 ก.

```sql
ingredient(id, code, name_th, base_unit,       -- 'g' | 'ml' | 'ea'
        category,                              -- POWDER, DAIRY, SYRUP, TOPPING, PACKAGING
        is_tracked bool,                       -- ⭐ ใช้บางส่วนได้เป็นสถานะปกติ
        cost_per_base_minor,                   -- ถัวเฉลี่ยเคลื่อนที่
        reorder_point_base, par_level_base,
        shelf_life_days, default_supplier_id, is_active)

purchase_unit(id, ingredient_id, name,         -- 'ถุง 1 กก.', 'ลัง 12 กล่อง'
        factor_to_base numeric,                -- 1000
        is_default_purchase, is_default_count, barcode)
```

⭐ **เก็บปริมาณเป็นจำนวนเต็มหน่วยพันส่วน (`qty_milli`: มัทฉะ 0.5 ก. = 500)** — SQLite ไม่มี DECIMAL และ float สะสมความคลาดเคลื่อนหลังตัดสต็อกหลายหมื่นครั้ง (ฝั่งเซิร์ฟเวอร์ใช้ `DECIMAL(16,4)` ได้)

**2 ความสะดวกที่ตัดสินว่าฟีเจอร์นี้จะถูกใช้จริงหรือไม่:**
- **`is_default_count`** — ไม่มีใครนับมัทฉะ 3,420 กรัม เขานับ **"3.5 ถุง"** ต้องให้กรอกเป็นหน่วยซื้อทศนิยมแล้วแปลงให้
- **`is_tracked`** — น้ำ น้ำแข็ง หลอด ทิชชู่ ต้องปิดการติดตามได้โดยไม่พังระบบสูตร

### 2.2 สูตรและสูตรย่อย

```sql
recipe(id, scope,                     -- 'VARIANT'|'PRODUCT'|'MODIFIER_OPTION'|'SUBRECIPE'
        ref_id, version int, effective_from, effective_to, is_active,
        yield_qty_base, yield_unit,   -- เฉพาะสูตรย่อย
        batch_note)

recipe_line(id, recipe_id, component_kind,     -- 'INGREDIENT' | 'SUBRECIPE'
        component_id, qty_base numeric,
        scales_with,                  -- 'NONE'|'SIZE'|'SWEETNESS'|'ICE'|'SHOT'
        waste_pct_bp int,             -- เผื่อหก/ตัดทิ้งของบรรทัดนี้
        substitutable_group,          -- ให้นมโอ๊ตแทนนมสดได้
        is_optional)
```

⭐ **สูตรย่อยจำเป็นสำหรับร้านชา** เพราะสิ่งที่ร้านทำจริงคือ **ต้มหัวเชื้อ**:
ชาไทย 100 ก. + น้ำ 3,000 มล. ต้ม → ได้หัวเชื้อ **2,600 มล.** (ระเหย/ดูดซับหายไป) → ต้นทุนต่อ มล. = ต้นทุนวัตถุดิบรวม ÷ 2,600 → แต่ละแก้วดึงหัวเชื้อ 120 มล.
"yield percentage" คือคำศัพท์อุตสาหกรรมสำหรับเรื่องนี้พอดี = สัดส่วนของที่ขายได้ต่อของที่ใช้ไป

### 2.3 ลำดับการตัดสต็อก

⭐ **ตัดตอน "ทำเสร็จ" (fulfillment) ไม่ใช่ตอนใส่ตะกร้าและไม่ใช่ตอนจ่ายเงิน** — ข้อนี้คือสิ่งที่ทำให้การยกเลิกบิลถูกต้อง

```
สำหรับแต่ละ order_line:
  1. หาสูตร:        recipe(VARIANT, variant_id) ?? recipe(PRODUCT, product_id)
  2. คูณตามขนาด:     บรรทัดที่ scales_with='SIZE' → qty ×= option_value(SIZE).recipe_scale
                    (ถ้ามีสูตรเฉพาะ variant ให้ใช้สูตรนั้นแทน)
  3. ตัดแก้ว:        ตัด 1 ea ของ variant.cup_ingredient_id  (scales_with='NONE')
  4. คูณตาม modifier: สำหรับ modifier ที่ is_recipe_affecting
                       บรรทัดที่ scales_with ตรงกับ group.code → qty ×= modifier.factor
                       (หวาน 50% → ไซรัป ×0.5 · น้ำแข็ง 'น้อย' → น้ำแข็ง ×0.6)
  5. สูตรของ modifier: ท็อปปิ้งที่มีสูตรของตัวเอง → บวกบรรทัดของมัน × จำนวนที่สั่ง
  6. การแทนที่:      นมโอ๊ตแทนบรรทัดในกลุ่ม substitutable_group='DAIRY'
  7. เผื่อสูญเสีย:    qty ×= (1 + waste_pct_bp / 10000)
  8. กระจายสูตรย่อยแบบ recursive: qty_ของ_component = qty × (input / yield)
  9. คูณทั้งหมดด้วย order_line.qty
 10. เขียน stock_movement + snapshot cogs_minor ลงบรรทัด
```

**การคูณตามขนาด:** ใช้ **สูตรฐาน + ตัวคูณ `recipe_scale`** เป็นหลัก และให้สูตรเฉพาะ variant override ได้
สูตรแยกทุก variant แม่นกว่าแต่ทำให้ข้อมูลที่ต้องกรอกคูณด้วย ขนาด×อุณหภูมิ · ตัวคูณล้วนๆ ก็ผิดสำหรับแก้วและน้ำแข็งซึ่งไม่ได้โตเป็นเส้นตรง → **จึงใช้แบบผสม**

### 2.4 บัญชีแยกประเภทการเคลื่อนไหว

```sql
stock_movement(id UUID, ingredient_id, location_id,
        qty_base_delta,                        -- มีเครื่องหมาย; ลบ = ใช้ไป
        movement_type,                          -- PURCHASE | SALE | WASTE | COUNT_ADJUST
                                                -- | PRODUCTION_IN | PRODUCTION_OUT
                                                -- | TRANSFER | VOID_REVERSAL | OPENING
        unit_cost_minor, total_cost_minor,
        ref_type, ref_id,                       -- ORDER_LINE / PURCHASE / COUNT / WASTE
        occurred_at, business_date,
        device_id, user_id, created_at,
        idempotency_key UNIQUE)

ingredient_stock(ingredient_id, location_id, qty_base, last_movement_id, updated_at)
```

⭐ **append-only** — ยอดคงเหลือเป็นแคชที่อัปเดตใน transaction เดียวกับการ insert movement และคำนวณใหม่จาก `SUM(qty_base_delta)` ได้เสมอ
🚫 **ห้าม `UPDATE qty = qty - n` เด็ดขาด** — เป็นทั้ง lost-update bug ข้ามเครื่อง และทำให้อธิบายที่มาของตัวเลขไม่ได้ตลอดกาล

**⭐ การยกเลิกบิลมี 2 กรณีทางธุรกิจ:**
- **ยกเลิกก่อนชงเสร็จ** → เขียน `VOID_REVERSAL` คืนวัตถุดิบ
- **ยกเลิกหลังชงแล้ว** → วัตถุดิบหายจริง → เขียน `WASTE` เหตุผล `REMAKE` หรือ `VOID_AFTER_MAKE`
ถามพนักงาน หรืออนุมานจาก `fulfillment_status` — **ระบบที่ reverse ทุกกรณีจะสร้างสต็อกผีสะสมขึ้นเรื่อยๆ**

**การคิดต้นทุน:** ใช้ **ถัวเฉลี่ยเคลื่อนที่ (moving weighted average)** ต่อวัตถุดิบ (FIFO layer แม่นกว่าแต่โค้ดเพิ่มราว 3 เท่า ร้านเล็กไม่รู้สึกถึงความต่าง) และ **snapshot `cost_per_base_minor` ลง movement ตอนเขียน** เพื่อไม่ให้ราคาซัพพลายเออร์ที่เปลี่ยนทีหลังมาเขียน margin ของเดือนที่แล้วใหม่

### 2.5 การนับสต็อก ของเสีย และการแจ้งเตือน

```sql
stock_count(id, location_id, type,      -- 'FULL' | 'PARTIAL'
        started_at, closed_at, user_id, status)
stock_count_line(count_id, ingredient_id,
        expected_base,                   -- แช่แข็งตอนเริ่มนับ
        counted_qty, counted_unit_id,    -- นับเป็นหน่วยซื้อ
        counted_base, variance_base, variance_cost_minor, note)

waste_log(id, ingredient_id NULL, product_id NULL, variant_id NULL,
        qty_base, reason_code,           -- SPILL|EXPIRED|REMAKE|TRAINING|STAFF|QC|CLOSING_DUMP
        cost_minor, user_id, shift_id, occurred_at, photo_url, note)
```

การปิดรอบนับจะสร้าง `COUNT_ADJUST` movement เท่ากับ `นับได้ − ที่ควรมี` — **ห้ามเขียนทับตัวเลขปริมาณ**

**⭐ จุดสั่งซื้อควรคำนวณ ไม่ใช่ให้กรอก:**
```
ใช้เฉลี่ยต่อวัน = Σ|SALE movements| ย้อนหลัง 21 วัน ÷ 21
จุดสั่งซื้อ    = ใช้เฉลี่ยต่อวัน × lead_time_days × safety_factor(1.3)
```
ให้เจ้าของแก้ทับได้ แต่ต้องมีค่าเริ่มต้น — **การให้กรอกจุดสั่งซื้อ 60 รายการเองคือการฆ่าฟีเจอร์นั้นทิ้ง**

**⭐ รายงานส่วนต่าง — ของจริงที่ต้องส่งมอบ:**
```
ทฤษฎีควรใช้ = Σ movement ประเภท SALE ในช่วงนั้น
ใช้จริง     = ยอดยกมา + ซื้อเข้า − ยอดนับปลายงวด
ส่วนต่าง    = ใช้จริง − ทฤษฎี      (× ต้นทุน = กี่บาทที่หายไป)
```

### 2.6 ⚠️ ความจริงที่ต้องยอมรับ — ส่วนใหญ่มันไม่รอดจากหน้างาน

**สิ่งที่ร้านเล็กทำจริง:** ติดตามแค่ "6 อย่างใหญ่" — ผงมัทฉะ ใบชา นม ไซรัป ไข่มุก แก้ว+ฝา — และไม่สนใจน้ำ น้ำแข็ง น้ำตาลที่รินมือ หลอด ทิชชู่ · **นับสัปดาห์ละครั้ง เป็นถุง ไม่ใช่เป็นกรัม**

**จุดที่มันพัง:**
1. ⭐ **การรินมือแกว่ง ±20% ทุกแก้ว** — "หวาน 50%" ของบาริสต้าคนละคนไม่เท่ากัน ตัวเลขทฤษฎีกับจริงจะห่างกันภายในไม่กี่วัน และพอเจ้าของเห็นว่าตัวเลขผิด **เขาจะเลิกเชื่อทั้งโมดูล** (ที่ตวง/ปั๊มช่วยลดได้ แต่ไม่มีอะไรกำจัดได้)
2. **ไม่มีใครบันทึกของเสียตอนคิวยาว** — แก้วที่หกบ่าย 3 ถูกบันทึกตอน 3 ทุ่ม หรือไม่ถูกบันทึกเลย
3. **ยอดหัวเชื้อแกว่ง** — ต้มคนละรอบ ระเหยไม่เท่ากันตามวัน "2,600 มล." คือการเดา
4. ⭐ **ขนาดบรรจุเปลี่ยนเงียบๆ** — ถุง 1 กก. กลายเป็น 900 ก. ต้นทุนทุกสูตรผิดหมดโดยไม่มีอะไรเตือน (สแกนบาร์โค้ด + ชั่งน้ำหนักตอนรับของช่วยได้)
5. **นับผงกับไซรัปให้แม่นเป็นไปไม่ได้** ถ้าไม่มีตาชั่งที่เคาน์เตอร์

**เกณฑ์อ้างอิงสำหรับตั้งความคาดหวัง:** ส่วนต่างต้นทุนวัตถุดิบ ~**2%** ถือว่าปกติ · ครัวมืออาชีพสูญเสีย **10–15%** ของค่าวัตถุดิบไปกับของเสีย
เศรษฐศาสตร์ยังคุ้มอยู่: มัทฉะลาเต้ต้นทุน "ประมาณ 1.75 ดอลลาร์ มั้ง" ที่ขาย 6.00 ดอลลาร์ ซ่อน margin ที่แกว่งได้ ~8 จุด = **~480 ดอลลาร์/เดือน ที่ยอดขาย 1,000 แก้ว**

### ⭐ ผลต่อการออกแบบ
- **ถือว่าการตัดสต็อกอัตโนมัติเป็น "การพยากรณ์เพื่อสั่งของ" และการนับจริงเป็น "ความจริงสำหรับคิดต้นทุน" — เขียนกำกับใน UI แบบนั้นตรงๆ**
- **ส่งมอบรายงานส่วนต่างเป็นผลลัพธ์หลัก ไม่ใช่ตัวเลขคงเหลือ**
- **รองรับการใช้บางส่วน (`is_tracked`) เป็นสถานะปกติ ไม่ใช่สถานะพัง**
- **บันไดการใช้งาน — ร้านส่วนใหญ่หยุดที่ขั้น 2 อย่างมีความสุข:**
  1. กรอกต้นทุนคงที่ต่อแก้ว → ได้รายงาน margin ทันที ภาระเป็นศูนย์
  2. ทำสูตร + ติดตามเฉพาะวัตถุดิบมูลค่าสูง ~10 รายการ
  3. BOM เต็มรูป สูตรย่อย yield เผื่อสูญเสีย

### 3.1 ⭐ สอง state machine แยกกัน

บั๊กที่พบบ่อยที่สุดคือใช้คอลัมน์ `status` เดียว — **การจ่ายเงินกับการทำเสร็จเป็นคนละแกน**: ร้านน้ำไทย = จ่ายก่อนทำ · คาเฟ่เปิดบิล = ทำก่อนจ่าย · เดลิเวอรี = จ่ายมาแล้วตั้งแต่ก่อนเราเห็นออเดอร์

⭐ **การล่ามแฮช** (`row_hash = H(payload || prev_hash)`) ใช้โค้ดราว **20 บรรทัด** แต่ทำให้ตรวจจับการแก้ข้อมูลย้อนหลังได้ — **มีค่ามหาศาลกับเจ้าของที่สงสัยพนักงาน**

⭐ **ติดตามการยกเลิกและส่วนลดรายพนักงานรายกะ และแสดงจำนวน + มูลค่าใน Z-report** — ในธุรกิจเงินสด นี่คือช่องทางทุจริตอันดับ 1 และ **"ยกเลิกได้โดยไม่ต้องระบุเหตุผล" คือการออกแบบที่ตกหล่นอันดับ 1**

### 3.4 เลขคิวและสติกเกอร์

- **สติกเกอร์พิมพ์ต่อแก้ว ไม่ใช่ต่อบรรทัด** — เนื้อหา: เลขคิว · ชื่อเครื่องดื่ม (ไทย) · ขนาด/ร้อน-เย็น · ความหวาน · น้ำแข็ง · ท็อปปิ้ง · ชื่อย่อคนขาย · เวลา (บางระบบใส่ QR ที่เข้ารหัส modifier ทั้งชุดไว้ตรวจตอนส่งของด้วย)

### 3.6 X-report กับ Z-report

- **X = ภาพนิ่งอ่านอย่างเดียว รันกี่ครั้งก็ได้ ไม่รีเซ็ตอะไรทั้งสิ้น** (ใช้ตอนเปลี่ยนกะ ก่อนนำเงินไปฝาก กลางช่วงเร่ง)
- **Z = ปิดกะ ล็อกและรีเซ็ตยอดสะสม** มีเลข Z ที่ห้ามใช้ซ้ำ

| เนื้อหา | X | Z |
|---|:-:|:-:|
| ยอดขายรวม/สุทธิ, จำนวนบิล, ยอดเฉลี่ยต่อบิล | ✓ | ✓ |
| ส่วนลด (จำนวน มูลค่า แยกตามพนักงาน แยกตามเหตุผล) | ✓ | ✓ |
| การยกเลิก (จำนวน มูลค่า แยกตามพนักงาน แยกตามเหตุผล) | ✓ | ✓ |
| การคืนเงิน (จำนวน มูลค่า เหตุผล) | ✓ | ✓ |

**⭐ กฎเหล็ก 2 ข้อ:**
1. **การออก Z ต้อง idempotent และย้อนกลับไม่ได้ — หนึ่งกะ หนึ่ง Z ตลอดกาล**
2. ⭐ **เก็บ Z เป็น JSON snapshot + ไฟล์ที่พิมพ์ออกมา แล้วพิมพ์ซ้ำจากที่เก็บไว้ ห้ามคำนวณใหม่** — ถ้ามีออเดอร์ sync เข้ามาช้าหลังปิดกะ การคำนวณใหม่จะได้ตัวเลขไม่ตรงกับใบที่พิมพ์แปะผนังไว้แล้ว **แล้วความเชื่อถือในระบบจะหมดไปทันที** (ออเดอร์ที่มาช้าให้ไปอยู่ใน `late_posting` exception list ของกะถัดไป)

## 4. สถาปัตยกรรม Offline-First

### 4.1 ⭐ สภาพจริงของงานนี้

ร้านเดียว 1–3 แท็บเล็ต ห้องเดียวกัน Wi-Fi เดียวกัน หนึ่งบิลมีคนเขียนคนเดียวในทางปฏิบัติ
**ข้อมูล ~99% เป็นข้อเท็จจริงที่เกิดแล้วเปลี่ยนไม่ได้** (บิล การจ่ายเงิน การเคลื่อนไหวสต็อก event) สิ่งที่แก้ร่วมกันจริงๆ มีน้อยมาก: บิลที่เปิดค้าง ตัวนับเลข ยอดสต็อก

⭐ **ข้อสังเกตนี้คือหัวใจของการออกแบบทั้งหมด: ข้อเท็จจริงที่ไม่เปลี่ยนย่อมไม่ชนกัน** งานวิศวกรรมส่วนใหญ่ใน ecosystem ของ sync engine มีไว้แก้ conflict บน mutable shared state — **ซึ่งเราควรออกแบบให้มันไม่มีตั้งแต่แรก แทนที่จะไปแก้**

### 4.2 เปรียบเทียบตัวเลือก

| ตัวเลือก | ได้อะไร | สรุปสำหรับงานนี้ |
|---|---|---|
| **SQLite + outbox เขียนเอง** | คุมได้ 100% ไม่ผูกกับใคร ~500–1,500 บรรทัดสำหรับงานรูปแบบนี้ | ⭐ **แนะนำ** |
| **WatermelonDB** | SQLite ที่จูนมาเพื่อ RN, lazy loading, protocol pull/push ที่ถูกต้อง — แต่ต้องเขียนทั้งสองปลายเอง | ดีถ้าใช้ React Native ให้ primitive ที่ถูกต้อง |
| **RxDB** | reactive query + replication plugin (CouchDB, Supabase, GraphQL, custom) TypeScript เต็มรูป | ใช้ได้ หนักกว่า เส้นทาง IndexedDB บนเว็บช้า |
| **PouchDB / CouchDB** | multi-master จริง revision tree พิสูจน์แล้วเรื่องออฟไลน์ | โมเดล winning-revision/loser ไม่เหมาะกับเรื่องเงิน ecosystem เก่าลง |
| **ElectricSQL** | sync ขาอ่าน Postgres→client ดีเยี่ยม (GA 1.0 มี.ค. 2025) | ⚠️ **จงใจไม่ทำขาเขียนและ offline write** → ยังต้องเขียนส่วนที่สำคัญเองอยู่ดี |
| **PowerSync** | Postgres/MongoDB ↔ SQLite แบบ managed มีคิวอัปโหลดถาวร FIFO retry อัตโนมัติ write checkpoint | ตัวเลือก managed ที่ดีที่สุด — แต่ค่าเริ่มต้นเป็น last-write-wins รายฟิลด์ ตรรกะ conflict จริงยังเป็นของเราใน `uploadData()` |
| **Yjs / Automerge (CRDT)** | ยอดเยี่ยมสำหรับข้อความและลิสต์ที่แก้ร่วมกัน | 🚫 **ผิดเครื่องมือสำหรับเรื่องเงิน** LWW ตัดสินด้วยนาฬิกาเครื่อง สองเครื่องออฟไลน์ห่างกันชั่วโมง อันที่แก้**ก่อน**ชนะ ทั้งที่ผู้ใช้คิดว่าอันหลังชนะ และ "merge การจ่ายเงินสองครั้ง" ไม่มีความหมาย |

### 4.3 ⭐ สถาปัตยกรรมที่แนะนำสำหรับนักพัฒนาคนเดียว

**SQLite เป็นแหล่งความจริงบนเครื่อง + outbox append-only + เซิร์ฟเวอร์โง่ๆ ที่ idempotent**

```
┌── แท็บเล็ต ──────────────────────────────┐
│  UI ── SQLite ในเครื่อง (แหล่งความจริง)   │
│         ├── ตารางโดเมน                    │
│         └── outbox (FIFO, ถาวร)           │
│              ↓ background worker          │
└──────────────┼────────────────────────────┘
               │ HTTPS + idempotency key
┌──────────────┼────────────────────────────┐
│  เซิร์ฟเวอร์: Postgres — รายงาน + สำรอง   │
│  ข้อมูลอ้างอิง (เมนู/ราคา/สูตร) ไหลลง      │
│  ข้อมูลธุรกรรมไหลขึ้น                      │
└───────────────────────────────────────────┘
```

Runtime: `op-sqlite` หรือ `expo-sqlite` (React Native) · `better-sqlite3` (Electron)

**⭐ ข้อจำกัดสำคัญที่ตัดความซับซ้อนออกไปเกือบหมด: ไม่มีอะไรเขียนได้สองทาง**
- **ข้อมูลอ้างอิง** (เมนู variant modifier ราคา สูตร พนักงาน): **เซิร์ฟเวอร์เป็นเจ้าของ ไหลลงทางเดียว เครื่องอ่านอย่างเดียว เซิร์ฟเวอร์ชนะเสมอ**
- **ข้อมูลธุรกรรม** (บิล การจ่ายเงิน คืนเงิน movement event กะ): **เครื่องเป็นเจ้าของ ไหลขึ้นทางเดียว insert อย่างเดียว PK = UUID ที่เครื่องสร้าง**

| ประเภทตาราง | กลยุทธ์ |
|---|---|
| บิล / จ่ายเงิน / คืนเงิน / movement / event | insert อย่างเดียว UUID จากเครื่อง → **ชนกันไม่ได้เลย** |
| แคตตาล็อก / ราคา / สูตร | เซิร์ฟเวอร์ชนะ ไม่มีเงื่อนไข |
| ⭐ **ยอดสต็อก** | **ห้าม sync ยอด ให้ sync movement** — สองเครื่องเขียน `qty = qty − 30` = lost update / สองเครื่อง insert แถว `−30` สองแถว = ถูกต้องเสมอ |
| บิลค้างที่แก้จากสองเครื่อง | คอลัมน์ `version` แบบ optimistic เซิร์ฟเวอร์ปฏิเสธของเก่า + device lease `locked_by_device`, `lock_expires_at` |
| กะ / ลิ้นชัก | ผูก `shift.device_id` · ถ้าลิ้นชักเดียวใช้หลายเครื่อง ให้เลือกเครื่องหนึ่งเป็นเจ้าของลิ้นชัก |

**ID:** **UUIDv7 หรือ ULID สร้างจากเครื่อง** — เรียงตามเวลา (ดีต่อ B-tree locality) และฝัง timestamp
🚫 **ห้ามใช้ AUTOINCREMENT กับอะไรก็ตามที่ข้ามเครื่อง**

### 4.4 ⭐ เลขที่บิลตอนออฟไลน์ — กับดักคลาสสิก

**3 วิธีที่ใช้ได้:**

1. ⭐ **prefix ตามเครื่อง (แนะนำ)** — `receipt_no = {device_code}-{seq}` → `A-001042`, `B-000317`
   นี่คือสิ่งที่ระบบ production ทำจริง (คำแนะนำของ Lightspeed เรื่องเลขบิลไม่เรียง และการจัดการ number sequence ของ Dynamics 365 Commerce ลงเอยที่นี่ทั้งคู่)
   ไม่ขาดต่อเนื่องต่อเครื่อง ไม่ชนกัน ออฟไลน์ได้เต็มที่ ตรวจสอบรายเครื่องได้จาก Z-report
2. **จองเลขเป็นบล็อก** — เซิร์ฟเวอร์ให้เครื่องละ 1,000 เลข เครื่องดึงจากในเครื่อง ขอบล็อกใหม่ตอนใช้ไป 80%
   ได้ชุดเลขเดียวและออฟไลน์ได้ แลกกับมีเลขขาดตอนทิ้งบล็อก **ใช้เมื่อถูกบังคับให้มีชุดเลขเดียวเท่านั้น** (Dynamics 365 มีโหมดนี้พอดีสำหรับองค์กรที่ต้องการความไม่ซ้ำอย่างเข้มงวด)
3. **เซิร์ฟเวอร์ให้เลขตอน sync** — ต่อเนื่องสมบูรณ์และเรียงทั่วโลก **แต่ตอนพิมพ์ยังไม่มีเลข → ใช้กับใบเสร็จที่พิมพ์ไม่ได้**

🚫 **ห้ามเด็ดขาด:** ออกเลขที่อาจชนกันแล้วค่อยไปเปลี่ยนทีหลัง — ทำให้ใบเสร็จที่พิมพ์ไปแล้วและช่วงเลขใน Z-report ทุกใบเป็นโมฆะ

### 4.5 นาฬิกาเพี้ยน

**อย่าเชื่อนาฬิกาเครื่องในการเรียงลำดับ** เก็บ 3 อย่างทุก event:
```
occurred_at_device    -- สิ่งที่แท็บเล็ตเชื่อ
device_seq            -- เพิ่มทีละ 1 ต่อเครื่อง ไม่ขาด
recorded_at_server    -- นาฬิกาเซิร์ฟเวอร์ตอนรับเข้า
```
เรียงลำดับ**ภายในเครื่อง**ด้วย `device_seq` · เรียง**ข้ามเครื่อง**ด้วย server cursor

- ทางเลือก: เพิ่ม **HLC** (physical ms, counter, node id) ~50 บรรทัด ได้ความสอดคล้องเชิงเหตุผลและผูกกับเวลาจริงแบบมีขอบเขต — **ใช้เพื่อการแสดงผลเรียงลำดับเท่านั้น ห้ามใช้ตัดสิน conflict เรื่องเงิน**
- ทุกครั้งที่ sync คำนวณ `clock_offset = server_time − device_time` **เตือนผู้ใช้เมื่อเกิน ~2 นาที** และเก็บ offset ต่อ batch ไว้แก้รายงานย้อนหลังได้
- ⭐ **`business_date` ต้องกำหนดชัด ไม่ใช่ derive** — ร้านปิดตี 1 ยอดต้องลงวันก่อนหน้า `order.business_date` **มาจากกะ ไม่ใช่จาก `date(created_at)`** และตั้ง timezone เป็น Asia/Bangkok ระดับร้าน **อย่าเชื่อ locale ของเครื่อง** (timezone ของเครื่อง POS ไม่ตรงกับของร้านเป็นความล้มเหลวที่มีบันทึกไว้)

### 4.6 Idempotency

```sql
idempotency_record(key PK, request_hash, response_json, status, created_at)
```
- ทุก endpoint ที่เปลี่ยนข้อมูลรับ `Idempotency-Key` — ใช้ UUID ของ entity หรือ `hash(device_id || device_seq)`
- key เดิม + hash เดิม → ตอบ response ที่เก็บไว้ **200**
- key เดิม + hash ต่าง → **409**
- ⭐ **client สร้าง key ก่อนยิงครั้งแรก และใช้ key เดิมทุกครั้งที่ retry** — **การสร้าง key ใหม่ตอน retry คือสาเหตุอันดับ 1 ที่ POS สร้างบิลซ้ำ**
- **การตัดเงินต้อง idempotent ตลอดสาย รวมถึง idempotency key ของ PSP ด้วย** ไม่งั้น retry = ตัดเงินซ้ำ

### 4.7 ลูป sync

```
PUSH  SELECT * FROM outbox WHERE state='PENDING' ORDER BY seq LIMIT 100
      POST /sync/push  (เป็น batch, มี Idempotency-Key รายชิ้น)
        2xx          → mark SENT
        4xx          → mark DEAD + แสดงใน UI (ห้ามทิ้งเงียบ)
        5xx/timeout  → backoff 1s, 2s, 4s … 60s + jitter แล้ว retry
      ⭐ FIFO เคร่งครัด ห้ามข้ามชิ้นที่ล้มเหลว —
      บิลต้องถึงก่อนการจ่ายเงิน การจ่ายเงินต้องถึงก่อนการคืนเงิน

PULL  GET /sync/pull?since={server_cursor}&limit=500
      upsert ข้อมูลอ้างอิงใน transaction เดียว แล้วค่อยบันทึก cursor
```

⭐ **cursor ต้องเป็นค่าที่เซิร์ฟเวอร์กำหนดและเพิ่มขึ้นทางเดียว** (Postgres sequence หรือ logical-replication LSN)
🚫 **ห้ามใช้ timestamp เป็น cursor** — จะทำแถวหายเงียบๆ เพราะนาฬิกาเพี้ยนและช่วงเวลาระหว่าง commit กับมองเห็น (แถวที่ commit ด้วย timestamp เก่ากว่า อาจมองเห็นได้หลังจากเราเลื่อน cursor ผ่านไปแล้ว)

**⭐ 2 อย่างที่สำคัญกว่าตัวอัลกอริทึม:**
- **ตัวบอกสถานะ sync ค้างอยู่ใน UI ตลอด** เช่น `ออฟไลน์ · 12 รายการรอส่ง` — พนักงานและเจ้าของต้องเห็นว่ามีงานที่ยังไม่ส่ง **ก่อน**จะไปล้างเครื่องหรือลงแอปใหม่
- **หน้า dead-letter** — outbox ที่ล้มเหลวเงียบๆ มาทั้งสัปดาห์จะถูกค้นพบตอนปิดบัญชีสิ้นเดือน

**การสำรองข้อมูล:** ⭐ **ภัยพิบัติที่เกิดจริงคือแท็บเล็ตตกแตกทั้งที่มีบิลยังไม่ sync ไม่ใช่ merge conflict**
→ sync ให้ถี่ (วินาที ไม่ใช่นาที) · อาจทำ replication ระหว่างเครื่องใน LAN โดยให้เครื่องหนึ่งเป็นฮับ · อัปโหลดไฟล์ SQLite ทุกคืน
**สำหรับนักพัฒนาคนเดียว สิ่งเหล่านี้มีค่ากว่า CRDT ใดๆ**

### 4.8 ⭐ การจ่ายเงินตอนออฟไลน์ — ต้องพูดตรงๆ

บัตรและ PromptPay **อนุมัติตอนออฟไลน์ไม่ได้** โหมดออฟไลน์ของ Square เองก็ระบุชัดว่า: รายการไม่ได้ถูกอนุมัติจริง ร้านค้ารับความเสี่ยงเองหากบัตรถูกปฏิเสธ Square จะไม่ตามเก็บเงินจากลูกค้าให้ รายการที่คิวไว้หมดอายุใน 72 ชม. และแนะนำให้ตั้งเพดานต่อรายการ

**นโยบายที่ควรใช้:**
- **เงินสด** — ออฟไลน์ได้เต็มที่ ไม่มีข้อแม้
- **PromptPay** — `PENDING_VERIFY` (แคชเชียร์ดูสลิปด้วยตา) กระทบยอดตอนปิดกะ และรายงานมูลค่าที่ยังไม่กระทบยอดใน Z-report
- **บัตร** — **บล็อก** หรือเตือนแรงพร้อมให้กดยอมรับความเสี่ยงอย่างชัดแจ้ง + เพดานต่อรายการ **ห้ามคิวการอนุมัติไว้เงียบๆ**

---

## 5. ลำดับการสร้างที่แนะนำ

1. ⭐ **POS ทำงานในเครื่องล้วนๆ** — SQLite, แคตตาล็อก, รับออเดอร์, จ่ายเงินสด, ใบเสร็จ + สติกเกอร์, เลขคิว **ไม่มีคลาวด์เลย** แล้ว**เอาไปใช้จริงหนึ่งวันเต็ม**
2. **วินัยเรื่องกะ** — เปิด/ปิดกะพร้อมนับเงินแยกชนิด, X/Z report, ยกเลิก/ส่วนลดที่ต้องมีเหตุผลและการอนุมัติ, `order_event` ที่ล่ามแฮช
3. **Sync** — outbox → เซิร์ฟเวอร์ idempotent, pull ข้อมูลอ้างอิงด้วย server cursor, สถานะ sync ที่มองเห็น + หน้า dead-letter (**เซิร์ฟเวอร์มีไว้รายงานและสำรองเท่านั้น**)
4. **ช่องทางขาย** — price list เดลิเวอรี, รายงานรายได้สุทธิที่รู้ค่า GP, รับออเดอร์จากภายนอก
5. **สต็อกบางส่วน** — บัญชี movement, สูตรเฉพาะวัตถุดิบมูลค่าสูง ~10 รายการ, การนับ, บันทึกของเสีย, รายงานส่วนต่าง
6. **BOM เต็มรูป** — สูตรย่อย yield เผื่อสูญเสีย **เฉพาะเมื่อขั้น 5 ถูกใช้งานจริงแล้วเท่านั้น**

---

## 6. ⭐ 2 การตัดสินใจที่มีผลมากที่สุดในทั้ง design

1. **อุณหภูมิและขนาดเป็น variant ส่วนความหวานและน้ำแข็งเป็น modifier ราคา 0 ที่มีตัวคูณเป็นตัวเลข** — การตัดสินใจข้อเดียวนี้กำหนดว่าระบบสต็อกจะทำงานได้จริงหรือไม่
2. **sync movement ไม่ใช่ level และทำให้ข้อมูลธุรกรรมทั้งหมด insert อย่างเดียวด้วย UUID จากเครื่อง** — ข้อนี้กำจัดปัญหา conflict resolution ทั้งหมดสำหรับร้าน 1–3 เครื่อง ซึ่งเป็นเหตุผลที่การเขียน outbox เองชนะการรับ PowerSync หรือ ElectricSQL มาใช้
