## 3. มิติของสูตร: เมนู × ขนาด × ความหวาน

สูตรเก็บเป็น **ตารางชัดแจ้ง 360 แถว** (24 เมนู × 3 ขนาด × 5 ระดับหวาน) แต่ละแถวระบุปริมาณของ "วัตถุดิบในสูตร" 17 ตัว + บรรจุภัณฑ์ตามขนาด

### ระดับความหวาน (0 / 25 / 50 / 75 / 100 %)
ไม่ใช่ตัวคูณเดียว แต่ละเมนูมี "กฎ" ของตัวเอง เช่น

| เมนู | กฎความหวาน (16 oz) |
|---|---|
| Original | สลับนมข้นจืด ↔ นมข้นหวาน (58/0 → 34/32) + น้ำเชื่อมชดเชยคงที่ 16.6 ml ทุกระดับที่ > 0% |
| Matcha Latte | นมสดลด 3 ml ต่อขั้น น้ำเชื่อมเพิ่ม 7 ml ต่อขั้น (0 → 28) |
| Coconut Tea | นมข้นหวาน 0 → 20 ทีละ 5 · 0% ใช้เบสมะพร้าวมากกว่า (95 vs 82.2) |

นิยามในไฟล์: 100% ≈ 14 °Brix · 50% ≈ 11 · 0% ≈ 7 (จากน้ำตาลในเบส)

### ขนาด
- 20 oz = 16 oz × **1.25** ทุกบรรทัด
- 22 oz = 16 oz × **1.375** สำหรับของเหลว และ × **1.36** สำหรับน้ำแข็ง
- ราคาเป็นตัวเลขต่อขนาด ไม่ใช่ +บาท (สอดคล้องกับที่ออกแบบไว้ใน [05-โครงสร้างข้อมูลฯ](05-โครงสร้างข้อมูลและสถาปัตยกรรม.md))

### บรรจุภัณฑ์
1 ชุดต่อแก้ว = แก้ว + ฝาโดม + หลอด + สติกเกอร์ ตามขนาด (16 oz ฿4.00 · 20 oz ฿4.60 · 22 oz ฿4.80) รวมอยู่ในต้นทุนต่อแก้ว

## 4. โครงสร้างวัตถุดิบ 3 ชั้น

```
เมนู (360 สูตร)
  └─ วัตถุดิบในสูตร 17 ตัว + บรรจุภัณฑ์ 3 ชุด        ← ชั้นที่สูตรอ้างถึง
       ├─ เบส/ซับสูตร 7 ตัว (ทำเป็น batch)        ← มี BOM และ yield
       ├─ ตัวแทน 1:1 ของของดิบ 9 ตัว (นมสด = RM-MLK-01)
       └─ ชุดบรรจุภัณฑ์ (แก้ว+ฝา+หลอด+สติกเกอร์)
            └─ สินค้าที่ซื้อจริง 32 รายการ (RM-xxx-## / PK-xxx-##)   ← ชั้นที่นับสต็อกและมีราคาซื้อ
```

## 5. ต้นทุน

- ต้นทุนต่อหน่วยใช้ = ราคาเฉลี่ยจากบันทึกซื้อ ÷ ปริมาณต่อหน่วยซื้อ (ถ้ายังไม่มีบันทึกซื้อใช้ราคาตั้งต้น) → ตรงกับ **moving weighted average** ที่ออกแบบไว้
- ต้นทุนเบส = Σ (ส่วนประกอบ × ต้นทุน) ÷ yield ของ batch
- ต้นทุนต่อแก้ว = Σ (วัตถุดิบในสูตร × ต้นทุน) + ชุดบรรจุภัณฑ์
- ในไฟล์ **น้ำแข็งและน้ำคิดต้นทุน** (0.014 ฿/g และ 0.00075–0.002 ฿/ml) แม้จะเล็ก → ระบบควรมี `is_tracked=false` แต่ยังคิดต้นทุนด้วยราคามาตรฐานได้ (แยก "นับสต็อก" กับ "คิดต้นทุน" ออกจากกัน)
- ตัวอย่างต้นทุน 16 oz 50%: Original ฿14.74 (GP 67%) · Matcha Latte ฿32.15 (GP 62% — ผงมัทฉะเป็น 55% ของต้นทุน)

## 7. สิ่งที่ไฟล์มีแต่ POS ไม่ควรรับมา (คงไว้ใน Excel)

- **R&D Log / สรุปการชิม (JAR test)** เป็นงานพัฒนาสูตร ไม่ใช่งานหน้าร้าน
- **คู่มือมัทฉะ / เคล็ดลับ / SOP** เป็นเอกสาร ควรอยู่ใน Excel หรือ Notion ไม่ใช่ในฐานข้อมูล POS (แต่ POS อาจแสดง "เบสที่ต้องมีพร้อม" ต่อเมนูได้)
- **Schema สำหรับบอท LINE OA** ออกแบบให้บอทเขียนลง Excel — POS จะแทนที่ทั้งหมด (ถ้าอยากสั่งผ่าน LINE ในอนาคต ให้ต่อกับ API ของ POS แทน)

## 8. ผลต่อการออกแบบ POS (สรุป)

1. **สูตรเป็นตารางชัดแจ้ง ต่อ (เมนู, ขนาด, ความหวาน)** ไม่ใช่ modifier ที่มี factor เดียว → เปลี่ยนจากแบบร่างเดิม (ดูการตัดสินใจ D16 ใน [../design/00-บันทึกการตัดสินใจ.md](../design/00-บันทึกการตัดสินใจ.md))
2. **ความหวานเป็นมิติของสูตร ไม่ใช่ modifier** ราคาไม่เปลี่ยน แต่วัตถุดิบเปลี่ยน
3. **ยังไม่ต้องมี modifier / topping / ระดับน้ำแข็ง** ในเฟส 1 แต่ schema เผื่อไว้ (เช่น "ไม่ใส่น้ำแข็ง" ในอนาคต = modifier ที่ลบบรรทัดน้ำแข็ง)
4. **วัตถุดิบ 3 ชั้น** ต้องมี item ที่เป็น "prepared" พร้อม BOM + yield + อายุ และหน้าจอ "ทำเบส"
5. **ของดิบ 32 รายการ** พร้อมหน่วยซื้อ/หน่วยใช้/จุดสั่งซื้อ นำเข้าจากไฟล์ได้ทันที
6. **นำเข้าครั้งเดียวด้วยสคริปต์** (items → BOM → recipes → prices → equipment) แล้ว POS เป็นแหล่งความจริงแทน Excel ไม่ทำ sync สองทาง
7. เกณฑ์ GP (60/55%) ใช้เป็นตัวเตือนในหน้าจัดการเมนูได้
8. ทะเบียนอุปกรณ์ + ค่าเสื่อม มีอยู่แล้ว 15 รายการ → เป็นโมดูลเล็กที่นำเข้าได้ (ไม่กระทบต้นทุนต่อแก้ว)
