สถานะ: ตรวจจากหน้าราคาจริง 17 ก.ย. 2026 (✅ = อ่านจากเอกสารทางการวันนี้ · ⚠️ = จากความรู้เดิม ยังไม่ได้ยืนยันวันนี้)
โจทย์ (D14): เซิร์ฟเวอร์ทำแค่รับ sync · รายงาน · สำรองข้อมูล · ปริมาณงานน้อยมาก (ร้านเดียว ไม่กี่ร้อยบิล/วัน) · **ต้องฟรีจริงแบบถาวร ไม่ใช่ทดลองใช้**

### ทำไม Neon
- ฟรีถาวรจริง ไม่ต้องใส่บัตร · อยู่ Singapore (latency จากไทย ~30–40 ms)
- หลับแล้ว **ตื่นเองอัตโนมัติ** (cold start < 1 วินาที) ต่างจาก Supabase ที่ต้องกดกู้คืนเองถ้าร้านปิดยาวเกิน 1 สัปดาห์
- มี **branch** สำหรับทดสอบ migration ก่อนใช้จริง (สำคัญกับ D12 ความถูกต้อง)
- 0.5 GB พอราว 2–3 ปีตามประมาณการ §1 · เมื่อใกล้เต็ม ย้ายไป Supabase หรือจ่าย Launch $19/เดือน หรือ archive ข้อมูลเก่า

### ⚠️ กฎการใช้ Neon ให้ไม่เกิน 100 CU-ชม.
- Neon คิดเวลาที่ compute ตื่นอยู่ (ขั้นต่ำ 0.25 CU) → **100 CU-ชม. = ตื่นได้ ~400 ชม./เดือน**
- ถ้า POS sync ทุก 30 วินาทีตลอด 24 ชม. compute จะไม่หลับเลย = 720 ชม. × 0.25 = 180 CU-ชม. **เกิน** → compute ถูกระงับจนสิ้นเดือน (ข้อมูลไม่หาย แต่ sync ไม่ได้)
- ทางแก้: sync **เมื่อมีข้อมูลใหม่ + ทุก 5–10 นาทีเฉพาะเวลาที่มี shift เปิดอยู่** และ **หยุด sync เมื่อปิดร้าน** → เปิดร้าน 10–12 ชม./วัน ≈ 300–360 ชม. × 0.25 = 75–90 CU-ชม. ยังอยู่ในเกณฑ์ แต่ทับเส้น
- ทางแก้เพิ่ม: API เปิด connection เฉพาะตอนมี request (ไม่ใช้ connection pool ที่ค้าง) และ cron งานกลางคืน (ตรวจ invariant, backup) รวมไว้ในช่วงเดียว
- มีหน้า usage ใน console ให้ดู → ตั้งเตือนที่ 80 CU-ชม.

ถ้าเกินบ่อย → สลับไป Supabase (ไม่มีเพดานชั่วโมง compute แต่ต้องจำเรื่อง 1 สัปดาห์)

### ทำไม Cloud Run
- ฟรีจริงที่ปริมาณงานนี้ (60k requests/เดือน เทียบเพดาน 2M) และไม่มีนโยบายหลับ 15 นาทีแบบ Render
- อยู่ Singapore เหมือน Neon → API ↔ DB ใน region เดียวกัน
- deploy จาก container → ย้ายไปที่อื่นได้ทุกเมื่อ ไม่ล็อกอิน
- ข้อเสีย: ต้องเปิด billing account (ผูกบัตร) — ตั้ง **budget alert ที่ ฿50** และ **cap max instances = 1** กัน bill ช็อก

### ถ้าไม่อยากผูกบัตรเลย
Render Web Service ฟรี + Neon ฟรี = ไม่ต้องใส่บัตรเลยทั้งคู่ แลกกับ cold start ~30–60 วินาทีตอนเปิดร้าน (แอปขายได้ปกติเพราะ offline-first; แค่ sync รอบแรกช้า)

## 5. ทางเลือกแหวกแนว: SQLite ทั้งสองฝั่ง

ถ้าฝั่งเครื่องใช้ SQLite (WASM) อยู่แล้ว การให้เซิร์ฟเวอร์ใช้ SQLite ด้วย (Turso หรือ D1) จะตัดปัญหา "schema 2 dialect" ที่ระบุใน [../design/01-ตัวเลือก-tech-stack.md](../design/01-ตัวเลือก-tech-stack.md) ทิ้งไปเลย และ Turso ฟรีให้ถึง 5 GB

ข้อเสีย: NestJS + Drizzle ต่อ Turso ได้ (ผ่าน `@libsql/client`) แต่ ecosystem รายงาน/constraint ของ Postgres แข็งแรงกว่า · Turso อยู่ระหว่างเปลี่ยนผ่าน (libSQL → Turso Database) ⚠️

**สรุป: ยังยึด Postgres บน Neon** เพราะ D12 ให้น้ำหนักความถูกต้อง และ Postgres มี constraint/transaction ที่พิสูจน์แล้ว ส่วน schema 2 dialect แก้ด้วยเทสต์ตรวจความตรงกัน (spike #3)

## 6. ข้อเสนอสุดท้าย (แก้ไข 17 ก.ย. หลัง Q30: ไม่ผูกบัตร · และ Q29: ต้องรับ LINE webhook)

```
[แท็บเล็ต/มือถือ + ลูกค้าใน LINE (LIFF)]  PWA บน Cloudflare Pages
        │ sync ขณะเปิดร้าน · pull ออเดอร์ LINE ทุก 30–60 วิ (endpoint เช็ค flag ในหน่วยความจำก่อนแตะ DB)
        ▼
[Render free · Singapore]  NestJS  ตื่นตลอดด้วย ping /health ทุก 10 นาที (cron-job.org / UptimeRobot)
        │                 744 ชม./เดือน จาก 750 → เปิดได้ service เดียว
        ▼
[Neon · Singapore]  PostgreSQL 0.5 GB  หลับหลัง 5 นาที (ping/poll ต้องไม่ปลุก)
        │
        └── ทุกคืน 02:00  GitHub Actions: ตรวจ invariant + pg_dump → R2
```

ค่าใช้จ่ายต่อเดือน: **฿0** · **ไม่ต้องผูกบัตรกับใครเลย** (Render, Neon, Cloudflare, GitHub ล้วนสมัครฟรีไม่ต้องใส่บัตร ⚠️ ยืนยันตอนสมัครจริง)
ข้อแลก: การ ping กันหลับเป็นพื้นที่สีเทาของ Render · ถ้าถูกระงับ ย้าย webhook ไป Cloudflare Workers และยอมให้ API หลับ (ดู [11-สั่งผ่าน-LINE.md](11-สั่งผ่าน-LINE.md) §3)
Cloud Run ถูกตัดออกเพราะต้องผูกบัตร (เก็บไว้เป็นทางเลือกถ้าวันหน้ายอมผูก: cold start เร็วกว่า ไม่ต้อง ping)
