# ความผิดพลาดที่พบบ่อยเวลาสร้าง POS เอง

รวบรวมจากประสบการณ์ที่มีบันทึกไว้ของคนที่สร้าง POS เอง และจากช่องโหว่ที่พบใน POS สำเร็จรูป

---

## 1. เรื่องเงินและความถูกต้อง

| ปัญหา | ทางแก้ |
|---|---|
| ⭐ **ใช้ float กับจำนวนเงิน** | ใช้จำนวนเต็มหน่วยสตางค์ทุกที่ + ฟังก์ชันปัดเศษเดียว |
| ⭐ **คำนวณอดีตใหม่จากแคตตาล็อกปัจจุบัน** — แก้ราคาทีเดียว ใบเสร็จเมื่อวานเปลี่ยน | snapshot ชื่อ ราคา และส่วนต่าง modifier ลงบรรทัดบิล |
| **ไม่ตัดสินใจลำดับ ส่วนลด/ภาษี/ปัดเศษ ให้ชัด** | กำหนดครั้งเดียว: ลดก่อนคิดภาษี · ปัดระดับบรรทัดหรือระดับบิล · ครึ่งขึ้นหรือ banker's rounding — เข้ารหัสไว้ในฟังก์ชันบริสุทธิ์เดียวที่มีตารางเทสต์ |
| ⭐ **ส่วนลดระดับบิลไม่กระจายลงบรรทัด** | ต้องกระจายด้วย largest-remainder ให้ Σ บรรทัด = หัวบิลเป๊ะ ไม่งั้น margin ต่อรายการเพี้ยนและภาษีบวกไม่ลง |
| **สับสน inclusive กับ exclusive tax** | เก็บ flag `tax_inclusive` ต่อบรรทัด |
| ⭐ **สมมติว่าต้องมี VAT เสมอ** (เฉพาะไทย) | ร้านต่ำกว่า 1.8 ล้านไม่ได้จด VAT และออกใบกำกับภาษี**ไม่ได้** → **สร้างโหมด "ไม่มีภาษี" เป็นพลเมืองชั้นหนึ่ง** |
| **hard-code อัตราภาษี 7%** | 7% หมดอายุ **30 ก.ย. 2570** ต้องเก็บเป็น config ที่มี `effective_from` |
| **ราคา modifier ไม่ปรับตามขนาด** | มีตาราง `modifier_option_price_override(modifier_option_id, option_value_id, price_delta)` |
| **ไม่รองรับ MAX หรือ "N ชิ้นแรกฟรี"** จนกว่าจะมีโปรที่ต้องใช้ | ใส่ `price_behavior` (SUM/MAX/FREE_N_THEN_SUM) ไว้ตั้งแต่แรก |

## 2. โมเดลข้อมูล

| ปัญหา | ทางแก้ |
|---|---|
| ⭐ **ระเบิด combination เป็นสินค้า** — 3 ขนาด × 3 อุณหภูมิ × 5 ความหวาน × 4 น้ำแข็ง = 180 SKU | ขนาด/อุณหภูมิ = variant · ความหวาน/น้ำแข็ง = modifier |
| ⭐ **ผิดคนละด้าน: ทำขนาดเป็น modifier** | ตัดแก้วตามขนาดไม่ได้ ทำสูตรต่อขนาดไม่ได้ ตั้งราคาท็อปปิ้งต่อขนาดไม่ได้ |
| ⭐ **ลบข้อมูลจริง ไม่มี `is_active`** | รายงานย้อนหลังพังหมด ต้องใช้ soft delete ทุกที่ |
| **สูตรและราคาไม่มี version** | COGS ย้อนหลังเปลี่ยนเงียบๆ → เก็บ `recipe_version_id` และ snapshot ราคา |
| ⭐ **modifier ไม่มี `factor`** | ความหวานกลายเป็นข้อความที่เครื่องอ่านไม่ออก (นี่คือข้อจำกัดที่ผู้ใช้ Loyverse เจอจริงๆ — composite/modifier ไม่ตัดสต็อก) |
| **ไม่แยก `receipt_no` กับ `queue_no`** | อันหนึ่งต้องแก้ไม่ได้และอยู่ถาวร อีกอันต้องสั้นและใช้ซ้ำทุกวัน |

## 3. การปฏิบัติงานหน้าร้าน

| ปัญหา | ทำไมถึงสำคัญ |
|---|---|
| ⭐ **ไม่มีแนวคิดกะและลิ้นชักเงิน** | เกิน/ขาดมองไม่เห็น → เงินรั่วจับไม่ได้ **ซึ่งเป็นเหตุผลทั้งหมดที่ธุรกิจเงินสดซื้อ POS ตั้งแต่แรก** |
| ⭐ **ยกเลิกบิลได้โดยไม่ต้องมีเหตุผล ไม่ต้องอนุมัติ ไม่มีรายงานรายพนักงาน** | ในธุรกิจเงินสด นี่คือช่องทางทุจริตอันดับ 1 และเป็นการออกแบบที่ตกหล่นอันดับ 1 |
| ⭐ **ใช้การลบแทนการกลับรายการ** | "undo" ที่ลบแถวทิ้งทำลายร่องรอยการตรวจสอบทั้งหมด |
| ⭐ **คำนวณ Z ใหม่ตอนพิมพ์ซ้ำ แทนที่จะเล่นจาก snapshot** | ออเดอร์ที่ sync มาช้าทำให้ตัวเลขไม่ตรงกับใบที่แปะผนังไว้ **ความเชื่อถือในระบบหมดทันที** |
| ⭐ **ไม่มี `business_date`** | ร้านปิดตี 1 ยอดขายลงผิดวัน รายงานรายวันผิดหมดแบบแนบเนียนจนไม่มีใครสังเกต |
| **timezone ของเครื่องไม่ตรงกับของร้าน** | ตั้ง Asia/Bangkok ระดับร้าน อย่าเชื่อ locale ของเครื่อง |
| **ไม่มีโหมดฝึกอบรม/สาธิต** | พนักงานฝึกบนข้อมูลจริง |

## 4. Offline / Sync

| ปัญหา | ผลที่เกิด |
|---|---|
| ⭐ **ใช้ timestamp เป็น sync cursor** | **แถวหายเงียบๆ** เพราะนาฬิกาเพี้ยนและช่วงเวลาระหว่าง commit กับมองเห็น → ต้องใช้ค่าที่เซิร์ฟเวอร์กำหนดและเพิ่มขึ้นทางเดียว (sequence หรือ LSN) |
| ⭐ **AUTOINCREMENT id บนเครื่อง** | ชนกันตอน merge → ใช้ UUIDv7/ULID ที่เครื่องสร้าง |
| ⭐ **retry ที่ไม่ idempotent** | **บิลซ้ำและตัดเงินซ้ำ — มีรายงานทั่วโลก** สาเหตุคือสร้าง idempotency key ใหม่ตอน retry |
| ⭐ **sync ยอดสต็อกแทน movement** | lost update — สองเครื่องเขียน `qty = qty − 30` พร้อมกัน ข้อมูลหาย |
| ⭐ **ไม่มี UI บอกสถานะ sync และไม่มี dead-letter queue** | พังเงียบเป็นสัปดาห์ พนักงานลงแอปใหม่แล้วยอดขายหายไปทั้งหมด |
| **ข้ามชิ้นที่ล้มเหลวใน outbox** | บิลต้องถึงก่อนการจ่ายเงิน การจ่ายเงินต้องถึงก่อนการคืนเงิน — ต้อง FIFO เคร่งครัด |
| **เปลี่ยนราคากลางกะบนเครื่องที่ข้อมูลเก่า** | ต้องมีนโยบาย: เปลี่ยนราคาได้เฉพาะตอนเปลี่ยนกะ หรือใช้ price list ที่มี `effective_from` |
| ⭐ **สร้าง CRDT sync ให้ร้านที่มี 2 เครื่อง** | over-engineering และ **CRDT ผิดโดยหลักการสำหรับเรื่องเงิน** เพราะ LWW ตัดสินด้วยนาฬิกาเครื่อง |
| **มาร์กการจ่าย QR เป็น CAPTURED ทั้งที่ยังไม่ยืนยัน** | ต้องมีสถานะ `PENDING_VERIFY` จริง และรายงานยอดที่ยังไม่กระทบยอดใน Z-report |
| **คิวการอนุมัติบัตรไว้เงียบๆ ตอนออฟไลน์** | บัตรอนุมัติออฟไลน์ไม่ได้ ร้านรับความเสี่ยงเอง (Square เองก็เตือนแบบนี้) → บล็อกหรือเตือนแรง |

## 5. ฮาร์ดแวร์และความจริงทางกายภาพ

| ปัญหา | รายละเอียด |
|---|---|
| ⭐ **เครื่องพิมพ์คือภาระซัพพอร์ตอันดับ 1** | บลูทูธหลุด สิทธิ์ USB บน Android ภาษาถิ่น ESC/POS ต่างกันรายรุ่น |
| ⭐ **ภาษาไทยบนเครื่องพิมพ์ความร้อนราคาถูก** | TIS-620/CP874 แต่ละรุ่นวางสระ/วรรณยุกต์ไม่เหมือนกัน — **ทดสอบกับรุ่นที่จะซื้อจริงก่อน หรือเรนเดอร์เป็นรูปภาพแล้วพิมพ์เป็นรูป** |
| ⭐ **ลิ้นชักเปิดผ่านพอร์ตของเครื่องพิมพ์** | **ไม่มีเครื่องพิมพ์ = ไม่มีลิ้นชัก** และต้องเช็ค 12V/24V ให้ตรง |
| ⭐ **โหมดประหยัดแบตของแท็บเล็ตฆ่า sync worker และการเชื่อมต่อ BLE** | ต้องปิด battery optimization ทีละเครื่องตอนติดตั้ง (OEM จีนดุเป็นพิเศษ) |
| **ขนาดจอ** | เครื่องดื่มที่มี 5 กลุ่มตัวเลือกต้องใช้จอ ≥10" ไม่งั้นบาริสต้ากดผิดตอนเร่ง |
| **สั่งซื้อรุ่นที่ไม่มีขายในไทย** | XP-80C / XP-T80Q / XP-365B / Gprinter ตัวเครื่อง / Bixolon — ไม่มีในช่องทางจำหน่ายไทย |
| **ซื้อเครื่องสแกน 1D** | QR พร้อมเพย์และ LINE เป็น 2D → เงิน 1,800 บาททิ้งเปล่า |
| **ซื้อ SUNMI มือสองจากฝูงไรเดอร์ foodpanda** | Android 7.1 bootloader ล็อก ไม่มีประกัน |

## 6. ผลิตภัณฑ์และกระบวนการ

| ปัญหา | ทางแก้ |
|---|---|
| ⭐ **สร้างระบบสต็อกก่อนที่การรับออเดอร์จะนิ่ง** | **ความเร็วที่เคาน์เตอร์คือตัวผลิตภัณฑ์ ที่เหลือคือรายงาน** |
| ⭐ **ไม่เทสต์ที่ความเร็วจริง** | 40 ออเดอร์ใน 20 นาที คนเดียว มือเปียก มีคิว และลูกค้าเปลี่ยนความหวานหลังพิมพ์สติกเกอร์ไปแล้ว |
| ⭐ **เชื่อสต็อกที่ตัดอัตโนมัติว่าเป็นความจริง** | มันคือ**การพยากรณ์เพื่อสั่งของ** ความจริงคือการนับจริง (การรินมือแกว่ง ±20% ทุกแก้ว) |
| **ฟีเจอร์บวมและการล็อกฮาร์ดแวร์เฉพาะ** | เป็นสาเหตุหลักที่ร้านค้าไม่พอใจ POS |
| **ให้เจ้าของกรอกจุดสั่งซื้อ 60 รายการเอง** | ต้องคำนวณจากยอดใช้เฉลี่ย 21 วัน แล้วให้แก้ทับได้ |

## 7. ⭐ 5 อย่างที่ต้องทำให้ถูกตั้งแต่วันแรก เพราะแก้ทีหลังแพงมาก

1. **จำนวนเต็มหน่วยสตางค์ + ฟังก์ชันคำนวณราคาบริสุทธิ์เดียว**
2. **snapshot ทุกอย่างลงบรรทัดบิล — ห้าม join กลับหาแคตตาล็อกเพื่อรายงาน**
3. **ข้อมูลธุรกรรม insert อย่างเดียว + UUID จากเครื่อง + `business_date` ที่กำหนดชัด**
4. **เลขที่บิลมี prefix ตามเครื่อง เรียงต่อเนื่อง แก้ไม่ได้ + ห้ามลบบิล (ยกเลิกได้แต่ต้องเหลือร่องรอย)**
5. **`factor` เป็นตัวเลขบนความหวาน/น้ำแข็ง + `option_value.recipe_scale` บนขนาด** — ถ้าไม่มี 2 อย่างนี้ ระบบสต็อกจะไม่มีวันทำงานได้
