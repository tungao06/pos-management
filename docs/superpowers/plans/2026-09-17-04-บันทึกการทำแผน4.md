## 3. การตัดสินใจระหว่างทำที่ไม่ได้อยู่ในแผน

ต่อไปนี้คือ ruling ที่ controller ตัดสินระหว่างทำ (ไม่ได้เขียนไว้ในโค้ดต้นแบบของแผน) ตามลำดับที่เกิดในเลดเจอร์:

- **inactive items ที่ยังมีสต็อก (I-2, Task 3 review):** สินค้าที่ปิดใช้ (`is_active = false`) แต่ยัง on-hand ≠ 0 **นับได้และเบิกออกได้เป็นรายการ** (เพื่อเคลียร์ให้เป็น 0) แต่ **รับของ/ทำเบสยังปฏิเสธเสมอ** สำหรับ item ที่ inactive · ช่วยเหตุผล: "count all" (Q4-13) ต้องมองเห็นของที่ยังถือครองอยู่แม้ปิดใช้แล้ว (สอดคล้องเจตนา M-11) — implement ด้วย `requireStockItem(db, id, kinds, { allowInactiveWithStock: true })` (เฉพาะ Task 6/7 ที่เบิก/นับ) และ `stockCountableItems(db, costStates)` (รายการที่ต้องนับให้ครบ = active tracked + inactive ที่ on-hand ≠ 0) ruling นี้ถูก carry เข้า brief ของ Task 6/7 หลังเกิดที่ Task 3
- **วัตถุดิบ (ingredients) ไม่เคยถูกกันด้วย is_active (Task 5 m-3 → Task 6 I-1):** การขาย การทำเบส และการเบิกสต็อกออกตามสูตร **ไม่เช็ก is_active ของวัตถุดิบที่ใช้เป็นส่วนผสมเลย** เหมือนขายของ — Task 6 รอบแรกใส่เช็ก inactive-at-0 ของวัตถุดิบในสูตรผิดไปจากคำสั่ง controller เอง (dispatch wording ผิด) แก้โดยลบเช็กนั้นออกทั้งหมดใน fix round 1 (`73c2edb`) พร้อมเทสต์ยืนยันต้นทุนเฉลี่ย ≠ มาตรฐาน ยังทำงานถูก — เฉพาะ "ทำเบสของ item ที่ inactive เอง" ที่ยังถูกบล็อก ไม่ใช่การบริโภควัตถุดิบที่ inactive
- **`StockItemDto.isActive` และตัวเลือก active-only (I-2, Task 9 review):** brief เดิมของ Task 9 ไม่มีฟิลด์ isActive ใน DTO จึงหน้ารับของ/ทำเบสเผลอเสนอ item ที่ปิดใช้ให้เลือกได้ — เพิ่ม `isActive: boolean` เข้า `StockItemDto` (`stock-overview.ts`) ตัวเลือกในหน้ารับของและหน้าทำเบสกรองเฉพาะ active เท่านั้น ส่วนหน้าสต็อกยังโชว์ (มีตัวหมายว่า inactive) เพื่อให้เห็นของที่ต้องเคลียร์ — ruling นี้ apply ทั้ง Task 9 และ Task 10 (fix round หลัง Task 10 commit)
- **วันทำการของงานสต็อกใช้วันของกะที่เปิดอยู่เสมอ แม้กะเปิดข้ามเที่ยงคืน (m-3, Task 3 review):** เก็บพฤติกรรมเดิมตามคำตอบ Q4-1 (ตรงกับตรรกะฝั่งขาย) ไม่แก้เป็นวันที่ไทย ณ ขณะนั้นเมื่อกะเปิดค้าง — เพิ่มเทสต์ยืนยันพฤติกรรมนี้อย่างชัดเจนแทนการแก้โค้ด
- **ใบเสร็จรับของ ฿0 ที่ติ๊กจ่ายจากลิ้นชัก ไม่เขียน `PAID_OUT` (m-1, Task 4 review):** ก่อนหน้านี้จะพยายามเขียน `PAID_OUT` มูลค่า ฿0 หรือ error กำกวม — แก้เป็นข้าม `PAID_OUT` ไปเลยเมื่อยอดใบ = ฿0 (ไม่มีเงินให้จ่ายจากลิ้นชักจริง) มี test มาตรฐาน mutation-proven ยืนยัน (`608f61e`)
- **กล่องติ๊ก "จ่ายจากลิ้นชัก" ต้องรีเซ็ตเมื่อไม่มีกะเปิด (n-1, Task 9 re-review):** ถ้าปิดกะแล้วเปิดใหม่ (ในทางทฤษฎีที่ยังไปไม่ถึงจากแท็บเดียวในปัจจุบัน) ค่าที่ derive มาจากติ๊กเดิมต้องเคลียร์ เพราะเป็นเรื่องการยินยอมเรื่องเงิน (Q4-6) — controller สั่งแก้ทันทีถึงจะยังเข้าไม่ถึง (unreachable code path วันนี้) เพราะความเสี่ยงเรื่องเงินสำคัญกว่าความเล็กของบั๊ก (`6188fb1`)
- **"แก้ตัวเลข" เป็นแค่การแก้พิมพ์ผิด ไม่ใช่การนับใหม่ (I-2, Task 12 review):** เปิดแก้ต้อง prefill ค่าที่นับไว้เดิม (แยกเป็นหน่วยเต็ม + เศษ) ไม่เปิดเป็นช่องเปล่า · ช่องเปล่าถูกปฏิเสธเสมอ (ห้ามบันทึกเป็น 0 โดยไม่ตั้งใจ) · มีปุ่มยกเลิก · การนับใหม่จริง ๆ (คิด expected ใหม่) ทำได้ทางเดียวคือลบบรรทัดออกแล้วบันทึกใหม่ (remove + save) ซึ่งจะแช่แข็ง expected ใหม่ ณ ตอนบันทึกครั้งใหม่นั้น (T4-2) — ยืนยันด้วยเทสต์ I-9 (ค่าบัญชีคงที่ตอนแก้ตัวเลข) และเทสต์ "a real recount (removeCountLine, then save again) re-freezes expected to the live book" (review m-2)
- **db-schema baseline เช็กแล้วตรง:** Task 1 ปิดท้ายด้วยข้อสังเกตว่า baseline หลัง Task 1 คือ 120 เทสต์ (แผนคาดไว้ 121) และ Task 2 ควรพาไป 122 — task นี้ยืนยันแล้วว่า `pnpm exec turbo run typecheck test --force` ให้ db-schema = 122 ตรงกับที่คาดตอนจบแผน ไม่มีความคลาดเคลื่อนหลงเหลือ

- แผน 5: `KEY_COUNT_ITEM_CODES` (Q4-2) ย้ายเป็น setting ที่ sync ได้ · แก้จุดสั่งซื้อ/ต้นทุนมาตรฐาน/ของไม่นับสต็อกในหน้าจัดการสินค้า (D47 ข้อ 3–4) · เครื่องมือแก้ใบรับของผิด (Q4-7) · รูปใบเสร็จ (Q4-5 — `purchase.receipt_image_ref` ยังเป็น null)
- แผน 5: spec §6.1 เขียนว่าเรื่อง pull ตาม `server_seq` (อ่านไม่เกิน `pg_snapshot_xmin` หรือผู้เขียนคนเดียว) "แผน 4 เลือก" — ตอนเขียน spec แผน 4 หมายถึง API; ตอนนี้เป็นงานของแผน 5 (api-sync) แผนนี้ไม่ได้ตัดสิน
- แผน 5 (final review m-4): เหตุผลของ `PAID_OUT` ที่เขียนจากใบรับของ (`purchase.ts` `truncateCodePoints`) ตัดที่ 200 *code point* ไม่ใช่ 200 หน่วย UTF-16 อย่างที่ `REASON_MAX_LENGTH` ที่อื่นทุกจุดใช้ — ชื่อผู้ขายที่มี emoji ตั้งแต่ 7 ตัวขึ้นไปทำให้ reason ยาวได้ถึง 207 หน่วย UTF-16 · ฝั่ง ingest ของแผน 5 ต้องไม่บังคับ `.length <= 200` แบบเคร่งครัด หรือต้องใช้หน่วยเดียวกัน (code point) เทียบ
- แผน 7: รายงานส่วนต่างสต็อก (§4.5) อ่าน `stock_count_line.variance_satang` ของใบนับที่ปิดแล้ว **ยกเว้นบรรทัดยอดยกมา** = สินค้าที่ไม่มีในใบนับที่ปิดก่อนหน้า (ลำดับ rowid — เงื่อนไขเดียวกับ `StockCountLineDto.opening`) ไม่งั้นสัปดาห์แรกจะเห็นมูลค่าของทั้งร้านเป็น "ส่วนต่าง" (review I-5) · รายงานของเสียแยกตาม `stock_adjustment.reason_code` (ของเสีย/หมดอายุ/ทดลอง/แจก/อื่นๆ — movement ของแจกและอื่นๆ เป็น `WASTE`) · มูลค่าสต็อกใช้ `stockValueSatang` เดียวกัน
- แผน 7 (Task 5 m-4): รายงานที่อ้างต้นทุนของ production batch **ต้องอ่าน `production_batch.batch_cost_satang` โดยตรง ห้ามคำนวณใหม่ด้วยการรวม movement เอง** เพราะยอดรวมที่ปัดแล้ว (batch-level rounding) ไม่เท่ากับผลรวมของต้นทุนต่อบรรทัดที่ปัดแยกกัน (review m-4 ของ Task 5)
- แผน 8: invariant 5 (`item_cost_state.on_hand` = Σ movement) ยังรวมของ untracked (แคชติดลบของน้ำแข็ง) — rebuild แล้วเทียบได้ตรงเพราะ `insertMovements` ยังเขียนแคชทุก item · invariant 7 ตามคำตอบ Q4-1: ธุรกรรมสต็อกมี `business_date` ที่ไม่มีกะได้ → invariant 7 ใช้กับบิล/เงินสด/กะเท่านั้น
- ก่อนขายจริง: ล้างข้อมูลทดสอบบนแท็บเล็ตก่อนนับยอดยกมาจริง (ยังไม่มีปุ่ม — ติดตั้งแอปใหม่/ล้างข้อมูลเว็บไซต์ แล้วตั้งค่าเครื่องใหม่) · งาน deploy Pages + `registerType: 'prompt'` ยังค้างจากแผน 3

- เอกสาร spec รอบถัดไป: §3.3 เพิ่มตาราง `stock_adjustment` (T4-1) · §4.5 แก้ "expected = on_hand ณ เวลาเปิดใบนับ" เป็น "ณ เวลาบันทึกรายการนั้นครั้งแรก" (T4-2 — §4.5 เดิมหักของที่ขายระหว่างนับซ้ำ) · §5 หน้านับสต็อก/ปรับสต็อกตามที่สร้างจริง · §7 invariant 7 แก้ขอบเขตให้ตรงกับ D56 (ครอบเฉพาะบิล/เงินสด/กะ ไม่ครอบงานสต็อก)

## 6. ความเสี่ยงที่รู้อยู่ (Known risks)

- **ส่งซ้ำ (review M-7):** งานเขียนสต็อกไม่มี idempotency key จากหน้าจอ — ถ้า Worker commit แล้วแต่ promise ฝั่งหน้าจอหาย (รีโหลดกลางคำสั่ง) แล้วกดซ้ำ จะได้ใบรับของ/batch/ใบเบิกซ้ำ · ตอนนี้กันด้วยการปิดปุ่มระหว่างรอ (แบบแผน 3/3b) · แผน 5 ออกแบบ key ฝั่งหน้าจอ
- **การนับแบบไม่เห็นยอดปลอดภัยเท่าที่หน้าสต็อกปลอดภัย (Q4-3):** หน้าสต็อกแสดงคงเหลือทุกรายการ และหลังบันทึกรายการเห็นส่วนต่างทันที จึงคิดย้อนหายอดบัญชีได้ — ยอมรับสำหรับร้าน 2 คน แบบเดียวกับ 3b ความเสี่ยง (d)
- `stock_count_line` ถูก UPDATE/DELETE ระหว่างร่าง (T4-11) — ขัดกับหลัก "insert อย่างเดียว" อย่างเคร่งครัด (ยอมรับเพราะไม่ใช่ตารางบัญชีและร่างยังไม่เคยส่งก่อนปิด)
- ต้นทุนเฉลี่ยจากราคารับเข้าผิดที่ยืนยันไปแล้วค้างจนของล็อตนั้นหมด (Q4-7) — ไม่มีปุ่มยกเลิกใบรับของในแผนนี้
- อายุเบสคิดจาก batch ล่าสุด ไม่ใช่ FIFO (Q4-9) — เทของใหม่ทับของเก่าจะทำให้อายุที่แสดงยาวกว่าจริง
- **I-2 (final review — เดิมคือ Task 4 m-6) — ฿0 line ที่ on-hand ≤ 0 รีเซ็ตต้นทุนเฉลี่ยเป็นของบรรทัดนั้นเอง (spec §4.4), และผลตามมาที่ ledger ยังไม่เคยบันทึกไว้: ภายในใบเดียวกัน ผลลัพธ์ขึ้นกับลำดับบรรทัดเมื่อสินค้าเริ่มติดลบ — ตัวอย่าง RM-TEA-01 เริ่มที่ −500 g พร้อมบรรทัดจ่ายเงิน (400 g ฿77) และบรรทัดแถม (400 g ฿0): ถ้าบรรทัดแถมมาก่อนจะได้ต้นทุนเฉลี่ย ฿0.1925/g แต่ถ้าบรรทัดจ่ายเงินมาก่อนจะได้ 0 — ของชิ้นเดียวกันได้ต้นทุนคนละค่ากันแค่เพราะลำดับที่พิมพ์ (บรรทัดจ่ายเงิน 2 ราคาต่างกันก็เป็นแบบเดียวกัน คือบรรทัดหลังชนะ ไม่ใช่การถ่วงเฉลี่ย) ไม่ใช่เงินสด แต่กระทบ COGS/margin และติดค้างถาวรเพราะแถว SALE ประทับ `unit_cost_usat` ไว้แล้ว — พฤติกรรมนี้ตรงตาม spec §4.4 คำต่อคำ การเปลี่ยนจึงเป็นสิทธิ์เจ้าของ ไม่ merge-blocking เพราะร้านยังไม่ live และยังไม่มีต้นทุนที่ประทับไว้จริง **รอคำตอบเจ้าของที่ Q4-17 ก่อนขายจริง** (ยังไม่ตอบ ณ final review) — ข้อเสนอที่แนะนำ (ก): รวมทุกบรรทัดของสินค้าเดียวกันในใบเดียวกันก่อนคิดเฉลี่ย (ต้นทุนรวม ÷ ปริมาณรวม) ใบบรรทัดเดียวยังทำงานแบบเดิม ลำดับไม่มีผลอีกต่อไป
- **m-1 (final review) — จุดตัดของการนับ (count cut-off):** ใบรับของ/ทำเบส/ของแจกที่เกิดขึ้นจริงก่อนสินค้าถูกนับ แต่พิมพ์เข้าระบบหลังบรรทัดนั้นถูกบันทึกไปแล้ว จะถูกบวกเข้าไปทับยอดที่แช่แข็งไว้ (T4-2) ทำให้คงเหลือดูเกินจนกว่าจะนับครั้งถัดไป — ไม่ใช่บั๊กของโค้ด แก้ตัวเองได้ตอนนับใหม่ → เพิ่มคำเตือนในหน้านับสต็อก ("บันทึกรับของ/ทำเบสให้ครบก่อนเริ่มนับ") ที่ `5271324`
- ส่วนของ spec text ที่ยังไม่แก้ให้ตรงกับพฤติกรรมจริง: §3.3 (ไม่มีตาราง `stock_adjustment`) · §4.5 (expected แช่แข็งตอนไหน) · §7 invariant 7 (ขอบเขต) — ยังเป็นหนี้เอกสาร ไม่ใช่หนี้โค้ด
- ข้อมูลทดสอบบนแท็บเล็ต (บิล/สต็อก/ยอดยกมาที่ใช้ทดสอบ) ต้องถูกล้างก่อนนับยอดยกมาจริง แต่ **ยังไม่มีปุ่มล้างข้อมูลในแอป** — ต้องล้างด้วยการติดตั้งแอปใหม่/ล้างข้อมูลเว็บไซต์เอง
- ใบนับยอดยกมาต้องครบ 38 รายการในครั้งเดียว (ของดิบ 31 + เบส 7) อาจใช้เวลานานและน่าเบื่อบนแท็บเล็ต ยังไม่ได้ลองจริง (Task 13 Step 2 ที่เลื่อนไป D51 จะเป็นบทพิสูจน์แรก)
- `stockOverview` อ่าน `production_batch` ทั้งหมดทุกครั้ง (หลักพันแถวต่อปี — ประเมินว่าเร็วพอในสเกลร้าน 2 คน แต่ยังไม่มี pagination/index เพิ่ม)
