| Q5-9 | **แท็บเล็ตพิสูจน์ตัวเองกับเซิร์ฟเวอร์ครั้งแรกอย่างไร** — spec §7 บอกแค่ "`POST /auth/device` · token อายุยาวต่อเครื่อง" แต่ไม่ได้บอกว่าเครื่องได้ token มาได้อย่างไร | (ก) **รหัสลงทะเบียนครั้งเดียว**: เจ้าของตั้ง `REGISTRATION_CODE` (สุ่มยาว ≥ 16 ตัวอักษร) ใน Render แล้วพิมพ์ลงแท็บเล็ตตอนตั้งค่าเครื่อง (หรือทีหลังที่หน้าสถานะระบบ) → เซิร์ฟเวอร์คืน token อายุยาว เก็บ **แฮช** ไว้ฝั่งเซิร์ฟเวอร์ เพิกถอนได้ · (ข) ล็อกอินด้วยบัญชี+PIN ของเจ้าของแล้วออก token · (ค) ใส่ token ที่สร้างไว้ล่วงหน้าลงเครื่องด้วยมือ · (ง) ไม่ต้องล็อกอินเลย ใครยิงมาก็รับ (เชื่อ CORS) | **(ก)** | ร้านมีเครื่องขาย 1–2 เครื่อง ลงทะเบียนไม่กี่ครั้งตลอดอายุระบบ · รหัสเดียวจำง่ายและเปลี่ยนได้ทันทีถ้ารั่ว (แก้ env แล้ว redeploy) · PIN ในเครื่องมีไว้ระบุ "ใคร" ไม่ใช่ "เครื่องไหน" (spec §7: PIN ตรวจในเครื่องได้ตอนออฟไลน์) จึงไม่เหมาะเป็นกุญแจของเซิร์ฟเวอร์ · (ง) ใครก็ยิงข้อมูลปลอมเข้าฐานข้อมูลร้านได้ | Task 5 (`AuthService.register` · `device_token`) · Task 10 (`registerDevice`) · `.env.example` | |
| Q5-10 | **ผู้ใช้ · แฮช PIN · พร้อมเพย์ ขึ้นเซิร์ฟเวอร์ไหม** — แผน 3 สร้างข้อมูลพวกนี้ในเครื่องตอนตั้งค่าครั้งแรกและ **ไม่ได้อยู่ใน outbox** (งานส่งต่อ T15) จึงต้องตัดสินตอนนี้ | (ก) **ขึ้น ตอนลงทะเบียนครั้งเดียว**: ส่ง `device` + ผู้ใช้ (`pin_hash` เท่านั้น **ไม่มี PIN ดิบ**) + `setting` (รวมเลขพร้อมเพย์) · หลังจากนั้นเซิร์ฟเวอร์เป็นเจ้าของ (type R) และเครื่อง pull กลับลงมา · (ข) ไม่ขึ้นเลย — สร้างผู้ใช้ที่เซิร์ฟเวอร์แยกต่างหาก (ต้องมีหน้า admin ก่อน = รอ 5b) · (ค) ขึ้นเฉพาะ device ไม่เอาผู้ใช้ | **(ก)** | ถ้าผู้ใช้ไม่อยู่บนเซิร์ฟเวอร์ ทุกบิลที่อ้าง `created_by` จะถูกปฏิเสธด้วย `FK_MISSING` ทันที — sync ใช้ไม่ได้เลย · แฮช PIN ปลอดภัยพอจะเดินทาง (argon2id) และจำเป็นสำหรับเครื่องที่ 2 ที่ต้องล็อกอินได้แบบออฟไลน์ (spec §7 "pin_hash sync ลงมา") · เลขพร้อมเพย์เป็นข้อมูลร้านไม่ใช่ข้อมูลลูกค้า | Task 5 · Task 10 + เทสต์ "the raw PIN must never leave" | |
| Q5-11 | **เครื่องใหม่/เครื่องทดแทนดึงข้อมูลย้อนหลังแค่ไหน** — spec §6.4 บอก "ดึงแค่ 30 วันเพื่อหน้าประวัติ" แต่ไม่ได้บอกว่า 30 วันนั้นครอบอะไรบ้าง | (ก) **ตาราง R ทั้งหมด + `item_cost_state` + บิล 30 วัน (บิล/บรรทัด/event/การจ่าย)** · **ไม่ดึง** สต็อก/เงินสด/กะ/Z ย้อนหลัง (ดูจากรายงานฝั่งเซิร์ฟเวอร์ของแผน 7) · เครื่องใหม่ได้ **คำนำหน้าเลขที่บิลใหม่** (B, C, …) ตาม spec §2.2 · (ข) ดึงทุกอย่างทั้งหมดเท่าที่มี · (ค) ดึงแค่ตาราง R ไม่เอาบิลเลย (หน้าประวัติว่างจนกว่าจะขายใหม่) | **(ก)** | ตรงกับ spec §6.4 · หน้าประวัติและปุ่มยกเลิกใช้บิลของกะที่เปิดอยู่เป็นหลัก (D47 ข้อ 2) 30 วันจึงเหลือเฟือ · (ข) ทำให้ฐานข้อมูลในเครื่องโตโดยไม่มีใครใช้และกิน CU ของ Neon ตอนกู้คืน · ยอดยกมาของสต็อกอยู่ใน `item_cost_state` อยู่แล้ว จึงขายต่อได้ทันทีโดยไม่ต้องมีประวัติ movement | Task 10 `restoreDevice` · Task 13 S5-8 | |
| Q5-12 | **แถวที่เซิร์ฟเวอร์ "ปฏิเสธถาวร" (dead letter) ต้องทำอย่างไรต่อ** — spec §6.1 บอกแค่ "ย้ายไป dead-letter · ไม่ส่งซ้ำอัตโนมัติ · แสดงในหน้าตั้งค่า · ไม่บล็อกรายการอื่น" แต่ไม่ได้บอกว่าใครแก้และแก้อย่างไร | (ก) **หน้า "สถานะระบบ" แสดงทุกแถวที่ตาย พร้อมเหตุผลเป็นภาษาไทย + ปุ่ม "ส่งใหม่" (ทุกคนกดได้ ไม่ต้อง PIN)** · หน้าขายขึ้นแถบแดงเมื่อมีแถวตาย > 0 · **ไม่ลบแถวทิ้งไม่ว่ากรณีใด** · ไม่ส่งซ้ำเอง · แจ้งเตือนอัตโนมัติ (LINE/อีเมล) รอแผน 8 · (ข) เหมือน (ก) แต่ปุ่มส่งใหม่ต้อง PIN เจ้าของ · (ค) ให้ระบบส่งซ้ำเองทุกชั่วโมง 3 ครั้งแล้วค่อยตาย · (ง) มีปุ่ม "ทิ้งรายการนี้" ด้วยสำหรับของที่แก้ไม่ได้จริง ๆ | **(ก)** | แถวที่ตายเกือบทั้งหมดจะเกิดจากบั๊กหรือ schema ไม่ตรง ซึ่งต้องแก้ที่โค้ดแล้วค่อยกดส่งใหม่ — การส่งซ้ำอัตโนมัติ (ค) แค่เลื่อนเวลาที่เราจะรู้ตัว · ร้าน 2 คนเป็นเจ้าของทั้งคู่ PIN จึงไม่เพิ่มความปลอดภัย (หลักเดียวกับ Q4-4) · (ง) อันตราย: แถวที่ตายอาจเป็นเงินจริงที่รับมาแล้ว ปุ่มทิ้งทำให้ยอดบนเซิร์ฟเวอร์ต่างจากลิ้นชักอย่างถาวรโดยไม่มีร่องรอย | Task 8 `status.ts` (`listDeadRows`/`retryDeadRow`) · Task 9 หน้าจอ + e2e · Task 13 (ความเสี่ยง) | |
| Q5-13 | **ส่งแถวเดิมซ้ำแต่เนื้อหาไม่เหมือนเดิม ให้เซิร์ฟเวอร์ทำอย่างไร** — เกิดได้ถ้ามีบั๊ก หรือถ้ามีคนแก้ไฟล์ฐานข้อมูลในเครื่อง · spec §6.1 บอกแค่ "insert-if-absent" | (ก) **เก็บของเดิมไว้ ปฏิเสธของใหม่เป็น `CONFLICT` (dead letter พร้อมเหตุผล)** — ยกเว้น 3 ตารางที่ตั้งใจส่งสองครั้ง (`order` paid→voided · `shift` open→closed · `stock_count` open→closed) ที่อัปเดตทับได้ · ทำได้ด้วยตารางใหม่ฝั่งเซิร์ฟเวอร์ `ingested_row` ที่จำแฮชของเนื้อหาแต่ละแถว (spec §3.6 ยังไม่มีตารางนี้ — **โปรดรับทราบ** แก้ spec ในรอบเอกสารถัดไป) · (ข) ให้ของใหม่ทับของเก่าเสมอ (last-write-wins) · (ค) รับเงียบ ๆ ไม่ตรวจ (ของเดิมอยู่ ของใหม่หาย ไม่มีใครรู้) | **(ก)** | spec §6.1 เขียนชัดว่า "ไม่ใช้ CRDT · ไม่มี last-write-wins บนธุรกรรม" — (ข) ขัดโดยตรง · (ค) ทำให้ยอดบนเซิร์ฟเวอร์ต่างจากในเครื่องแบบเงียบ ๆ ซึ่งเป็นสิ่งที่ระบบนี้ตั้งใจกันตั้งแต่แรก (D21) · (ก) ทำให้ความไม่ตรงกันโผล่ขึ้นหน้าจอทันทีในรูปแบบเดียวกับ dead letter อื่น | Task 3 (ตาราง `ingested_row`) · Task 6 + เทสต์ "refuses the same key with different content" | |

## ไม่ถาม เพราะตัดสินแล้ว

- ใช้ NestJS + PostgreSQL + Drizzle (D13) · เซิร์ฟเวอร์ทำแค่ sync/รายงาน/สำรอง การขายทำงานในเครื่อง 100% (D14)
- Render free Singapore + Neon free Singapore + Cloudflare Pages + R2 · **ไม่ผูกบัตร** · ping ทุก 10 นาที · sync เฉพาะเวลาเปิดร้าน · `/health` และ poll ไม่แตะ DB (D15)
- จังหวะ sync: push debounce 5 วินาที · pull ทุก 300 วินาที · เช็คออเดอร์เข้าทุก 30 วินาที · ปิดกะแล้วส่งให้หมดแล้วหยุด (spec §6.2)
- push เป็นชุด ≤ 200 แถว FIFO พร้อม idempotency key ต่อแถว · dead letter ไม่ส่งซ้ำอัตโนมัติและไม่บล็อกแถวอื่น (spec §6.1)
- เซิร์ฟเวอร์ชนะเสมอบนข้อมูลหลัก · ห้ามแก้ข้อมูลหลักตอนออฟไลน์ · ไม่ใช้ CRDT · ไม่มี last-write-wins บนธุรกรรม (spec §6.1)
- เครื่องใหม่ได้คำนำหน้าเลขที่บิลใหม่ · ข้อมูลที่ยังไม่ push หายไปพร้อมแท็บเล็ตที่พัง (spec §2.2, §6.4, D6)
- คีย์ outbox เป็น `<table>:<id>[:suffix]` และแถว `order`/`shift`/`stock_count` ถูกส่งสองครั้ง (บันทึกแผน 3 M7 · 3b · 4)
- seed ของเซิร์ฟเวอร์ใช้ `canonicalSeedOpts()` เพื่อให้ id ตรงกับในแท็บเล็ต (บันทึกแผน 3 §5)
- ตารางบัญชี (`stock_movement` `order_event` `cash_movement` `z_report`) แก้/ลบไม่ได้ทั้ง 2 dialect (spec §3 · แผน 2)
- agent ไม่ push · merge เข้า main ได้หลัง audit + final review (opus) เท่านั้น (D42, D49) · โมเดล agent ตาม D43 · commit ไม่มี trailer ของ AI และ `docs/**` commit ได้ (D45)
- ทดสอบบนแท็บเล็ตจริงเลื่อนไปรอบท้ายสุด (D51) — รายการของแผนนี้ (S5-1…S5-10) อยู่ใน Task 13 Step 2
