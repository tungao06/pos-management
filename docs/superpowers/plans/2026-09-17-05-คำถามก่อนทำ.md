## ไม่ถาม เพราะตัดสินแล้ว

- ใช้ NestJS + PostgreSQL + Drizzle (D13) · เซิร์ฟเวอร์ทำแค่ sync/รายงาน/สำรอง การขายทำงานในเครื่อง 100% (D14)
- Render free Singapore + Neon free Singapore + Cloudflare Pages + R2 · **ไม่ผูกบัตร ค่าใช้จ่าย ฿0** · ping ทุก 10 นาที · sync เฉพาะเวลาเปิดร้าน · `/health` และ poll ไม่แตะ DB (D15)
- สำรองข้อมูล: GitHub Actions cron 02:00 ICT → `pg_dump` → R2 · เก็บ 30 วัน + ทุกวันที่ 1 เก็บ 12 เดือน · ทดสอบ restore เดือนละครั้ง (spec §10 — ที่ถามใน Q5-14 คือใครถือ bucket และทดสอบอย่างไรเท่านั้น)
- จังหวะ sync: push debounce 5 วินาที · pull ทุก 300 วินาที · เช็คออเดอร์เข้าทุก 30 วินาที · ปิดร้านแล้วส่งให้หมดแล้วหยุด · เปิดแอปตอนปิดร้าน = pull ครั้งเดียว (spec §6.2)
- push เป็นชุด ≤ 200 แถว FIFO พร้อม idempotency key ต่อแถว · **dead letter ไม่ส่งซ้ำอัตโนมัติ** และไม่บล็อกแถวอื่น (spec §6.1)
- เซิร์ฟเวอร์ชนะเสมอบนข้อมูลหลัก · ห้ามแก้ข้อมูลหลักตอนออฟไลน์ · ไม่ใช้ CRDT · ไม่มี last-write-wins บนธุรกรรม (spec §6.1)
- นาฬิกาเพี้ยนไม่บล็อกการขาย — ลำดับใช้ `chain_seq`/`seq` ไม่ใช่เวลา (spec §6.3 · D28)
- `GET /sync/inbox-flag` มีอยู่ตาม spec §6.2 และ §7 (ไม่ใช่ทางเลือกว่าจะทำหรือไม่)
- เครื่องใหม่ได้คำนำหน้าเลขที่บิลใหม่ · ข้อมูลที่ยังไม่ push หายไปพร้อมแท็บเล็ตที่พัง (spec §2.2, §6.4, D6)
- คีย์ outbox เป็น `<table>:<id>[:suffix]` และแถว `order`/`shift`/`stock_count` ถูกส่งสองครั้ง (บันทึกแผน 3 M7 · 3b · 4)
- seed ของเซิร์ฟเวอร์ใช้ `canonicalSeedOpts()` เพื่อให้ id ตรงกับในแท็บเล็ต (บันทึกแผน 3 §5)
- ตารางบัญชี (`stock_movement` `order_event` `cash_movement` `z_report`) แก้/ลบไม่ได้ทั้ง 2 dialect (spec §3 · แผน 2)
- agent ไม่ push · agent ไม่ deploy เอง · merge เข้า main ได้หลัง audit + final review (opus) เท่านั้น (D42, D49) · โมเดล agent ตาม D43 · commit ไม่มี trailer ของ AI และ `docs/**` commit ได้ (D45)
- ทดสอบบนแท็บเล็ตจริงเลื่อนไปรอบท้ายสุด (D51) — รายการของแผนนี้ (S5-1…S5-10) อยู่ใน Task 13 Step 2 และทำได้หลังแผน 5b deploy แล้ว
