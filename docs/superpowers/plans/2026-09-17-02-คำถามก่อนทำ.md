**สรุป:** ไม่มีคำถามที่ขวางการเริ่มแผน 2 — ทุกข้อด้านล่างเป็นเรื่องของแผน 3–6 ที่ schema ของแผน 2 รองรับได้ทุกทางเลือกโดยไม่ต้องแก้ตาราง แต่ควรตอบก่อนเขียนแผนที่เกี่ยวข้อง

## คำถามถึงเจ้าของ

### Q1. ออเดอร์ LINE: ใครออกเลข `seq` ของ event เมื่อทั้งเซิร์ฟเวอร์และแท็บเล็ตเขียน event ให้บิลเดียวกันได้

**ที่มา:** D38 ให้ `order_event` มี `seq` ต่อบิล และ schema บังคับ unique (order_id, seq) · ออเดอร์ LINE มีคนเขียน event 2 ฝั่ง: เซิร์ฟเวอร์ (`CREATED`, `PAYMENT_CLAIMED`, `CANCELLED` อัตโนมัติ) และแท็บเล็ต (`PAID`, `REJECTED`, `READY`, `PICKED_UP`) · spec §6.5 บังคับให้กด "รับเงินแล้ว" ต้องออนไลน์ แต่ไม่ได้พูดถึง "ปฏิเสธ" · ถ้าแท็บเล็ตปฏิเสธตอนออฟไลน์ ขณะเดียวกันลูกค้ากด "โอนแล้ว" ทั้งสองฝั่งจะได้ seq เดียวกัน แล้วฝั่งที่ส่งทีหลังจะ sync ไม่ผ่าน

**ทางเลือก:**
- (ก) การกระทำบนออเดอร์ LINE ที่ยังไม่ paid (รับเงิน/ปฏิเสธ) ต้องออนไลน์ และเซิร์ฟเวอร์เป็นคนออก seq · หลัง paid เซิร์ฟเวอร์ไม่เขียน event ให้บิลนั้นอีก แท็บเล็ตออก seq เองได้
- (ข) ปฏิเสธตอนออฟไลน์ได้ ถ้าชนกันให้เซิร์ฟเวอร์เลื่อน seq ของฝั่งที่มาทีหลัง (ต้องคำนวณแฮชใหม่ → ขัดหลัก insert อย่างเดียว)
- (ค) เลิกบังคับ unique (order_id, seq)

**แนะนำ: (ก)** — ตรงกับหลักใน §6.5 อยู่แล้ว ("ออเดอร์นี้มาจากเน็ตอยู่แล้ว") ไม่ต้องแก้แฮชย้อนหลัง และคง unique ที่ช่วยจับ event ซ้ำได้ · ไม่กระทบแผน 2 · ต้องตอบก่อนแผน 5/6

### Q2. ยกเลิกบิลเงินสดของ **กะ/วันก่อน** ได้ไหม และเงินคืนลงกะไหน

**ที่มา:** D36 กำหนด `VOID_REFUND` และสูตรเงินสดคาดหวัง แต่ไม่ได้บอกกรณีบิลชำระในกะที่ปิดไปแล้ว (Z report ของกะนั้นเป็น snapshot แก้ไม่ได้)

**ทางเลือก:**
- (ก) ได้ · `VOID_REFUND` ลงกะที่เปิดอยู่ตอนยกเลิก (เงินออกจากลิ้นชักวันนี้) · Z ของวันเก่าไม่เปลี่ยน · รายงานแสดง "ยกเลิกบิลข้ามวัน" แยก
- (ข) ยกเลิกได้เฉพาะบิลของกะที่ยังเปิด · บิลเก่าต้องคืนเงินนอกระบบแล้วบันทึกเป็น `PAID_OUT` พร้อมเหตุผล
- (ค) ห้ามทั้งหมด

**แนะนำ: (ก)** — เงินสดในลิ้นชักตรงกับความจริงของวันที่คืนเงิน, Z เก่ายังแก้ไม่ได้ตาม D22, และยังตามรอยได้ด้วย `cash_movement.order_id` · schema แผน 2 รองรับทุกทางเลือก · ต้องตอบก่อนแผน 3

### Q3. ต้นทุนมาตรฐานของ **ของที่ไม่นับสต็อก** (น้ำแข็ง น้ำ เกลือ) จะอัปเดตเมื่อไร

**ที่มา:** D34 ให้ต้นทุนมาตรฐาน = ต้นทุนเฉลี่ยจากบันทึกซื้อ **ณ วันนำเข้า** · spec §4.2 คิดต้นทุนของที่ `is_tracked=false` ด้วย `standard_cost` เสมอ (ไม่ใช้ถัวเฉลี่ย) · ถ้าราคาน้ำแข็งขึ้นหลังเปิดใช้ระบบ ต้นทุนต่อแก้วจะไม่เปลี่ยนตามจนกว่าจะมีคนแก้ค่า

**ทางเลือก:**
- (ก) ไม่อัปเดตอัตโนมัติ · เจ้าของแก้ในหน้าจัดการสินค้า (บันทึก audit_log) · ตอนรับของเข้า ถ้าราคาต่อหน่วยต่างจากต้นทุนมาตรฐานเกิน 10% ให้ขึ้นเตือน
- (ข) รับของเข้าของที่ไม่นับสต็อก → ตั้ง `standard_cost` = ราคาต่อหน่วยของบิลล่าสุดอัตโนมัติ (บันทึก audit_log)
- (ค) ถัวเฉลี่ยเคลื่อนที่เหมือนของที่นับสต็อก (แต่ไม่มียอดคงเหลือจริงให้ถ่วงน้ำหนัก)

**แนะนำ: (ก)** — ตัวเลขต้นทุนเปลี่ยนเฉพาะเมื่อคนตั้งใจเปลี่ยนและมีร่องรอย (D12, D21) และไม่ต้องเดาน้ำหนักถัวเฉลี่ยของของที่ไม่ได้นับ · ไม่กระทบแผน 2 · ต้องตอบก่อนแผน 4

### Q4. เมื่อแก้ต้นทุนมาตรฐานของดิบหรือแก้ BOM ภายหลัง ต้นทุนมาตรฐานของเบส/ชุดบรรจุภัณฑ์ต้องคำนวณใหม่ไหม

**ที่มา:** แผน 1 เก็บค่า roll-up จาก BOM ลงใน `item.standard_cost_usat` ของเบส 7 ตัวและชุดบรรจุภัณฑ์ 3 ชุด (แผน 2 คัดลอกลง DB ตรง ๆ) · ค่านี้ใช้เป็นต้นทุนเฉลี่ยก่อนมีการทำเบสครั้งแรก (§4.4) และเป็นต้นทุนชุดบรรจุภัณฑ์ตลอด (ไม่นับสต็อก จึงระเบิดลงของดิบตอนขาย แต่หน้าจัดการเมนูใช้แสดงต้นทุน/แก้ว)

**ทางเลือก:**
- (ก) คำนวณใหม่อัตโนมัติทุกครั้งที่ต้นทุนมาตรฐานของส่วนประกอบหรือ BOM เปลี่ยน แล้วบันทึก audit_log ของ item ที่ได้รับผล
- (ข) เก็บค่าเดิม มีปุ่ม "คำนวณต้นทุนมาตรฐานใหม่" ให้เจ้าของกดเอง
- (ค) ไม่เก็บค่าในตาราง คำนวณสดจาก BOM ทุกครั้ง (ต้องแก้ข้อตกลงในแผน 1 ที่เก็บค่า roll-up ไว้)

**แนะนำ: (ก)** — ค่าที่เก็บไว้จะไม่เพี้ยนจาก BOM ปัจจุบัน และยังมีร่องรอยทุกครั้ง · ไม่กระทบแผน 2 · ต้องตอบก่อนแผน 5 (admin)
